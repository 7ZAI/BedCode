# 代码查看器为宿主内置功能（非 WASM 插件）

## 背景

BedCode 有完整插件系统（桌面端 WASM 组件沙箱 + 移动端加载），终端窗口 header 存在 `PluginTerminalToolbar` 插件扩展点。直觉上"终端工具栏新增按钮 + 文件浏览 UI"像是一个插件该做的事。

但两个现实约束让插件形态不成立：

1. **fs_auth 三层授权**：插件访问宿主文件系统须过「路径白名单 → 插件白名单 → 弹窗授权」。一个完整的目录树浏览器代表对任意目录树的高频遍历——每次进入未授权目录都弹窗，交互不可用。宿主自身调用文件系统则天然豁免（宿主就是授权主体）；
2. **无跨端复用诉求**：代码查看器只服务桌面端终端窗口（移动端是瘦终端，不承担代码浏览），没有作为插件跨端分发的价值。

## 决定

**代码查看器作为宿主内置功能实现**：

- 新增 Rust 命令域 `commands/code_viewer.rs`（目录列举 / 文件读取 / 路径安全校验，遵守 AppError 与防目录穿越约束）；
- 前端为 Vue 组件 + composable（`useCodeViewer`），状态按 sessionId 隔离并持久化到 localStorage；
- 工具栏按钮直接进终端窗口 header，位于插件扩展点之前；`PluginTerminalToolbar` 只承载插件注册项，不为本功能开特例。

插件系统的 fs 能力面**不因本功能扩展**——文件树浏览的宿主私有路径不走 WIT 契约。

## Considered Options

- **WASM 插件形态**：走 fs_auth 弹窗高频受阻；同时 ABI 契约（WIT）要把目录树浏览/大文件读取变成宿主原语——那是为移动端消费方设计的接口面，为单一桌面端消费方扩容得不偿失。
- **宿主内置（本决定）**：零授权摩擦、零 ABI 变更；代价是代码面板领域逻辑与插件系统无交集，后续若插件想"向代码面板推送已修改文件"，走既有消息总线/事件通道即可，不改变归属。
- **插件 + 宿主一次性授权整个锚点目录**：fs_auth 支持路径白名单，理论上可预授权根目录——但根目录可被用户随时切换，白名单维护与同步是持续成本，且白名单本质是"信任此目录"，与树浏览器"浏览任意目录"的形态冲突。否决。

## Consequences

- 桌面端 `src-tauri` 新增一个命令域，插件 SDK/WIT/双端 host_impl 均无改动。
- 代码面板成为终端窗口的宿主特征，而非插件生态的一部分——插件无法被审批流阻止，也无法被用户禁用（与插件可控性取向不同，此为有意取舍：它是核心观察工具，不是扩展）。
- 未来如需"代码面板感知插件事件"，入口是 `events/` 与插件消息总线，宿主侧只做转发不做编排。
