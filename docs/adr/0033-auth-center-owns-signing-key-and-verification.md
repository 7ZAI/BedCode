# 认证中心持有入场签发密钥并执行验签（auth center owns the signing key and verification）

## 状态

**已实施**（2026-09-29，desktop ABI v32 → **v33**；mobile ABI 保持 11）。
spec：`.scratch/2026-09-29-auth-center-owns-signing-key/spec.md`（8 票，实施记录见文末）。
**本 ADR 修订 ADR 0031 的 K5「凭据与密码学不动」**（修订记录追加，**不改原文**——
ADR 是时间切片，改写会丢失决策现场）。
边界单一事实源仍是 **ADR 0022**；本 ADR 不改 B1–B6 判据，只改**归属**（见 §归属裁决）。

## 背景

ADR 0031 把「谁是认证中心」从启发式改成注册事实、把裁决切 fail-closed。落地后的架构复核
暴露出两处**设计与文档的错位**（都不是 bug）：

**错位一：`plugin_secrets` 同一张表里躺着两把同名的钥匙。**

| 属主 | 键 | 来源 | 今天谁用 |
| --- | --- | --- | --- |
| `host` | `jwt.key` | 宿主 `utils/auth/jwt.rs` → `host_secrets` 首启生成 | 宿主四处验签 + `host-auth device-token-*` 代签 |
| `com.bedcode.terminal-session` | `jwt.key` | 插件 `pairing/keys.rs` guest 内 `getrandom` | **无人**——activate 里探活只为打一行 `len` 日志 |

隔离是 `WHERE plugin_id = ?1` 做实的，两把钥匙互不通用。而插件那把是**死的**：生产签发
路径走 `host.auth_device_token_issue(...)` 绕回宿主，插件自带的 HS256 实现
（`pairing/jwt.rs`）在生产路径上零调用点。**名义上的「密钥不出宿主」与事实相反**：
插件自己就持有明文副本并带完整密码学实现。

**错位二：文档把「不同 key 域」写成了「插件无法验签」。**
`bedcode.wit` 的 `auth-policy` 接口注释写着「插件密钥域与宿主不同，**无法也不应验签**
——验签执行点留宿主」。前半句成立（属主隔离），后半句不成立。跨越这条注释去查事实的
方法不是读注释，而是**追密钥**：注释说「密钥不出宿主」，而 `keys.rs` 正在 guest 内生成
它。**跨实现锁也不构成反证**：`utils/auth/jwt.rs::host_jsonwebtoken_matches_plugin_fixed_vector`
两侧都用**固定注入 key**，只证明「两个实现产出逐字节相同的 token」（格式锚点），
**不证明**两个 key 域能互通（它们本来就不互通）。

**错位三：验签散落宿主四处**（HTTP `/api` 中间件 / 端点档位闸 / 协议网关 / WS 插件端点
首消息 / `host-auth` 两个原语），每处各自 `JwtService::new()` 各验一遍。

## 决定

用户裁定（2026-09-29）：**验签与密钥生成等放入认证中心**——理由是「认证中心作为内部
业务服务是高度可信的」。

| # | 决定 | 状态 |
| --- | --- | --- |
| **D1** | **入场签发密钥的生成、签发、验签全部归认证中心**（`com.bedcode.terminal-session`）。宿主不再持有任何设备 JWT 密码学 | 用户裁定 |
| **D2** | 中心是**内部业务服务**，作为本机信任锚点，可信度等同于宿主。这是 D1 的前提 | 用户裁定 |
| **D3** | 迁移：**接受存量已配对设备全量重新配对**，不做过渡期双密钥验签 | 按 spec §17 推荐采纳（与 v24 退役三表口径一致） |
| **D4** | 新增**密钥轮换**（`kid` + 上一代宽限验签） | 按 spec §17 推荐采纳；否决路径见 §9 末「降级预案」 |
| **D5** | ABI 破坏性 bump **32 → 33**：`host-auth` 退役 `device-token-issue` / `device-token-verify` | 由 D1 直接推出 |

## 信任模型论证：为什么「中心可信」成立

D1 表面上违反「验签方应当是信任锚」的直觉，需要论证「中心**就是**信任锚」。

**关键事实：入场凭证是 HS256 —— 对称算法**（`pairing/jwt.rs`，自实现 HMAC-SHA256）。
对称意味着**验签方与签发方持有同一把秘密**。因此：

1. **中心今天已经能伪造。** 它调 `host-auth device-token-issue` 就能给任意设备签发入场
   token，而 `enforce_connection_policy` 决定放行。**「中心能签发」与「中心持有密钥」
   的权限差距，只差一次可审计的 API 调用 vs. 一块内存里的裸密钥。**
2. 既然中心已被授予「为任何设备签发入场凭证」的权力，把签发密钥交给它**不增加任何实际
   权限**。
3. 反过来，**验签方必须是签发方**——这是对称密码学的硬约束：中心若要验签，就得能读宿主
   那把密钥，也就必须跨 `plugin_secrets` 的属主隔离。这正是 D1 要消除的东西。

**结论**：把密钥与验签收敛到中心，是让实现**匹配既有的授权事实**，而不是扩大授权面。

### 这个论证的边界（必须写明）

它成立的前提就是「中心可信」。两条已知边界：

- **中心可被替换**（ADR 0031 明确「单中心注册表天然允许未来换人」）：信任锚因此可被换掉。
  这在今天的 fail-closed 模型下**已是既有事实**（中心停用 = 认证面全断），本 ADR 不改变
  这一点，**只是让它更诚实**：换掉中心 = 换掉签发密钥，旧 token 全部作废。
- **泄露后果从「理论」变「不可恢复」**：D1 之后入场密钥明文躺在 guest 线性内存里。
  `utils/auth/` 下**今天没有任何轮换机制**（已 grep 确认无 rotate/rotation），故 D4 必须
  同批落地——否则这把密钥一旦泄露，既不能吊销也不能换钥，只能全量重新配对。

## 性能实测：决策依据，不是估算

探针：`bedcode-desktop/src-tauri/src/wasm_core/manager/runtime/tests/auth_center_perf.rs`
（只读探针，**必须 `#[ignore]` 显式运行**，理由见该文件头：它让中心整段在册，而注册表
是进程级单槽）。真实 terminal-session 产物 + 真实 WASM 导出调用，`cargo test` dev
profile，N=1000，3 轮：

| 段 | 耗时 | 占热路径 |
| --- | --- | --- |
| **A** 宿主原生验签（HS256，进程内） | 5.96 – 7.09 µs/op | ~6% |
| **B** 认证中心往返（guest 导出调用） | 95.7 – 113.5 µs/op | **~94%** |
| 每请求合计（`jwt_gateway` 热路径） | 101.7 – 120.6 µs/op | |
| 中心往返 / 原生验签 | 15 – 17× | |
| 单实例串行吞吐上限 | 8,300 – 9,800 req/s | |

**三点结论**：

1. **平均成本不是问题。** 移动端远程终端的请求量是几十/秒量级，离 9k/s 差三个数量级。
2. **crypto 放哪几乎不影响性能。** A 只占 6%，把验签搬进 guest（WASM 里 HS256 约
   10–20 µs）相对 100 µs 的往返仍是小头。**D1 与性能解耦**，可以纯按信任模型决策。
3. **真正的杠杆在消掉每请求往返**（B 占 94%），且与 crypto 位置无关（本地信任缓存 /
   撤销推送 / WS 建连时裁决 + HTTP 短 TTL 缓存）。**本 ADR 不做**（见 §Out of Scope）。

### 实施后复测（2026-09-29，票 06 交付）

**结论 2 当时预测的代价确实发生了，但它很小，且不改变任何决策依据。**

| 段 | 变更后实测（N=1000，3 轮） |
| --- | --- |
| 认证中心一次调用（**含 guest 内 HS256 验签**） | **130.6 / 135.1 / 135.0 µs/op** |
| 单实例串行吞吐上限 | ~7,400 req/s |

对照变更前合计 101.7 – 120.6 µs/op：**合计上升约 12–27%**，并非持平。原因与
§性能实测 结论 2 动手前的预测一致——HS256 验签改在 WASM 内执行（约 10–20 µs）而非
宿主原生（约 6 µs），往返本身（约 100 – 113 µs）仍是绝对大头。**真实负载是几十/秒
量级，距 7.4k/s 仍差两个数量级以上**，故 D1 仍与性能解耦。

记录这条数字而不是只写「合计不劣化」，是因为：探针**没有**硬阈值门禁（绝对值随机器 /
构建模式波动，阈值化会因 CI 负载抖动假红），所以「不劣化」若不附实测值就是一句无法
被反驳的空话；后来人复查时会把它当成已验证的结论。**探针本身的修法**记在这里：
它原先用 `test_tokens::issue`（经 `auth-grant` 互调）取 token，而本探针自建
`WasmRuntime` 不经过 `PluginHost` ⇒ 消息总线无 dispatcher ⇒ guest 收不到互调请求，
表现为 5s 超时（**不是**订阅竞态，加重试无用）。改用 `seed_keyring` + 以同一把密钥
`sign_with_seeded_key` 后可跑通——两者与生产「中心自签自验」同构，字节级等价由插件侧
冻结向量钉住。

### 已记账的既有风险（本 ADR 不修）

- `CallModel::Mutex` 是默认（`wasm_core/config.rs`）：**每实例一把锁全程持有**，同实例的
  策略调用**串行**，并发不提升吞吐。
- `block_on_async` 落在 actix worker → **每个在飞请求占住一个 actix worker 线程**直到完成。
- 超时 `AUTH_CENTER_TIMEOUT_MS = 5_000`。
- 合起来：**N 个慢 / trap 的中心调用 = 整个 HTTP server 停摆最长 5 秒**。触发条件是
  「插件慢」（同实例其它插件做重活时排队），不是外部攻击，但是**可自伤**。

## 归属裁决（ADR 0022 §5.1.2 三问）

1. **离宿主能实现吗？** 不能——入场密钥的签发/验签是一次业务授权的产物，宿主没有第二个
   消费者（只有中心签发 + 中心验签两个面，都在中心内部）→ 归插件
2. **携带产品语义吗？** 是。「设备入场凭证」是产品概念（设备名、指纹、撤销、配对关系、
   7 天窗口），宿主既不解释也不需要解释 → B1/B3 命中
3. → **归插件**

宿主侧留下的是 ADR 0022 §5.1.3 允许的两类薄壳：

- **安全闸门**：`enforce_connection_policy` 只做「问中心一次」+ `deny_kind` 三态分类，
  中心不可达即拒（fail-closed 不变）
- **零解析窄转发**：`auth-method-invoke` / 会话互调不变

**裁决门返回值的修订**：ADR 0032 时代的锁 `l2_gate_returns_decision_only` 要求
`enforce_connection_policy -> Result<(), String>`（宿主只回裁决、不拿产品事实）。D1 之后
宿主**必须**拿到认证身份（`deviceId` / `deviceName` / `fingerprint`）才能填连接会话与
转发给插件的 `caller` 上下文——那**不是新增产品事实**，而是同一个数据换了来源（宿主验签
结果 → 中心裁决结果）。故该锁**收紧**而非放宽：成功态改为一枚字段集**钉死**的
`AuthenticatedIdentity`（恰好 3 个字段），仍禁止返回配对记录 / 信任列表 / 任何设备档案，
仍禁止 `&mut` 出参与额外上下文参数。修订理由记在锁的文档注释与 ADR 0032 的实现记录里。

## 目标形态

```text
今天（两个 key 域）                      目标（一个 key 域）
─────────────────────────────────────    ─────────────────────────────────────
插件 keys.rs 生成 key（死代码）    ──▶    插件 keys.rs 生成 key（活，唯一真源）
插件 auth_http → 宿主 device-token-issue ─▶  插件 auth_http → 插件本地 sign
宿主 JwtService sign/verify         ──▶    宿主无 JWT 密码学
plugin_secrets ('host','jwt.key')  ──▶    该行成为死数据并清理
四处宿主验签                        ──▶    一处：中心 verify-device-token
```

**收敛点**：中心的 `policy::evaluate` 本来就已经在做结构复检 + claims 解析 + 时效 +
撤销检查，只差密码学那一步。**这是「补上一行」，不是「新建一条链路」。**

## WIT 契约变更（ABI 32 → 33，破坏性）

`packages/plugin-sdk-desktop/rust/wit/bedcode.wit` · `host-auth` 退役 2 函数：
`device-token-issue` / `device-token-verify`（理由：中心自持密钥后不再需要宿主代签 /
代验）。

**`host-auth` 保留面（不动）**：`secret-get/set/delete/keys` · `auth-setting-set` ·
`biometric-credential-bound` / `biometric-verify-signature` / `biometric-credential-bind` ·
`link-identity-parts` · `auth-center-register` / `auth-center-unregister` /
`auth-methods-list` / `auth-method-invoke`。

**token wire 格式逐字节不变**：HS256 + 三段 base64url + claims 形状
`sub` / `iss` / `iat` / `exp` / `device_name?` / `fingerprint?`（D4 的 `kid` 是
**可选追加**字段，`skip_serializing_if = "Option::is_none"`，旧 token 无该字段时走
「验上一代 / 验当前」路径）。移动端把 token 当**不透明串**（只存 localStorage、只往上传，
从不自行验签或解析），**移动端零改动**。

**双端偏离登记**（ADR 0022 修订记录追加）：本组 2 函数是**桌面独有**（移动端 WIT/SDK
本就不含它们，grep 已核实），移动端不跟演不投影，mobile ABI 保持 11。

## 迁移路径

### 存量设备

`auth_http/mod.rs::handle_reauth`：设备用**旧 token 本身**当证明来换新 token
（验签旧 token → 签发新 token）。密钥一换，旧 token 验不过 → 换新失败 → 只能走配对码 /
QR / 生物重配。

采纳 D3（方案 A：全量重配）：与 v24 退役 `pairings` / `connection_history` /
`session_configs` 三表的既有口径一致（不兼容旧版本存量用户）。方案 B（过渡期双密钥）
被否的理由：它要求中心**一次性跨属主接管**宿主旧 `jwt.key`——正是 D1 要消除的动作，
且要在中心里长期留一条「两把 key 都验」的分支。

**用户可见面**：重配后移动端 `authenticate` 拿到「凭证失效」而非网络错误，**文案必须
区分**（ADR 0030 错误码口径，见 §失败模式 F3 与实施记录）。

### 发布顺序（spec §10.2 三步法的实际执行）

| 阶段 | 宿主 | 中心插件 | 结果 |
| --- | --- | --- | --- |
| 迁移前 | ABI 32，宿主持钥验签 | v32 产物（委托宿主代签） | 现状 |
| 步骤 1 | ABI 33 代码就位，**宿主仍持钥验签**（旧路径保留） | v32 产物仍可用 | 行为不变，为步骤 2 留回归窗口与回滚点 |
| 步骤 2 | 宿主验签退役，四处改调中心 | v33 产物（自持密钥） | 中间态：宿主已切、中心未升级 → **全部认证拒绝** |
| 步骤 3 | 同上 | v33 产物发布 | 恢复正常（存量设备需重配） |
| 兜底 | `stale_artifact_rebuild_hint` 点名；UI 给「认证中心未就绪 / 需重新配对」显式信号 | — | 排障不靠猜 |

**发布纪律**：步骤 2 与步骤 3 的两个产物（宿主 + 中心插件）**必须同批发布**。本仓插件
产物全部由源码构建（同批成本低）。**降级预案**：步骤 2/3 之间出问题，回滚宿主到步骤 1
版本即可（旧路径仍在），不需回滚插件产物——这是「步骤 1 保留旧路径」的设计目的。

## fail-visible 三形态（AGENTS §8）

| 形态 | 落点 |
| --- | --- |
| ① 旧读路径显性失败 | `device-token-issue` / `device-token-verify` 退役后，插件若仍调 → **实例化期**缺 import 即报错，不静默 |
| ② 旧产物点名重建 | `LoadedWasmPlugin::stale_artifact_rebuild_hint`：v32 产物拿到点名缺失 import + 「按 v33 SDK 重建」 |
| ③ 退役字眼加载即抛 | 宿主源码扫描锁「宿主无 JWT 密码学」（`JwtService` / `verify_token_with_expiry` / `generate_device_token` / `verify_device_token` 零命中），手法同 `l2_gating_test.rs` |

补充（F4）：**中心密钥不可用时 activate 显性失败**——禁止降级为「用进程随机密钥后仍
对外服务」（那比重启即全灭更糟：设备以为已配对，实际每次重启全灭）。

## 失败模式与可观测性

| # | 失败 | 现象 | 处置 |
| --- | --- | --- | --- |
| F1 | 中心未注册 | 全部认证拒绝（`no_center`） | ADR 0031 已承认的可用性耦合；UI 显式信号（实施记录 §6） |
| F2 | 中心 trap / 超时 | `deny_kind=unavailable`，全部拒绝 | 既有；见上文「已记账的既有风险」 |
| F3 | 存量 token 验不过 | `handle_reauth` 返回凭证失效 | D3；文案必须区分「凭证失效（需重新配对）」与「网络错误」 |
| F4 | 中心密钥生成失败 | activate 显性失败 | 禁止降级 |
| F5 | 旧产物 | 实例化期点名 | fail-visible ② |

**日志字段**（AGENTS §8 结构化字段红线，`key = %value` 形式，禁止拼进消息）：
`deny_kind`、`center_id`、`center_owner`、`plugin_id`、`device_id`、`request_id`、
`key_id`（仅轮换时）。**禁止**把 JWT / claims / 密钥任何片段写进日志或错误文本
（凭据红线）——日志只记长度与 `key_id`。

## Considered Options

| 方案 | 为什么不选 |
| --- | --- |
| **A 维持现状**（插件代管密钥、宿主代签代验） | 就是错位现场：两把同名死钥匙 + 一条零生产调用点的密码学实现 + 注释与事实相反。留着等于让后来人按错误文档做判断 |
| **B 宿主把密钥推给中心**（中心不持久化，activate 时领取） | 中心重启要重新领，且密钥在两处内存里——**不减少**暴露面，只增加领取协议 |
| **C 改用非对称签名**（EdDSA / RS256：中心持私钥、宿主持公钥） | 那才是标准做法，但它是**另一套信任模型** + **另一次存量作废**，且宿主要维护公钥真源与轮换面。本批不做（见 §Out of Scope） |
| **D 宿主保留验签、中心只签发** | 对称算法下验签方必须持密钥 ⇒ 中心得把密钥推给宿主 ⇒ 回到「宿主代验」，等于什么都不改还要多一条推送链路 |
| **E 过渡期双密钥**（中心一次性接管宿主旧 key，7 天宽限） | 见 §迁移：要求一次**长期密钥跨域移动**，正是 D1 要消除的动作 |

## Consequences

### 正面

- 「密钥不出宿主」这句话从此**为真**（宿主确实不再持有设备入场密码学）；
- 两把同名死钥匙收敛为一把活钥匙，插件那把密码学实现从死代码变成生产路径；
- 验签执行点从宿主四处收敛到中心一处，`deny_kind` 的失败面从「两次调用」收窄为
  「一次调用」（宿主验签 → 问中心，两步变一步）；
- 密钥轮换成为可能（D4），把「理论泄露风险」变成「可恢复」。

### 代价 / 风险

- **破坏性变更**：ABI 32 → 33，`host-auth` 两函数退役；**存量已配对设备需全量重新配对**；
- **宿主可观测性变厚**：认证拒绝的根因（`no_center` / `unavailable` / `policy`）现在
  **只在中心侧产生**，宿主日志里的 `deny_kind` 成了唯一线索——`policy` 态的原因串由中心
  透出，中心必须自己打点；
- **中心停用的爆炸半径不变**（fail-closed，ADR 0031），但现在还多一件：中心密钥丢失
  等于全量重配；
- **L2 反向依赖的信任面变厚**：宿主从「问一个安全闸门」变成「把入场凭证的签发权交给
  它」。这是 D2 明确承担的信任，D4 是它的对价；
- 移动端零改动（token 不透明），但**用户可见**：迁移后需重新配对，文案必须区分。

## Out of Scope

- 不改 fail-closed 语义（ADR 0031 K3）：无中心仍是一律拒绝。
- 不改移动端 WIT / ABI / 代码（mobile ABI 保持 11），移动端只在新 i18n 文案上配合。
- 不消每请求往返（性能结论 3）：信任缓存 / 撤销推送 / 裁决降频是独立专项。
- 不改 token wire 格式的**既有字段**（只可选追加 `kid`）。
- 不引入非对称签名（方案 C）。
- 不动生物凭证验签（`biometric-verify-signature`）：P-256 公钥由宿主托管，与设备入场
  JWT 是两条线。
- 不做认证中心热切换 / 多中心按 method 分派（ADR 0031 K4）。
