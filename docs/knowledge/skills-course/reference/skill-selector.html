Matt Pocock Skills 速查表

"选哪个技能"的一页答案。按要干的活分组；每行：触发词、什么时候用、什么时候别用、最佳用法。

触发格式统一为 /技能名。术语：主线 = idea → ship 的默认路径；on-ramp = 旁路并入主线；seam = 测试切入的公共边界。

2 · 主线流程：idea → ship

绝大多数新功能走这条路。顺序：磨想法 → （切票）→ 实现 → 评审 → 提交。

技能何时用何时别用最佳用法
/grill-with-docs 有代码库，要把模糊想法磨清楚；状态化，落 CONTEXT.md + ADR 没代码库 → 用 /grill-me；想法已很清楚 → 直接 implement 从这一步起保持一个未中断的 context window直到 to-tickets 完成
/grill-me 没代码库，磨任何计划/设计；无状态、不落本地 有代码库且想要留痕 → grill-with-docs 和 grill-with-docs 共用 /grilling 原语：一次一问、给推荐答案
/grilling 底层访谈原语，被上面几个技能内部驱动 通常不直接调 —— 让 grill-me / wayfinder 去调 事实去环境里查，决策归你，每题等你答才继续
/to-spec 对话磨清楚了，要把它固化成可构建的 spec（多 session 构建前） 一次 session 能干完的小活 → 跳过，直接 implement wayfinder 地图清了也在这里并入：把 linked decisions 塌缩成 plan
/to-tickets spec 要拆成可独立领取的 tracer-bullet 票，每张声明 blocking edges 单 session 小活；或 triage 产出的票（已经 agent-ready） 本地 tracker = .scratch/<feature>/issues/ 一票一文件；按 blocker 顺序领
/implement 按 spec/ticket 实现一块工作 还没 spec/ticket —— 先 grill/to-spec；纯探索用 prototype 内部驱动 /tdd，结尾跑 /code-review 再 commit；每张票开新 context
/tdd 要测试先行地造一个具体行为；红→绿循环 想要完整 spec 流程 —— 它只是 implement 的内件；重构属评审阶段不是循环内 先定 seam 并和你确认；竖直切片（一测试一实现），别横向铺所有测试
/code-review 评审自某固定点（commit/branch/tag/merge-base）以来的 diff 还没东西可评；或评审对象不是 diff 双轴分开看：Standards（仓库规范+Fowler smell 基线）vs Spec（需求对齐），别合并排一名

3 · On-ramps（旁路并入主线）

不是你主动发起的新功能，而是"情况来了"——处理后并入主线 implement。

技能何时用何时别用最佳用法
/triage 别人提的 bug/需求堆积，要走 triage 角色状态机、产出 agent-ready 票 /to-tickets 自己产的票 —— 已经 agent-ready，别再 triage 五个角色标签：needs-triage / needs-info / ready-for-agent / ready-for-human / wontfix
/diagnosing-bugs 难 bug：一眼看不出、间歇 flake、两个已知好状态间的回归 一眼能定的 bug —— 直接修；想边修边加功能的复杂改动 拒绝先理论化，先建一条就红的反馈环，再用回归测试修；找不到 seam 就 handoff 给 improve-codebase-architecture
/wayfinder 巨型雾状工作：一次 session 装不下、且看不清路线 well-scoped 的小功能；或看得清路只是活多 —— 直接 to-spec/to-tickets 产 decision tickets（决策，不是交付）；地图清了 handoff 到 to-spec，不直接 implement

4 · 跨 session（上下文管理）

context 快满或要分叉时用。一个 fork、一个 continue。

技能何时用何时别用最佳用法
/handoff 对话满了/要分叉（如进 prototype session）；把对话压成 markdown，开新 session引用它 想留在同一对话 —— 用内置 /compact 双向桥：handoff 出去 → 新 session 干 → handoff 回来带上结论
/compact （内置） 留在同一对话，在阶段之间压缩早期轮次 阶段中途 —— agent 会迷失；要留痕用 handoff handoff 是 fork，compact 是 continue；别搞反

5 · 独立工具（主线之外）

不并入主线的独立技能，按需取用。

技能何时用何时别用最佳用法
/prototype 一个设计问题纸面定不下：状态模型对不对、UI 该长啥样 要保留的代码 —— 它是 throwaway，留答案删代码 主线第 2 步的支路：handoff 出 → prototype → handoff 回
/research 把读资料腿活委托给后台 agent，对 primary sources 调查，留 cited markdown 当前目录内能查到的；要立刻同步拿答案的 产出带进主线 grill-with-docs 喂思考，不替代思考
/teach 跨多 session 学一个概念，用当前目录做有状态工作区 一次性问答；要立刻产出代码 你现在就在用这个 —— MISSION.md/lessons/reference 体系
/writing-great-skills 写或改技能，要可预测的技能设计词汇 只是用现成技能 本 mission 之外，单独学

6 · 代码库健康 + 词汇层

不是功能开发，是养护 + 跑在其他技能下面的"词"。

技能何时用何时别用最佳用法
/improve-codebase-architecture 有空档，扫"deepening 机会"，生成一个可带进主线的点子 赶功能 deadline；没整块时间评审 它是勘察找候选；选中的那个到 /codebase-design 长凳上去设计
/codebase-design 设计一个模块的形状：小接口 + 深_behaviour + 干净 seam 还没选中要深化的模块 tdd 和 improve-codebase-architecture 都讲这套词（depth/seam/adapter/locality）
/domain-modeling 磨领域语言：挑战模糊术语、消歧 overloaded 词、把难逆决策记成 ADR 是模块形状问题而非用词问题 → codebase-design grill-with-docs 靠它保持 CONTEXT.md 是干净 glossary

速决：拿到一个活，怎么走？

  1. 是别人提来的 raw issue？ → /triage，产出 ready-for-agent 票后并入 implement。
  2. 是难 bug？ → /diagnosing-bugs；找不到 seam 再 handoff 给 improve-codebase-architecture。
  3. 大到一次 session 装不下又看不清路？ → /wayfinder；地图清了 handoff 到 to-spec。
  4. 是自己的新想法？ → 有代码库 /grill-with-docs，没代码库 /grill-me。
  5. 磨清楚后：一次 session 干得完？直接 /implement；干不完 → /to-spec → /to-tickets → 每张票开新窗口 /implement。
  6. implement 内部：红→绿 /tdd（先定 seam），完事 /code-review 双轴评审，再 commit。
  7. context 快满？ 阶段之间用内置 /compact；要 fork 出去用 /handoff。
