#### Cross-end real-interop integration test suite (new `cross-end-tests` package + both-ends `lib` rename; no production logic, no ABI, no version move)

- **What**: a new top-level Rust package `cross-end-tests/` runs the **desktop's real Actix server + the real `com.bedcode.terminal-session` WASM artifact** in the same process as the **mobile's real client code** (`AuthHttpClient` / `SessionHttpClient` / `TerminalLinkManager`) — zero mocks, no adb, no WebView, no emulator, and **run on demand — deliberately not wired into a workflow** (decided 2026-09-30: the build prerequisite is both ends' plugin artifacts, and rebuilding them in CI costs more than it buys; command is `cd cross-end-tests && cargo test`, see AGENTS §3). The pre-existing tests each mock the *other* end (desktop integration uses a generic reqwest / tokio-tungstenite client; mobile integration uses a fake desktop server). Two self-consistent mocks mean a wire-contract drift between the ends ships green on both sides while the real link is broken
- **L0 prerequisite — both `lib` names de-duplicated**: `bedcode_lib` (identical in both packages) → `bedcode_desktop_lib` / `bedcode_mobile_lib`. Two crates with the same name cannot coexist in one dependency graph, so without this the package could only depend on one end. Impact audited and contained to the two ends' own sources/tests/benches plus a handful of string constants (EnvFilter default `bedcode_lib=debug`, the plugin-log target prefix, `System.loadLibrary` in the hand-kept `android-backup` Kotlin copy, and four doc tables). A path dependency keys on the *package* name by default, so `Cargo.toml` names `package = "..."` explicitly
- **Documented behaviour change, not silent**: an operator's existing `bedcode_lib=debug` EnvFilter (and any log rule filtering on the plugin-log target) must switch to the new names. These are developer-tuning settings, not product features. The Android `.so` filename follows the lib name, so `System.loadLibrary("bedcode_mobile_lib")` changes too; the `gen/android` copy is gitignored and regenerated, but the hand-kept `android-backup/app-java/generated/Rust.kt` copy was updated by hand so a restore still matches
- **Coverage (each scenario = its own test binary — `AppContext` is a process-level `OnceLock`)**: pairing / QR / re-auth round-trips with four negative cases; the ADR 0033 keyring **rotation grace period proven from the client side** (a pre-rotation token still authenticates on both the HTTP and the WS face, and post-rotation tokens carry the new `kid`); session-control HTTP surface incl. the `1002` error envelope and the deliberate *remove-idempotent vs stop/input-strict* asymmetry; the **terminal-stream closed loop** where real `bash` PTY bytes travel desktop-plugin → `host-pty` → WS → mobile link ingest gate → page channel; fail-closed for "no auth centre registered" and forged credentials on both the HTTP and WS faces; plugin deactivate/activate ripple onto the mobile connection
- **A cross-end-only finding**: two of the first-draft contracts were wrong, and the real behaviour is the more interesting one. (a) With no auth centre registered the pairing endpoint is **401, not 404** — the no-credential tier is declared by the plugin at activate time, so with no activation there is *no unauthenticated bootstrap path at all*. (b) `remove` on a missing session is **idempotent by design** (documented in `actions::remove_via_host`) while `stop`/`input` are strict — that asymmetry is now pinned cross-end. Both are recorded in the test contracts, not worked around
- **Honest boundaries (documented, not hidden)**: `deny_kind`'s three states are a host **log** field, not a wire field — the client only ever sees 401 (deliberate, to avoid leaking deployment state); the biometric positive path needs an Android Keystore private key that a headless process cannot produce (only the "not bound → 1008" negative is covered); the QR "scan-to-confirm" UI step is bypassed by driving the plugin's own `qr-code-generate` entry point
- **Not wired into CI**: no job was added to `test.yml` (decided 2026-09-30, run on demand). The cost and its mitigation: cross-end contract drift is no longer caught automatically at PR time; it rests on the manual gate "changing a cross-end protocol must run `cross-end-tests`" in AGENTS §10 plus the cross-reference from the protocol chapter in `docs/knowledge/mobile-desktop-auth.md`
- **Verified**: both-ends `cargo test` green after the rename (desktop lib 1058 passed / 0 failed / 1 ignored plus all integration targets; mobile 379 passed / 0 failed); `cross-end-tests` 7/7 green; desktop vitest 1422, mobile vitest 509, root `eslint .` 0 errors; cross-end `cargo fmt --check` and `clippy --tests` clean; mobile `./gradlew :app:compileUniversalDebugKotlin` BUILD SUCCESSFUL; `cargo build --lib` emits `libbedcode_desktop_lib.so` (artifact name follows the lib name, measured); no leftover test processes or ports

#### Test fixtures under `packages/` consolidate into one feature-selected crate (desktop test infrastructure; no production code, no ABI, no version move)

- **What**: the six SDK-bound fixtures `plugin-http-test` / `plugin-task-test` / `plugin-pty-test` / `plugin-wasip3-test` / `plugin-sdk-test` / `plugin-ws-test` collapse into a single `packages/plugin-sdk-fixtures` crate, one per `[features]` slot, and are **deleted**. `plugin-component-test` (hand-written wit-bindgen fixture, 30+ call sites) is **deleted too** — its four observable behaviours (`test.panic`, `test.storage-get`, startup-failure injection, and the `name`/`args`/`stored` reply shape) moved into the `sdk` fixture, and its DB round-trip moved to a new `test.db-roundtrip` command so that `test.echo` — used by the fuel and latency probes — does not carry two extra table round-trips. The six near-verbatim "mtime check + `cargo build`" blocks become one parameterised `build_sdk_fixture(feature)`; each existing builder is now a one-line delegation
- **Mutually-exclusive features are load-bearing, but not for the reason one would guess**: a spike disproved the obvious story. Two features compiled together do **not** collide — `wasm_entry!` / `export!` inside separate modules emit non-conflicting symbols, and the component is ~4x larger with both fixtures in. The real reason for one-feature-per-build is **artifact ambiguity**: `build_sdk_fixture` archives by feature name, so one artifact must map unambiguously to one fixture. Cargo cannot express "at most one", so `compile_error!` enforces it
- **Artifact-name collision and the race it caused**: all features emit the same `bedcode_plugin_sdk_fixtures.wasm`, so a later build overwrites an earlier one. Fixed by archiving each build to a feature-suffixed name. That alone was not enough — with tests running in parallel, one thread could archive *another* thread's half-written file (observed as `failed to parse WebAssembly module`), so build+archive is now serialised behind a process-wide mutex with a double-check of the freshness cache after acquiring it
- **A drift lock caught a real coverage hole this created, not just a count change**: `production_manifests_declare_only_known_vocabulary` asserts how many manifests it scanned, and dropped from 11 to 7 when five `plugin.json` files became one crate's per-feature `http.json` / `pty.json` / `task.json` / `ws.json` + root `plugin.json`. The lock only recognised the single-fixture `plugin.json` name, so **4 fixture manifests had silently fallen out of the permission-vocabulary check**. It now scans every `*.json` in each package/app dir and keeps only those carrying an `id` field (which skips `package.json` / `tsconfig.json`); the floor is raised to 11 with the composition spelled out
- **Cost accepted (deliberate)**: with `plugin-component-test` gone, nothing can produce a component that *omits* an optional interface — the SDK's `wasm_entry!` exports all of them unconditionally. The three degradation tests that relied on such an artifact are removed, so **"an old plugin artifact still loads, and a missing optional export degrades to `Ok(false)`" is no longer covered**. The host's probe-and-degrade code is unchanged; only the test coverage of it is gone
- **`plugin-wasi-test` stays a separate crate and stays on `wasm32-wasip2`**: preopen was migrated to wasip3 on the theory that a shared `WasiCtx` and both p2/p3 linkers made it target-independent. **Empirically wrong** — both preopen E2E cases trap at `filesystem_method_descriptor_open_at`; the p3 linker attaches but the preopened-directory capability is not wired into the p3 filesystem interface. Reverted, both cases green, finding recorded in the source comments. Merging does not require a uniform target
- **`plugin-bench-test` stays separate** (749 lines / 29 commands): a benchmark fixture is a different kind of artefact from a functional closed-loop fixture
- **A latent fixture-staleness bug found and fixed**: the consolidated freshness check watched only the merged crate's own three files, and it short-circuits *before* invoking cargo — so "cargo's dependency fingerprint will notice the SDK changed" does not hold. A change to the SDK left every cached fixture artifact stale: **tests stayed green while exercising the old artifact**. It now walks the SDK's source trees (recursively, rather than an enumerated file list — the old per-builder lists were themselves the same bug waiting to happen) and rebuilds when anything under them is newer. Verified against a cold cache: all six features rebuilt from scratch, suite green
- **Per-fixture manifests**: the merged crate keeps one `<fixture>.json` per fixture; the root `plugin.json` belongs to the `sdk` fixture because `#[plugin_api]` reads that exact path at compile time (ADR 0005 single source of truth) and cross-checks the trait's method names against its `api` field — pointing the module at a *second* copy would have made that anti-drift comparison vacuous
- **One unexplained transient observed, not reproduced**: the first full run after the four wasm application artifacts were rebuilt reported 1055 passed / 2 failed; five subsequent runs (including one with all fixture artifacts deleted, forcing six live rebuilds) were all 1057 green. Most likely an overlap with the application-artifact rebuild, but that is a hypothesis — the failing test names were not captured and it did not recur
- **Verified**: host `cargo test` **lib 1057 passed / 0 failed / 1 ignored**, all integration targets green (broadcast_shutdown, build_manifest_smoke, error_envelope_integration, http_auth_biometric, link_crypto_http, pty_session_chain, server_integration, ws_auth_rules); `scripts/wasip3-toolchain.sh fixture` still produces a magic-validated Component off the merged crate. `bedcode.wit` unchanged, so no ABI implications

#### Terminal history truncation no longer toasts — silent on both ends (desktop wasm app `com.bedcode.terminal-session` + mobile; **no WIT/ABI move**)

- **What**: when history exceeds the cache (ring eviction / truncation), neither the desktop nor the mobile end prompts the user anymore — one background log line remains for diagnostics. Aligned with mature terminal products (no prompt; the user is none the wiser). Also removed the orphaned `desktop.terminal.historyTruncated` host copy key and the plugin/mobile i18n keys that had no consumers left

#### SDK `wasm_entry!` stops logging guest-reported failures at error level (desktop SDK behaviour; all four wasm application artifacts rebuilt; SDK package needs re-publishing)

- **What**: all ten failure paths inside the `wasm_entry!` macro — `activate` / `deactivate` / `on_startup` / `on_shutdown` / `on_message` / `on_message_binary` / `on_process_done` / `on_ws_message` / `on_ws_client_message` / `on_task_event` — now call `log_warn` instead of `log_error`
- **Why**: AGENTS.md §8 states a hard rule — *「guest 自报的可处理错误不升 `error!`」*. These `Err` values are the plugin reporting its own failure (the inner layer of the two-layer `Result`), not host-side evidence. Genuine host faults — traps, store poisoning, fuel exhaustion — are already logged `error!` and counted by the host runtime itself, so downgrading these does not lose a single host failure; it stops `error`-level from degrading into "some plugin returned an `Err`", which is what made the level unusable as an alert signal
- **How it stayed wrong for so long**: the contract lock (`engine_limits::test_component_guest_self_reported_failure_no_host_error`) only ever ran against the hand-written wit-bindgen fixture, which returns `Err(String)` directly and never goes through this macro. The SDK path had never been put in front of that assertion. Consolidating the fixtures onto the SDK binding is what finally exposed it
- **Blast radius**: SDK behaviour change, so all four wasm application artifacts were rebuilt (`pnpm run build`, wasmHash re-injected) and the SDK package needs a re-publish. No WIT change, no ABI number move, no host code change
- **Operational note**: anyone alerting on `error`-level plugin logs will stop seeing guest-reported failures there. They remain in the log at `warn` with the same message, and host-side faults are unaffected
- **Verified**: SDK crate 158 green + `wasm32-wasip3` release build clean; host `cargo test` lib 1057 green, all integration targets green

#### Biometric credential handling moves entirely into the auth centre — public-key custody and signature verification leave the host (B-downsink, desktop ABI v33 → v34; **breaking: devices with a bound biometric credential must re-bind**; mobile WIT/ABI unchanged)

- **Why**: the biometric **orchestration** (challenge issue / single-use / expiry, pairing checks, HTTP endpoints) already lived in the auth centre (`terminal-session` plugin); only two host pieces remained — public-key custody (`biometric:<fp>` rows in `plugin_secrets`) and P-256 signature verification. That is the same line as v33's JWT move (ADR 0033 D1). The P-256 public key is **public material** (the private key never leaves mobile secure hardware, ADR 0002), so custody location changes no exposure; the verification execution point moves from the host engine into the centre's WASM
- **Host side**: `host-auth` **retires 3 primitives** `biometric-credential-bound` / `biometric-verify-signature` / `biometric-credential-bind`; `utils/auth/biometric.rs` (challenge manager + verification) and the `biometric_challenges` field in `system/app_context.rs` are **deleted wholesale**; stale `biometric:*` rows in host `plugin_secrets` are purged idempotently (same treatment as v33 `jwt.key`; never touches the keyring)
- **Centre side**: biometric public keys now live in a new plugin-private table `auth_biometric_keys` (`biometric_key_get/set/delete`); verification runs in WASM via p256 (`auth_http/biometric.rs::verify_biometric_signature`, the p256 crate verified to compile on wasm32-wasip3); the challenge gate queries the private DB, bind/unbind writes the private DB (decoupled from pairing records)
- **fail-visible ②**: old v33 artifacts still importing those 3 functions get a **named "rebuild with v34 SDK" error at instantiation** — not a trap, not silent degradation
- **Migration, stated plainly**: host `biometric:*` rows are purged, so devices with a bound biometric credential must **re-bind** once; pairing records and pairing-code / QR / JWT auth are unaffected. The mobile wire flow (`/api/auth/biometric-*` challenge-response) is **byte-identical** — **zero mobile changes**; host (ABI 34) and the rebuilt centre artifact **must ship together**

#### The auth centre now owns the entry signing key, and the host has no device-token crypto left (ADR 0033, desktop ABI v32 → v33; **breaking: every already-paired device must re-pair**; mobile WIT/ABI unchanged)

- **What the architecture review found**: `plugin_secrets` held **two different keys under the same name** — one owned by `host` for the host's `JwtService`, one generated by `com.bedcode.terminal-session` inside the guest — and the plugin's copy was **dead**: production issuance went back through the host's `device-token-issue` primitive, so the plugin's complete HS256 implementation had **zero production call sites**, while the WIT comment claimed "the plugin's key domain differs from the host's, so it cannot and should not verify". The isolation claim was true; "the key never leaves the host" was not — the guest held a plaintext copy. The wrong part is now written down as a **failed assumption**, not quietly edited away
- **Why the centre is allowed to hold it**: `HS256` is **symmetric**, so a verifier must hold the signer's secret. The centre could already mint an entry credential for *any* device through `device-token-issue` and have `enforce_connection_policy` act on it — the difference between "the centre can issue" and "the centre holds the key" is one auditable API call versus raw key material in memory. Handing over the key therefore **grants no new authority**; it makes the implementation match the authorisation fact that already existed. The argument's boundary is written down too: it holds *because the centre is trusted*, and replacing the centre (which ADR 0031 already allows for) replaces the trust anchor
- **What changed on the host**: `utils/auth/jwt.rs` (`JwtService`) and `utils/auth/host_secrets.rs` are **deleted outright** — the latter turned out to have no production consumer at all (biometric public keys live in the *plugin-owned* secret store, so the host-owned store only ever served JWT), so it went with the code that used it. `host-auth` **retires `device-token-issue` / `device-token-verify`**. The four host verification sites (HTTP `/api` middleware, endpoint-level gate, protocol gateway, WS plugin endpoint) now ask the centre **once** instead of "host verifies, then ask the centre", so the failure surface is one call. The dead `('host','jwt.key')` row is removed by an idempotent migration that touches exactly that triple and leaves `biometric:<fp>` and plugin-owned rows alone
- **The host must not quietly read that fact back**: the gate's success value changed from `()` to an `AuthenticatedIdentity` of **exactly three fields** (`device_id` / `device_name` / `fingerprint`, pinned by a lock), and a centre that admits a token without a usable identity is treated as a centre fault (`deny_kind=unavailable`) rather than answered from a local credential table — that would be exactly the "host-side lookup" red line
- **Key rotation, in the same batch**: rotation is what stops a guest-side leak from becoming an *unrecoverable* incident. The keyring keeps at most two generations (current + previous), the previous one still verifies for a grace window of the longest token TTL (7 days), and rotation **does not revoke existing tokens** (revocation belongs to the revocation domain). It is triggered manually from the device centre (plugin command `session.auth.rotate-key`) or composably by another plugin (`auth-grant` / `jwt` / `rotate-key`)
- **`kid` is a diagnostic label, not an authorisation gate**: it is an **optional** claim declared last, so a token without it is byte-for-byte identical to a pre-migration token (pinned by a frozen vector). Under symmetric crypto the real gate is "can the signature be verified with a key in the ring" — a token from a pruned generation already fails there, and a party holding an in-ring key can write any `kid` they like. Treating `kid` as a gate would be both redundant and misleading about where the security decision lives
- **A corrupt keyring fails loudly instead of regenerating**: silently writing a new key would invalidate every paired device while the system looked perfectly healthy, and `activate()` refuses to come up rather than degrade to a per-process random key (which would look paired but die on every restart)
- **Fail-visible, all three forms**: a stale v32 artifact fails at **instantiation time** with a message naming the missing import and "rebuild with the v33 SDK" (not a trap, not a silent fallback); the retired function names are gone from the build chain's permission mapping so a stale entry **throws on load**; and `host_has_no_entry_token_crypto` fails the build if `JwtService` / `verify_token_with_expiry` / `generate_device_token` / `verify_device_token` / `JwtClaims` reappear on a production path
- **Migration, stated plainly**: the signing key changed hands, so **every already-paired device must re-pair** (one-time, about 30 s each) — the same call already made when v24 retired the `pairings` / `connection_history` / `session_configs` tables. The mobile client sees a "credential invalid" business code rather than a network error and treats the token as an **opaque string**, so it needs no code change. The host and the rebuilt centre artifact **must ship in one batch**: a host on v33 with a v32 centre artifact means every authentication is rejected
- **Performance: not the reason, and the cost went up slightly — measured, not estimated**: measured before the change, the centre round trip was 95.7–113.5 µs/op and the host's native verification 5.96–7.09 µs/op (~6% of the hot path), for a 101.7–120.6 µs/op total. Re-running the probe afterwards (N=1000, three runs) gives **130.6 / 135.1 / 135.0 µs/op** — so the total did **not** stay flat, it rose by roughly 12–27%. That is the expected price of the move rather than a surprise: HS256 verification now runs inside WASM (~10–20 µs) instead of natively (~6 µs), and ADR 0033 §4 predicted exactly that before the change was made. The decision's rationale is unaffected — the round trip, not the crypto, is ~94% of the cost, throughput is still ~7.4k req/s against a real load of tens per second, and the 7-day token TTL means this path is not per-frame. D1 was decided purely on the trust model; the number is recorded because a "costs nothing" claim that was never measured is exactly the kind that misleads later readers

#### The auth centre registers itself, and "no centre" now means "denied" instead of "let everyone in" (ADR 0031, desktop ABI v31 → v32; mobile WIT/ABI unchanged)

- **What the incident was**: on 2026-09-29 the desktop rejected every JWT-carrying request and WS connection (`auth-policy not provided by this plugin` → HTTP 401 / WS close 4001) while the mobile client kept self-healing without backoff — 616 rejections and 616 toasts in 98 seconds. The host was not broken; it was **picking the wrong auth centre**: the SDK makes every built plugin *unconditionally export* `auth-policy` (a default-deny implementation), and the host then took "the first candidate by id order" as the centre — which was `com.bedcode.agent-hub`, the only one sorting first and not implementing real policy
- **"Who is the auth centre" is now a registered fact, not a guess**: a centre plugin calls `host-auth.auth-center-register(methods)` in `activate()`; the host keeps a **single-slot registry** (`wasm_core/host_api/auth_center.rs`) and rejects a second registrant *by name*, deactivation unregisters, and the host reclaims on plugin stop/uninstall. The "capability probing + first-by-sort" path and the second discovery mechanism (the retired `SESSION_MARKER_API` api-registry anchor) are **deleted**, not deprecated — a regression lock (`retired_auth_center_discovery_is_not_reintroduced`) fails the build if either comes back
- **fail-closed replaces both fail-open fallbacks**: "no centre → let it through" and "centre call failed → let it through" are gone. No centre registered, centre call failure, and centre rejection are now three **distinguishable** denials with a structured `deny_kind` (`no_center` / `unavailable` / `policy`) and a readable reason, because they are three different repair paths. The cost is deliberate: with the centre plugin inactive, every authenticated surface on that host is unavailable — an authentication surface that fails open is an unauthenticated host
- **A stale centre plugin can no longer fail silently**: the boot sequence checks right after activating an L2 component that a centre is actually registered, and logs an `error` naming the plugin and the fix ("rebuild with the current SDK and call `auth-center-register` in `activate`"); the instantiation-time hint also gained the reverse case (a v32 artifact on an older host → "upgrade BedCode", not "rebuild the artifact")
- **Composable authentication**: `auth-methods-list` / `auth-method-invoke` let another plugin reuse an authentication method the centre already implements (pairing code / QR / biometric / JWT) without copying it. The host only checks that the requested method is in the registered list and then forwards the call **without parsing it** to the centre's `auth-grant` API; a business rejection from the centre is passed through unchanged
- **Mobile side, same batch (no protocol or ABI move)**: the WS client now keeps the **close code** (`ServerClosed { code, reason }`; 1006 when absent), and `4001` / `4003` are treated as **fatal** — no self-heal retry, one single "needs re-pairing" toast, because retrying against a host that is denying on purpose can only produce a log storm. Backoff additionally gets a **hard 1s floor** (clamped inside `calculate_delay`, not just in config) and a **same-cause circuit breaker** (5 consecutive identical failures give up; a changed cause resets it) as defence in depth
- **Migration**: the desktop host and the rebuilt centre artifact ship in one batch by construction here (all plugin artifacts are built from source in this repo); the other three wasm applications are not centres, and their older artifacts still load under an ABI 32 host

#### Plugin classification gets three explicit layers, and the "who loads first" question stops being implicit (desktop host + plugin SDK; **no WIT/ABI move — manifest-level only**)

- **What exists today is not "no classification" but a classification that cannot say what we need**: `PluginKind` had two values (`Application` / `System`), and `System` is defined as "provides `host-*` capabilities to the registry" — it is the *proxy identity* for a basic service, yet **no plugin uses it** (`ROUTABLE_CAPABILITIES` holds a single entry, `host-storage`). Two things did not fit: the auth centre is a *decision dependency of the host gateway* (the host actively calls it — the only reverse dependency in the repo, and neither "provides capabilities" nor "product feature" describes it), and "use it and throw it away" (a worker) has no expression at all, because `CallModel::EventLoop` means a **resident** owner task — the exact opposite of ephemeral
- **Three roles, load order `L1 → L2 → L3`**: `basic-service` (L1, engine-domain component, activates first and registers its `host-*` exports as capability providers) → `internal-business` (L2, the host's decision dependency) → `business-app` (L3, the business surface, **the default**). The boot sequence's single "system batch" became two explicit batches (`activate_role_driven_components`); the persisted-state batch is L3 and now filters to L3 only. Within a batch, plugins activate in id order — no implicit priority rules. Legacy spellings `system` / `application` still parse (serde aliases) so existing artifacts need no migration, while serialisation always writes the new spelling; an illegal `type` value is rejected **both** at build time (`manifest-validate.js`, points at the legal set) and at load time (serde) rather than silently falling back to L3
- **The host knows predicates, not role names**: boot order is read from the SDK constant `PluginKind::ROLE_DRIVEN_LOAD_ORDER`, and every decision site uses `is_role_driven()` / `provides_host_capabilities()` / `is_business_app()`. `PluginKind::BasicService` / `InternalBusiness` / `BusinessApp` do not appear in host source at all — a new role therefore needs no host change, and classification cannot decay into "the host branches on a role name to make business decisions" (locked by `host_switches_on_role_predicates_not_role_values`)
- **L1/L2 are role-driven: their enable state is not user state** — they are excluded from the persisted activation map, so "this component is on" is a property of its role, not of a toggle. Single failure still does not block the rest: an L2 that fails to activate leaves L3 running, with the failure visible as an `error` log naming the role plus an `Error` state in the plugin list
- **`lifecycle: ephemeral` (business worker) is registered as a type and nothing more**: its reason for existing is *memory lifetime*, not business layering — wasm linear memory can only grow, and the host's per-instance ceiling is never released, so a resident instance that processes a large input climbs monotonically into the ceiling and traps, with no self-healing without a process restart. The one-shot instance mechanism and scheduler are not built, so declaring `ephemeral` is **rejected on both sides** (build chain and host load) with a message naming what is missing (ADR 0032 §6) — silently treating it as resident would be the exact opposite of why the type exists
- **The L2 red lines are code, not prose**: `internal_business_host_dependency_stays_gated` pins every host file that may touch the L2 bridge surface to an explicit allowlist (gateway / WS auth middleware = security gate; `session_gateway` = zero-parse forwarding; `host-auth` composable-grant primitives = zero-parse forwarding plus single-centre arbitration), and the reverse self-check fails when an allowlist entry stops matching, so the list cannot rot into silently admitting new consumers. `l2_gate_returns_decision_only` pins the gate's signature to `Result<(), String>`: the moment the host can parse a product payload out of an L2 reply, the lock goes red
- **The first real L2 is `com.bedcode.terminal-session`, and both halves land together** (ADR 0031): the static `"type": "internal-business"` declaration decides load order, `auth-center-register` performs dynamic readiness and uniqueness arbitration, and shipping one half alone would leave the two-stage judgement inconsistent. **User-visible consequence of that role**: the auth centre's enable state is now role-driven — it is excluded from the persisted activation map, so deactivating it in the plugin manager lasts for the session only and it returns at next launch (the same direction as fail-closed)

#### Agent Hub usage dashboard rebuilt — session list de-duplicated, multi-dimensional charts (desktop, wasm app `com.bedcode.agent-hub`; **no WIT/ABI move, host untouched**)
- **The duplicate session list is gone**: the stats tab and the log tab both rendered the same `usage_session` rows, with *opposite cursor semantics* (append-more vs page-replace) and a *shared* filter set — so loading more in stats and then paging logs produced duplicate rows, and the logs table could show 45 rows labelled "page 1". Session-level detail now lives **only in the log tab**; the dashboard answers aggregate questions only. `statSessions/statTotal/statLoaded/loadMoreSessions/setListFilter` are deleted (locked by a test asserting the API surface and that mount issues exactly one `list-usage-sessions` call)
- **New aggregate parameters** (guest `usage::get_stats`, all verified against the real 160-session / 8-project / 2-CLI database): a **time window** (`days`, 0 = all-time, clamped server-side to `1..=3650` with out-of-range falling back to all-time rather than silently truncating); `total` gains active days, distinct project/model counts and the first/last timestamp; every grouping row gains the three cache/reasoning buckets plus `last_at`; **`byHour` is new** — a 7×24 rhythm matrix in host-local time
- **Token total is defined once and excludes reasoning**: `input + output + cache_read + cache_write`. Reasoning is a *subset* of output (claude's `thinking_tokens` is inside `output_tokens`), so adding it would inflate the total; it is surfaced as a separate "reasoning (within output)" metric instead, and this is pinned by a test that would go red at 150 instead of 100
- **Charts, hand-rolled in SVG/HTML rather than pulling in a chart library** (bundle +24 KB vs an estimated +500 KB for ECharts): a token/session/cost/duration trend area chart with a **stacked composition mode** (fixed semantic band order — reordering per day would make bands slither and become untrackable), a **7×24 rhythm heatmap**, a **CLI share donut**, and project/model ranking bars. Metric selection is global — one choice drives trend, rankings and the donut
- **A real ranking bug was found and fixed by the tests, not by review**: `ORDER BY tokens_in + tokens_out DESC` in a `GROUP BY` query is resolved by SQLite as the *input column* (an arbitrary row of the group), not the `SUM()` alias — so "Top projects" came back in effectively random order (the 128M-token main project ranked 2nd of 9). Both `byProject` and `byCli` now repeat the aggregate explicitly, with a lock that fails if anyone reverts to the bare-column form
- **Heatmap bucketing is rank-based, not linear**: real usage is extremely skewed (top hour-cell 19.3M vs 0.1M, top day 128M vs 20k), and linear bucketing collapses everything but the peak into the lowest band — exactly losing the "which hours are second-busiest" answer the chart exists to give. The test asserts all four bands stay in use on real data
- **Accessibility is a registered contract, not an afterthought**: 4 categorical chart colours were chosen by exhaustive search under the repo's own contrast math (12 themes: ≥3:1 on card, pairwise ΔE ≥25, ≥25 from semantic colours, ≥20 from palette primary, ≥50° hue separation, same hue across light/dark); the heatmap's low bands are **registered exemptions** (a sequential scale's low end *should* fade, and every cell has a `title` + aria + per-row totals), with a *stricter* check added in exchange — monotone luminance and ≥3:1 for the top band. The trend chart's interaction layer is HTML overlay buttons so keyboard focus and hover share one value path, and the chart is `aria-hidden` with a data-table toggle as the second reading channel
- **Stale-window responses are dropped by sequence number** (same idiom as `AgentHubState.seq`): switching the time window while a scan-triggered reload is in flight would otherwise leave "new pill selected, old window's data" on screen; a test reproduces the race
- Also: the 30-day window is the new default with "all time" one click away, and an empty window says so explicitly (with a jump to all-time) rather than rendering a blank board
- Costs: no WIT/ABI move, no host module touched, no new command; `get-usage-stats` gains an optional argument and returns two new keys. The plugin's `dist/index.js` grows 422 KB → 446 KB (gzip 123 KB)

#### Agent Hub usage stats complete their v1 promise — OpenCode SQLite adapter, Codex skeleton, manual data purge (desktop, wasm app `com.bedcode.agent-hub`; **no WIT/ABI move, host untouched**)
- **OpenCode sessions now reach the dashboard and the log view** (mother spec §2 v1 promise, previously unimplemented — `ADAPTERS` was `["claude","pi"]` while the overview listed four CLIs, so a user with OpenCode installed always saw zero usage data with no explanation). The `session` table is read through the plugin's **existing `host-process` channel** as `sqlite3 -json -readonly` (a new WIT primitive would have needed an ABI bump + dual-end sync, explicitly out of scope): keyset pagination on the session primary key, `message × part` join for the event stream, and — because the on-disk DB is **445 MB / 22 tables** — the big `part.data` blobs are **narrowed in SQL** (`json_extract` + `substr` on `state.output`, every extraction guarded by `json_valid` so one corrupt blob cannot fail a whole page). Verified against the real DB: the largest session (1 329 parts / 15.5 MB raw) round-trips as 7 pages, **1 329 unique rows with no gaps or duplicates, 977 KB total** (94 % of the raw payload never crosses the WATM boundary); all 54 sessions import
- **The four on-disk facts that contradicted the ticket text are handled explicitly**: `model` is a JSON *string* (`{"id":…,"providerID":…}`) so it is parsed guest-side (`json_extract` aborts the whole query on a non-JSON value); timestamps are **epoch ms**, not ISO8601Z, so a separate read path is used; `cost` is `0.0` on **every** row, which means "not reported", not "free" — it lands as NULL so the dashboard shows a blank instead of a misleading `$0.00` (spec §4.5 "store if present, never estimate"); 9 zero-token sessions import normally (no empty-model rows polluting the by-model breakdown)
- **Incremental rescan is a content fingerprint, not mtime**: the WIT has no mtime primitive (`host-fs.stat` returns size/isFile/isDir), and OpenCode runs in WAL mode where the main file only grows at checkpoint — so the watermark is `{db bytes}:{-wal bytes}`, stored in a new `parse_watermark.signature` column added by an idempotent `PRAGMA table_info` migration. Unchanged fingerprint → no `sqlite3` run at all; changed → full re-read upserted on `UNIQUE(adapter, cli_session_id)`, so repeated scans cannot duplicate sessions
- **Failure is visible, not silent**: three distinct machine-readable codes (`sqlite3-missing` / `db-missing` / `query-failed`) reach the stats tab as an informational banner with i18n text and per-source wording (install sqlite3 / run an OpenCode session / check the log). Errors are isolated to the OpenCode slot — the other three adapters are unaffected, and a failed round **keeps the previous session count** instead of blanking the list. Opening an OpenCode session's detail fails loudly rather than returning an empty event stream, which would have collapsed three different causes into one "no records"
- **Codex gets its official-format skeleton** (`~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`; `session_meta` / `turn_context` / `response_item` / `event_msg`; billing from `token_count.info.last_token_usage` with `input_tokens` split back out of the cached portion, model tracked statefully from the last `turn_context`). This is what makes the **sixth card state "installed · not initialized"** a derived fact rather than a special case: scanned + authorized + zero sessions. Unscanned / unauthorized / syncing / failed all resolve to `unknown` and keep the plain "installed" badge — reporting "not initialized" for "I can't see your data" would be a false alarm. Dual-install keeps its warning tone, because that one is actionable
- **Data retention: keep everything, purge on demand** (new `agent-hub.clear-usage-data`): the session aggregates and the parse watermarks are deleted **in one transaction** — deleting only the watermarks would make the next scan skip every file and the sessions would never come back, deleting only the sessions would re-import duplicates. Two-step confirm in place (no dialog), the guard rejects re-entry while a purge is in flight, and on success the dashboard plus both session lists reload so no "empty board, stale list" intermediate state is visible
- Costs: no WIT/ABI move, no host module touched, `plugin.json` gains one command; the four-sample `select`/adapter state migration backfills the two new slots and two new built-in sources into existing plugin state **without dropping user-added custom sources**

#### Agent Hub log sources gain multiple directories per source (desktop, wasm app `com.bedcode.agent-hub`; **no WIT/ABI move, host untouched**)
- **A source is now a name plus any number of directories, not one directory**: every source (built-in ones like `pi` included) can take additional log directories, so e.g. a project-local `.pi/sessions` folder can join `~/.pi/agent/sessions` under the same source instead of being shoehorned into a separate one. The persisted state migrates the legacy single `path` to a `paths` array idempotently on read (built-in and custom entries alike), keeping user-added custom sources intact
- **Directory-level add/remove, with ownership rules**: two new commands `add-usage-source-path` / `remove-usage-source-path`. Paths stay **globally unique across sources** (the same directory under two sources would import the same session files twice, once per adapter name); a built-in source's default path cannot be removed (user-added paths on it can), and removing the last directory of a custom source is rejected in favour of removing the source itself; SQLite sources (`opencode`) remain single-file read-only. All validation (`~/` expansion, absolute-path and scan-script-safety checks) is shared with `add-usage-source` via pure helpers covered by unit tests
- **Scan enumerates every directory**: `scan_sections` now yields one section per (source, directory) with the *same* section name per source, so `parse_listing` aggregates all its directories under the adapter name and the watermark/adapter keys keep working unchanged; built-in default paths still derive from the live home directory, and multiple directories of one source produce a single combined scan count
- **The sources panel renders the directory list**: each source shows its directories as indented rows (built-in default marked and not removable, user-added ones removable per-row) with a per-source **Add directory** button that opens the same fs:pick picker flow used for new sources (no name input — the source is fixed); the whole-source add flow is relabelled "Add log source" to distinguish the two
- Costs: no WIT/ABI move, no host module touched, no new permission; two new plugin commands; the plugin's `dist/index.js` grows to 457 KB (gzip 125 KB)

#### The "add log source" form gets a name dropdown, and a repeated directory is caught while it is picked (desktop, wasm app `com.bedcode.agent-hub`; **no WIT/ABI move, host untouched**)
- **One form, two actions — the name decides**: the source name is now a **dropdown of the already-added source names plus a free-text field**. Picking an existing name (`pi`) attaches the chosen directory to that source; a name that is not on the list creates a new source. The routing reads only *whether the final name already exists*, so typing `pi` by hand does the same thing as picking it from the dropdown — there is no second mode to keep straight. SQLite sources (`opencode`) are deliberately absent from the dropdown: they are single read-only library files and the guest would reject the directory anyway
- **A repeated directory is refused where it is picked, not on submit**: picking a directory that is already registered under *any* source immediately shows an inline "already added — duplicate, cannot add" message tied to the path field with `aria-describedby`, and the confirm button stays disabled, so the user is not walked through a submit that was doomed. The guest remains the final arbiter (`error.pathTaken`), this is the earlier feedback — the same rule the per-source add flow already relied on
- Costs: no WIT/ABI move, no host module touched, no new plugin command (both actions reuse `add-usage-source` / `add-usage-source-path`); 3 new i18n keys (zh-CN + en); the dev-shell mock gains the two directory-level commands it was missing and its duplicate check now actually fires (it compared a `path` field the state no longer had)

### Features

#### Agent Hub requests file access in batches — one dialog per business operation, not one per file (desktop host + wasm app `com.bedcode.agent-hub`; **no WIT/ABI move**)
- **The problem**: business operations that touch several files each raised their own dialog — or, worse, the grant never stuck. Host-process outputs (`~/.bedcode/agent-hub/runs/*.log`) get a **new filename per run**, so an exact-scope "remember" recorded that run's file and the *next* run asked again; the usage scan read Claude session files under `~/.claude/projects/` that no grant covered at all (silent read failure since the global `.claude/` whitelist retired); opening the providers page raised three dialogs (settings.json plus two bridge-file existence checks); one provider apply to Claude could raise up to five
- **Host**: `~/.bedcode/agent-hub/runs` joins agent-hub's first-party no-dialog list (criterion ②: plugin-owned transient output that an exact grant cannot express — a per-run dialog would repeat every run). The scope stays inside `runs/`, no user content; the audit projection and `auth_policy` overview test cover it
- **Guest**: the activate-time batch adds `~/.claude/projects` (the usage scan's session source of truth); `scan-usage` now batch-requests the **actual source roots of this scan** (one dialog listing all, already-granted paths skipped silently) instead of gating on the fixed activate list — which also un-dead-ends Claude/custom sources the old gate could never reach; providers state assembly (`build_state`) and Claude-target applies batch the three Claude paths (settings + two bridges) up front
- Costs: no WIT/ABI move, no permissions changed; guest-only logic (`scan_auth_roots` dedup helper, `claude_auth_paths`) with unit tests; the frontend changes are doc comments only

#### Per-app authorization policy and grant management — three tiers over file and network, with a management UI (desktop host; **no WIT/ABI move**)
- **The problem**: the host had per-app file grants (`fs_granted_paths`, a flat prefix list that granted read *and* write together) but **no network grants at all** — a plugin with `network:http` could reach any origin silently. The user's ask had three parts (per-app records, a policy per resource, and a UI to review/revoke), and only the first was roughly in place
- **A three-tier policy per (app × resource)**, answering one question: *when a target has no record, do we ask?* — **Always Ask / Default / Always Allow**. It decides **only** whether to ask; it does not decide whether a permission bit is in effect, and it relaxes no hard gate (manifest declaration, SSRF + public→private redirect blocking, canonicalization-fails-deny, quota, owner isolation all sit outside or ahead of it). "Ignore permissions" was explicitly rejected as wording: the security UI must not over-promise. Read at decision time, never cached — a cached verdict would make "I switched to Always Ask" a lie
- **Authorization records become the source of truth** (two new tables, `plugin_auth_policies` / `plugin_auth_records`, idempotent migration + index): file targets are a canonical path prefix **plus the effective operation set**, so granting *read* no longer implies *write*; the old flat list degrades to a read-only fallback for subtrees nobody has explicitly managed (existing users see no change). Network targets are a normalized origin (`scheme://host:port`, default ports explicit, lowercased) — **query and fragment never enter a stored target** (credential red line), with an optional path prefix matched on segment boundaries so `/v1` cannot match `/v1abc`
- **Outbound `host-http.fetch` now asks**: an unrecorded origin raises one dialog (new event + new command, both bound to the host-side credential — a plugin-facing credential cannot answer it), and requests to the same origin in flight are **merged into one dialog** with a 2 s reuse window, because agent-hub's single refresh issues dozens of requests to the same host and per-request dialogs would make the feature unusable in practice. `deny_always` writes a hard-deny record, and hard-deny records are honoured under **every** tier — "Always Ask" skips allow records, never a denial the user already gave
- **Grant bookkeeping is a fact, not a promise**: no-prompt auto-allow under Always Allow still records the target with `source='always_allow'` and is shown as **"unconfirmed"** in the UI, visually distinct from user-confirmed grants. Under Always Ask the user's "allow" is *not* recorded — the tier never reads records, so a record nobody reads would show a false "user granted this" in the management UI. Records cap at 500 per (app, resource) with the drop counted in core-monitor
- **A management UI in Settings → App Authorization** (secondary entry, not a top-level menu item — permissions are not a product surface), listing every installed wasm app sorted **by risk** (Always Allow on either resource first). Each row expands to the three-tier control per resource, the file-directory and network-origin lists with per-record revoke, and the plugin detail page carries the matching four sections (granted by user / auto-allowed-unconfirmed / first-party built-in / hard denied). "Cancel authorization" = delete the allow record + write a deny record; the deny is itself removable, so both intentions have an exit. The existing "Permissions" block is renamed **"Requested permissions"** — a static manifest declaration and a runtime ledger are orthogonal facts, and merging them would imply a mapping that does not exist
- **The first-party no-prompt directory list is now visible and revocable** (`~/.agents`, `~/.claude/skills`, project-level `.claude`/`.codex`/`.pi`/`.opencode`): those entries sit above the policy tier on purpose (otherwise "Always Ask" would turn one skill sync into N clicks), which is exactly why the spec requires them to be shown in both pages. Revoking one writes a deny record, which the pipeline intercepts before the first-party layer; removing that deny restores the exemption. Segment-form entries stay read-only — the project root is chosen per session, so there is no reusable target to record
- **Lifecycle**: deactivation **keeps** records and policy (stopping and restarting an app must not mean re-answering every dialog), uninstall **clears** both (a reinstall is a fresh grant, in line with ADR 0020's content-hash pinning). Both are locked by a test because they look like the same operation and are easy to "harmonize"
- Costs: no WIT/ABI move (the `fetch` import signature and return shape are untouched — this is a new *admission condition* inside the host, registered in the WIT's no-bump section alongside the v22 topic and the `fs:pick` precedents), no mobile change (ADR 0018: mobile is a self-contained app whose SAF grants are per-tree-URI), no change to any wasm app

#### Native system file picker becomes a declared, gated capability — `fs:pick` + post-selection authorization (desktop host; **no WIT/ABI move, manifest-level gate**)
- The native picker itself already existed (`host-platform.pick-files` / `pick-folder` / `pick-folders` over `tauri-plugin-dialog` — Windows IFileDialog, Linux xdg-desktop-portal) but was **ungated**: any plugin could raise it and receive absolute paths for free, and nothing examined what happened to the selection afterwards. The two halves are now split, matching what the user actually asked for
- **Admission gate — `fs:pick`, a separate manifest permission bit**: an undeclared plugin gets a fail-visible `Err` naming the missing bit **before the dialog opens** (not a bare "permission denied", and not after the user has already browsed their disk). It is deliberately *not* folded into `fs:read` / `fs:write` — "may raise a picker" and "may read any path" are different powers, and merging them would hand a plugin that only needs to attach one file a full-disk read. Vocabulary 32 → 33; the SDK stays the single source of truth, both generated copies (packaging CLI + host frontend) are regenerated, and the drift lock plus `generated_vocabulary_know` cover the new bit. `manifest-gen` infers `fs:pick` from `platform_pick_*` call sites, so the two real consumers (`file-transfer`, `agent-hub`) declare it automatically
- **Result gate — the selection is authorized before the plugin sees it**: after the dialog returns, every picked path runs through the existing `fs_auth` three-layer check. Paths already under a **granted directory** prefix (or a first-party declared dir) pass **silently**; only the ungranted remainder raises one dialog, merged across all picked paths. Denied / timed out / no dialog channel → `Err` and **not one path is returned** — an empty array would read as "the user selected nothing" and silently drop data (fail-visible)
- **"Remember" is recorded at directory granularity for picker-originated grants** (file → containing folder, folder → itself): the user's "yes" was about a folder, and per-file bookkeeping would re-ask for every additional file in the same transfer. The dialog now says so ("remembering grants the containing folder"), and a repeated grant no longer stacks duplicate entries. `respond` also no longer holds the pending-queue lock across the storage `await` (the request is taken out first)
- Cancelling the picker stays a cancel — no authorization round-trip is raised. Locks: the gate **order** is pinned by a test asserting the error names the permission rather than the headless limitation; "already granted ⇒ no dialog" is pinned in the headless checker (a dialog would have been impossible there, so passing *is* the proof); the directory-grant behaviour is pinned through the real `respond` path. Both mutants (directory-grant → file-grant, drop the granted-prefix skip) turn the suite red
- **No ABI bump**, following the v22 bus-topic precedent: the three `pick-*` imports and their signatures are unchanged, and what changed is a manifest-level admission condition enforced at runtime exactly like `fs:read` is. Pre-existing artifacts calling `pick-*` without the bit fail at the call site with a message naming it — a manifest edit, not a wasm rebuild. Recorded in the WIT's "semantic changes without a version bump" section
- **Mobile deliberately does not follow** (ADR 0018 dual-end deviation, registered in the WIT): its SAF picker already has the system grant per tree URI, so "selection = grant" holds there without a bit. `reveal-in-dir` stays ungated — it hands the plugin nothing it did not already have

#### Plugin call model upgrade — event-loop owner (grey-runnable) + on-demand async evaluation retired (desktop; **defaults unchanged, no ABI move**)
- Host-side plugin calls are collapsed from "one instance lock per call + `spawn_blocking` + `block_on_async`" into an **assembly entry**: `WasmInstanceEntry { meta, call_model, slot }` is the **only** host of the `Store`, and every call goes through `PluginHost::call_guest` (async) / `call_guest_blocking` (sync bridge). The `mutex` arm **keeps the previous implementation verbatim** (return values, error strings and trap recovery stay byte-for-byte equivalent for existing plugins); the `event-loop` arm runs one resident `run_concurrent` owner loop per instance (`start_call_concurrent` + oneshot settlement + `select! { biased }` preserving "start order = enqueue order")
- Grey switch `CoreConfig.call_model` (`mutex` (default, rollback window) / `event-loop`, overridable by name in `wasm-core.json`, invalid values fail at load); per-instance snapshot, so **reload switches it**; **default unchanged**, rollback window preserved (flipping the default awaits on-device verification)
- Shutdown semantics (fail-visible): deactivate / uninstall / reload **stop the owner and drop the store before reclaiming resources**; for `event-loop` instances the guest `on_shutdown` / `deactivate` exports are explicitly skipped and counted (`owner_cleanup_skipped` + warn, never silent); trap = whole instance unusable (byte-for-byte the previous semantics) with every waiting request failing explicitly; capability forwarding gained a 5 s timeout so cyclic dependencies degrade from "permanent deadlock" to "bounded failure"
- **On-demand async evaluation: retired** (ADR 0029 / `.scratch/2026-09-26-plugin-concurrency-model/`) — WIT-level `async func` is unusable on the pinned toolchain (async-lifted exports abort on entry); switching to host-side async (`func_wrap_async`) was then measured to have **no payoff**: while an async import is pending, a second call on the same instance makes **zero progress** (instance-level gate, independent of whether the import is async), and the owner closure **is not scheduled at all** during that window. So "a slow call blocks the whole plugin" cannot be fixed by async-ification; both facts are pinned as boundary locks (`runtime/tests/p3_async_host_import.rs`, turning red means re-evaluate). The remaining viable direction is a **non-waiting primitive** (return a handle immediately + completion events, like `host-process.run` / streaming `fetch`), pending a separate project

#### Mobile WS surface re-anchored on plugin endpoints — HTTP control plane, session-control event channel, terminal stream rewrite, WS frame encryption retired (mobile; desktop wasm app adds a minimal event broadcast)
- The mobile WS face is realigned to the desktop plugin endpoints (old `/ws/event` and `/ws/terminal/session/{id}` now 404). The **session-control** endpoint (`/ws/plugin/com.bedcode.terminal-session/session-control`) carries a minimal auth frame `{"type":"auth","token":"<jwt>"}` plus `{"type":"event",…}` event frames, restoring the `ws_sync_*` client event surface via the plugin broadcast; events are **never replayed** — after (re)connect the frontend reconciles over HTTP (`ws_event_channel_ready` → `loadActiveSessions` + active-queue pull). The **terminal** endpoint (`/ws/plugin/.../terminal`) is rewritten to the plugin protocol (fresh-subscribe replay + raw bytes + local byte count + `ring_resync` re-anchor + `session_stopped`); TB v3 parsing retired
- Session control / session & config loading / terminal input / plugin API (`session.list`, `terminal.sendInput`) move to HTTP (`/api/sessions/*`, `/api/configs`); the legacy `Message` envelope shrinks to 5 variants kept only for the WS legacy-auth integration scenario; the task API alias moves from `com.bedcode.auto-task` to `com.bedcode.terminal-session`
- **WS frame-level link encryption is retired** (desktop `TrafficChannel::WsPlugin => false`): the `ws-terminal` / `ws-event` settings switches, the `useLinkEncryption` WS fields, `install_event_crypto` and the `WsClient` crypto pipe are deleted; HTTP envelope encryption is kept unchanged (switch / strict / pinning semantics intact)
- Convergence: session-config push and device up/down events are **not** pushed by the plugin (mobile refreshes on demand / reconciles); the session status literal is unified to the desktop wire value `waitingInput` (was drifted `waiting_input`) and locked by tests
- Structural locks added for every retired surface (session-control no-envelope, no WS crypto residue in production, no `waiting_input` in session-status comparators), mutation-tested

#### Terminal output backpressure returns as delivery-time acking + two-level hysteresis (desktop, plugin-side; host untouched)
- The pre-downsink mechanism (host per-subscriber window with `acked_offset`, dual water marks, park wait, 30 s zombie reclaim) is restored **inside the `com.bedcode.terminal-session` app**, because the host PTY ring knows nothing about consumers: `session.output.ack` (`{sessionId, offset}`) advances a monotonic per-session watermark, and `session.output.pull` throttles once the unacked window reaches the high mark (128 KiB), releasing only below the low mark (64 KiB) — the migration-precedent values, including the `ack ≤ low < high` invariant asserted at compile time
- The frontend acks at **delivery into the write pipeline** (not "render complete"), throttled at 64 KiB accumulated or 250 ms idle, exactly like the pre-migration `useTerminalOutputStreamChannel`; a throttled response makes the pull loop keep its cursor, skip the write, and retry after a 200 ms backoff (= the old `park_poll_ms`), with `truncated`/resync re-anchoring both cursor and watermark
- Parked more than 30 s logs one warning (the old zombie reclaim; there is no connection to drop in the pull model) and keeps pulling — no silent stall
- New read-only diagnostic `session.output.watermarks` (`{sessionId?}` → pushed/acked/unacked/parked + park/truncated counters, mirroring the old `SubscriberStats`); the frontend fetches one snapshot on park exit and logs it, so "did backpressure actually engage" is observable without digging engine logs. Counters are clock-free by design (wasm32 guests have no clock; the frontend times the park duration)
- **Pull cadence aligned with the old engine** (spec F5): fast/idle 100/500 ms → 50/250 ms and a 4 × 16 KiB = 64 KiB per-tick budget (= the old `FETCH_BUDGET`), i.e. half the output latency at unchanged throughput ceiling; pacing decisions moved into a pure, unit-tested `terminalPullPolicy` module, and a parked session now always stays on the fast tick (previously a park during the idle tier stayed on the slow one)
- **No host change at all** — no WIT/ABI move; the real push engine event (millisecond wakeup) remains the documented follow-up (P2)

#### PTY output-available notification — rate-limited host wakeup (desktop; **no WIT/ABI move, one bus topic added**)
- The pull model left one latency hole: a session idle on the slow cadence (250 ms) noticed the first fresh byte only on the next poll. The host now publishes a **rate-limited hint** on the owner-private bus topic `<owner>::pty:output` whenever the ring gains bytes (≥50 ms per handle, payload `{ ptyId }`, no bytes) — the pre-downsink `OutputNotifySink` write-side decorator wrapped around `PtyRingSink`, so the `pty/` engine keeps **zero** bus dependencies
- **The data plane is unchanged**: bytes are still pulled by cursor (`ring-fetch`), `truncated` resync semantics stay byte-for-byte, and the hint is **droppable by design** (no subscriber / full queue / plugin deactivated / rate-limit merge — never replayed). Correctness therefore still rests entirely on the frontend cadence + resync; the event only buys latency (after an idle period: slow tick 250 ms → ~0)
- The plugin consumes it as an accelerator only: `terminal-session` subscribes during `activate` (a failure **downgrades** to pure polling and never blocks activation — the opposite of the `pty:exit` strong gate) and forwards `ptyId → sessionId` as the frontend event `session:output-available`; a hit pulls one round immediately, a foreign session id or a dirty payload is ignored, unmount releases the subscription. The SDK exposes the constant as `PTY_OUTPUT` beside `PTY_EXIT`
- Locks: a drift lock pins the host event name to the SDK constant (`output_event_name_matches_sdk_subscription_helper`) — one side renaming alone silently degrades to "subscribed but never received"; the rate limiting is verified against a real PTY burst (20+ pushes within a millisecond yield far fewer notifications, i.e. the decorator is active and the hint did not degenerate into per-chunk push), and the pure rate-limit decision function is unit-tested (first always passes / exactly-at-interval passes / inside-window dropped / clock rollback treated as not yet due)

#### Peer transfer orchestration sinks to the plugin — host `peer_engine_*` collapse into handle tables + engine event bridge (desktop, **v30 + v31**)

### Bug Fixes

#### The fuel watchdog now covers the three optional-export callbacks — no more cumulative drain → spurious plugin reload (desktop host; **no WIT/ABI move**)
- **The mechanism**: the per-call fuel budget is refilled inside `LoadedWasmPlugin::exports()`, but `on_message_binary` (v11), `on_ws_frame` (v14, both the client and endpoint-client branches) and `on_task_event` (v20) hold their probed `TypedFunc` handles and call `call_async` **directly**, bypassing `exports()`. Those three entry points therefore inherited no refill, so their fuel drained **cumulatively across calls** instead of resetting per call — contradicting the contract written into `config.rs` (`FUEL_PER_CALL`: "every export call resets the fuel; the budget constrains only the guest work inside a single call"). Once the remaining budget hit zero the guest trapped with `all fuel consumed`, the Store was poisoned, and `schedule_plugin_reload_after_trap` reloaded the plugin. The plugins whose dominant call path *is* these callbacks were the exposed ones: file-transfer (WebSocket frames) and any plugin receiving a steady stream of host task events. The same gap also under-counted `fuel_consumed_total` in core-monitor, since `record_fuel_consumed` only runs at refill time.
- **Scope**: the default `mutex` call model. The `event-loop` model routes every op through `start_op` → `refill_fuel`, so it was never affected — which is why the existing `test_component_fuel_watchdog` (which only exercises `invoke_command`, an `exports()` path) stayed green.
- **Fix**: each of the three methods now refills its own fuel at the top, with the reason recorded at the call site. `on_ws_frame` refills before the match rather than inside each arm, so the consumption accounting keeps flowing on the degrade path too.
- **Guard**: `test_optional_export_callbacks_refill_fuel` drains the store below a tenth of the budget and asserts each callback restores it — three consecutive rounds (kills a "refill only on the first call" variant), the `events-task` callback on its own fixture, and a negative case asserting a product without the `events-ws` export still returns exactly `Ok(false)` and is not disturbed. Mutation-checked: deleting any one of the three refills, or halving the refill, turns it red; the surviving variant (moving the refill below the no-export early return) is semantically equivalent and is recorded as such rather than papered over.

#### Agent Hub uninstalls of npm-global CLIs actually take effect — login shells now carry the user PATH (desktop, wasm app `com.bedcode.agent-hub`; **no WIT/ABI move, host untouched**)
- **The symptom**: an "uninstall finished" run left the CLI card showing "installed". The persisted process truth (`plugin_storage` `install.last`) held `exitCode: 127` / `npm: 未找到命令` — the script ran via `bash -lc`, and nvm puts its PATH injection behind the interactive guard (`case $- in *i*)`), so a login shell cannot see npm. The command never ran, and the post-run auto re-detect found codex still present
- **The fix**: `exec_script()` now prepends the interactive-shell PATH bootstrap that `detect.rs` already used for probing (`path_bootstrap_unix`, promoted to `pub(crate)`), unix only — Windows `cmd /C` reads the registry PATH and needs nothing. Install and uninstall entry points share it; a regression lock asserts the bootstrap survives into the command line
- **Uninstall failures are no longer silent on the overview card**: when the last run failed for a process reason (not a user cancel), the card surfaces "卸载失败，详情见「安装」页控制台" instead of pretending nothing happened — `failedUninstallFromLast` + watch + i18n key (zh + en)

#### Terminal window chrome — the black strip under the xterm grid is gone, and the header/footer stop fighting the terminal (desktop)
Found by pixel-sampling a real 2560×1440 capture of a `solarizedDark` session window (`#002b36` grid, `#fdfcfa` chrome, ~1.42 device scale) rather than by reading the code
- **Black strip between the display area and the window edge** (~14 CSS px, sampled as pure `#000000`): `xterm.css` hard-codes `.xterm-viewport { background-color:#000 }`, and that layer is `position:absolute; inset:0` *beneath* the render canvas — the row grid only covers `rows × cell height`, so the sub-row remainder at the bottom paints nothing and the layer's black shows through. It stayed invisible while the `default` theme was in use, because `TERMINAL_THEMES.default.background` **is** `#000000`; every non-black theme showed it. The host container now publishes the theme background as `--term-bg` and the override layer paints `var(--term-bg, #000)` — deliberately still **opaque** (unconditional `transparent` reopens the ghosting path closed by ticket `02-viewport-transparency-conditional`); only the colour changes. The selector carries the `.xterm` prefix (0,3,0) so it outranks `xterm.css`'s `.xterm .xterm-viewport` (0,2,0) instead of depending on stylesheet order. Regression guard in `terminalPreview.test.ts`: container and `--term-bg` stay same-sourced, follow a theme switch, and fall back to `default` on an unknown theme key (mutation-checked — dropping the binding turns 3 green into 3 red)
- **Header cwd/command starved to a one-character stub** (real capture: the command rendered as a bare `p`, no ellipsis, half-covered by the Stop button): both spans were `truncate` in the same row, so the shrink budget was split *proportional to content width* — the long cwd consumed it and the short command was left with a sliver too narrow for even an ellipsis. Priority is now explicit: the cwd is the only shrinking item (`min-w-0 flex-1`), the command keeps its width (`shrink-0`, capped at 8rem), so a narrow window shortens the path instead of shredding the command
- **Stop button restyled** off `wb-btn-primary` (a solid near-black block — the highest-contrast object in the bar, stealing attention from the session name/path, and semantically wrong: a destructive action wearing the primary-CTA treatment) to a danger ghost (translucent red outline + red label, solid red on hover, matching the close button's hover contract); the `uppercase` that does nothing for CJK is gone. Note for the next edit here: the translucent outline **must** be spelled `border-[color-mix(in_srgb,var(--color-danger)_35%,transparent)]` — Tailwind 3.4 silently drops an opacity modifier after a `var()` arbitrary value (no error, no rule emitted), which would have left the button borderless
- **Terminal gutter**: content used to sit flush against both window edges while the header/footer were inset by `px-3`; `.xterm` now carries `padding-inline: 0.5rem` with an explicit `box-sizing: border-box`. The padding goes on `.xterm`, **not** on the host container — addon-fit 0.11 only subtracts `.xterm`'s own padding and reads the parent's computed content width, so padding on the parent under-counts columns
- **Status bar is no longer selectable** (a drag inside the terminal painted the selection highlight across `运行中` / `运行时长`); the header keeps selection on purpose, since the path and command there are meant to be copyable. The three 1px toolbar dividers move from `--border` to `--border-strong` — at ≈1.05:1 against `--bg-card` they were invisible, leaving the grouping decorative
- Desktop frontend suite **868 passed**; root `eslint` **0 errors**. The always-visible scrollbar thumb was investigated and deliberately left alone: xterm already derives it from the theme foreground (`opacity(foreground, 0.2/0.4/0.5)`), and the sampled `#1a4049` matches `rgba(#839496, 0.2)` over `#002b36` channel for channel

#### Terminal resize contract fixed — the frontend now sends `requester`, so the PTY size actually follows the grid (desktop)

### Platform & Infrastructure

#### Wasmtime 47 → 48 on mobile — the two-end version lock is restored (mobile; zero code adaptation)
- The 2026-09-18 desktop upgrade deliberately forked the two ends (desktop 48.0.2 / mobile 47.0.3) to de-risk a 47-line EOL; mobile now catches up with `wasmtime = "48"` (lock resolves 48.0.3, MSRV 1.94 → 1.95), closing the ADR 0019 deviation. - **Zero code adaptation** — and the reason differs from desktop, which needed two edits: the desktop host depends on `wasmtime-wasi` (48 collapsed `DirPerms`/`FilePerms` into a two-state `FsPerms`, wasi-filesystem #14010), while the mobile host has **no WASI surface at all** (no `wasmtime-wasi` dependency, no preopens, no wasi imports in any of the three plugins), so the whole wasi half of the 48.0.0 release (socket deny #13936, filesystem perms, wasip2/p3 unification) has no counterpart here. Fuel watchdog semantics, the `ResourceLimiter` ceilings, and the AOT `.cwasm` cache are unchanged in 48
- `cargo check --lib` clean; full mobile `cargo test` green (347 lib + integration targets), including the 29 `wasm_runtime` cases that actually compile and load components (round-trip, fuel trap, limiter denial, AOT cache hit, ABI negotiation, SDK macro artifact load + activate)

Build-chain target (`wasm32-wasip3` vs `wasm32-unknown-unknown`) is explicitly outside the lock
- **Mobile wasip3 is not part of this change**: a probe crate proved the desktop A0-3 wiring shape (CM_ASYNC + `p3::add_to_linker` + sync `Store` + `instantiate_async`) compiles on 48, and no p2 compatibility shim would be needed (existing unknown-unknown components import no wasi). But today's mobile plugins use zero wasi, the win is a build-chain simplification behind a **breaking change to the published `@binblink/bedcode-plugin-sdk-mobile` CLI**, and it would pull `wasmtime-wasi` into the APK. Ticket split B-1..B-4, costed, in `.scratch/2026-09-26-mobile-wasmtime-48-wasip3/spec.md` §4 — pending a decision

#### Cargo build-space governance — the 30+ per-crate `target/` directories collapse into shared ones (desktop + mobile; no ABI move, no behavior change)
- This monorepo has **no root Cargo workspace**: every one of the 30+ `Cargo.toml` files is its own workspace, so `cargo build` wrote artifacts into **each crate's own `target/`**. Because the test fixtures and the wasm apps all depend on the *same* graph (SDK `bedcode-plugin-api` → `wit-bindgen` + proc-macro `bedcode-plugin-api-macros` → serde/anyhow/inventory), that graph was compiled once per crate — measured peak **6.0G across 11 fixture targets (429M–836M each) and 5.8G across 4 wasm-app targets**, ~11.8G of pure duplication. Every test run grew the footprint, because each fixture build created yet another directory
- Fixtures now share `bedcode-desktop/target/fixtures/` (single source of truth: the new `wasm_core/manager/runtime/fixture_target.rs`, `dir()` / `artifact()`, consumed by all 12 fixture builders in the host test tree via `CARGO_TARGET_DIR`); wasm apps share `bedcode-desktop/target/wasm-apps/` (`WASM_TARGET_DIR` in `scripts/plugin-wasm-config.mjs`, passed as `--target-dir` by each app's `build.js`); mobile fixtures share `bedcode-mobile/target/fixtures/`. Steady state: 9 fixtures = 417M and 4 apps = 150M, one copy of the graph each
- `packages/.cargo/config.toml` and `wasm-apps/.cargo/config.toml` pin the same directories, so **manual `cd <crate> && cargo build` and toolchain probes (clippy / rust-analyzer) land in the shared directory too** — without this, tooling silently recreated a 629M per-crate `debug/` directory. Neither file affects the host build: cargo discovers config by cwd ancestry, and `packages/` / `wasm-apps/` are not ancestors of `src-tauri/`
- The two shared directories are **deliberately not merged**: fixtures declare `[profile.release] opt-level="s"/lto=true` while the wasm apps declare no `[profile.*]` at all, and the profile participates in cargo's artifact fingerprint — one shared directory would keep two copies of the same dependency graph. They are also kept out of `src-tauri/target`, which owns the 15G threshold and the automatic `cargo clean` (mixing them would distort the accounting and couple the host cache to the fixture cache)
- `scripts/wasip3-toolchain.sh fixture` / `health` now build into the shared directories; `check-target-size.js` (both ends) still thresholds the host target as before but additionally reports every shared and leftover per-crate target directory (shared = keep, leftover = safe to delete) — it previously watched one directory and missed the other 16
- Reclaimed immediately: **3.9G** by dropping both hosts' `debug/incremental` plus the leftover per-crate directories (15.3G → 11.4G on the author's machine). Verified separately: `cargo test` does **not** hold the target-directory lock while tests execute, so fixtures sharing a directory with the parent test run cannot deadlock (probe: a concurrent `cargo build` with a real recompile finished in 0.04s mid-test)
- Not adopted, with reasons recorded in `.scratch/2026-09-26-cargo-target-space/spec.md`: a single root Cargo workspace (one `Cargo.lock` would couple the deliberate wasmtime 47/48 split of ADR 0019, mix stable/nightly toolchains, and let workspace feature unification contaminate wasm artifacts), sharing one target directory across the two hosts (little to dedupe — different wasmtime majors, target triples and feature sets; would serialize concurrent builds and widen `cargo clean`), and sccache (saves time, not space, and is mutually exclusive with incremental compilation). Mobile **plugin** targets were left alone: the published SDK CLI hardcodes `rust/target/...` in three places

#### The plugin→host sync event wire becomes the outbound wire — one format, no ABI bump (desktop; mobile wire byte-identical, but third-party plugins must rebuild)
- `bedcode_plugin_api::events::SyncEvent` used to travel as an internally tagged PascalCase object with flat fields, which the host then rewrote into the outbound `SyncPayload` shape (adjacently tagged snake_case + `data`) on its way to the mobile client. The two formats are now **one**: `SyncEvent` carries `{"type":"<snake_case variant>","data":{…}}`, its `session` field is the typed `wire::SessionSummary` and statuses are wire strings, so the host no longer restates a session event in another shape. The only asymmetry is `source_device` on `session_stopped` / `session_removed`: an envelope field the host uses to exclude the originating device, never serialized outbound
- **`host-events.broadcast-sync`'s WIT signature is unchanged (`event-json: string`), so the plugin ABI does not move** — but the JSON a plugin emits and the field types it constructs did change. Bundled artifacts were rebuilt; **third-party plugins must be rebuilt against the current `plugin-sdk-desktop`**. Stale artifacts are rejected at parse time with a named error instead of being read as "no event" — the fail-visible rule (AGENTS §8) applied to a format change rather than an interface removal
- Cross-platform wire shapes get a single source of truth in the SDK: `bedcode-plugin-api::wire` now defines `SyncPayload`, `SessionSummary`, `SessionControl*`, `Terminal*` and `KeyCombo`; the host's `enums/{sync,summary,control,special_key}.rs` are re-export shims (import paths unchanged, zero behavior change), and the mobile client keeps its parallel copy pinned variant-by-variant by `mobile_parallel_copy_shape_lock`
- CI gap closed: the shape locks moved into the SDK crate, but `test.yml` only ran `cargo test` in each end's `src-tauri` (and `sdk-publish.yml` only `cargo check`s the Rust side) — the desktop job now also runs the SDK crate's cargo test, otherwise the moved locks would execute in nobody's pipeline

#### Breaking plugin ABI v27 — old plugin artifacts must be rebuilt (desktop only; mobile untouched)
- ABI **26 → 27**, the first breaking contract change in this project: the `host-session` interface (12 functions) and `host-terminal` (`send`) are removed from the WIT as imports, and `terminal-hooks` plus `events.on-session-lifecycle` / `events.on-input-submitted` are removed as exports. Permission bits `session:write` and `terminal:observe` are retired (vocabulary 34 → 32); `session:read` now gates only host terminal-window facts. All four bundled plugin artifacts were rebuilt against the new SDK
- **An artifact built with an older SDK fails at instantiation, before ABI negotiation** — the host appends a diagnostic naming the missing interface and the required SDK version (`LoadedWasmPlugin::stale_artifact_rebuild_hint`), so the failure is actionable instead of looking like a trap. If you ship third-party plugins, rebuild them with the current `plugin-sdk-desktop` before upgrading
- Version-number rule unchanged and untouched by this work: desktop-only interfaces do not bump the mobile ABI (mobile stays at 11), so the mobile client and its SDK need no rebuild

#### HTTP protocol gateway — business URLs now alias to plugins (desktop, host business decarriage ticket 01)
- New platform service `server/gateway.rs`: a static alias table maps the ten business endpoints
  (`/api/configs`, `/api/quick-actions`, `/api/file-tree|file-tree-children|file-content|diff-tree|file-diff`,
  `/api/git/*`) onto their owning plugin's HTTP endpoint, so business implementations can move into plugin
  projects without the mobile client changing a line
- Cut-over requires all three of: host has verified the mobile JWT, the target plugin is `Activated`, and that exact
  endpoint is declared in its manifest `contributes.httpEndpoints`. Anything else falls through to the host
  implementation untouched — a plugin that is live but has not implemented the endpoint yet cannot steal a working
  route (the reverse of `/api/plugin/*`, where an empty declaration list means "pass the whole prefix")
- Forwarding reuses the existing plugin proxy kernel (`plugin_controller::forward_to_plugin`, header whitelist,
  `status`/`contentType` mapping, declaration governance); the gateway adds no new transport. Plugin `_http_endpoint`
  gains an optional `device` field carrying identity-only claim fields (`deviceId` / `deviceName`) — the JWT itself and
  the device fingerprint never leave the host
- Unverified requests can never be forwarded regardless of middleware registration order: `decide` takes
  `verified` as its first argument, and the actix "last registered wrap runs first" assumption that the wiring
  depends on is pinned by its own test
- The `/api` JWT gate moved from an inline closure to a named middleware (`jwt_auth::jwt_gateway`) so the ordering
  guarantee is testable on a real actix stack; the fallback branch never touches the payload, so host handlers keep
  reading their own typed extractors and byte-identical responses
- Response shapes for all ten endpoints are locked as golden JSON (including which optional fields serialise as
  explicit `null` and which are omitted), and a source scan pins that business handlers may only be mounted on
  aliased paths — the host route surface cannot silently grow back business endpoints

#### Plugin ABI desktop 16 → 19 (function-level appends to existing interfaces; mobile stays at 11)

- v19 `host-session` session face: config CRUD (`session:config`), `create-with-spec` (plugin computes the launch spec, host only does shell wrapping / WSL translation / size defaults / id pre-allocation), `restart` / `remove` / `rename` / `resize` (canonical-renderer decision rules in the plugin, registry fact in the kernel), `annotate`, `connections-list`; plus `host-platform.wsl-distros`

- `manifest-gen` command policy tightened: a manifest that already declares `contributes.commands` is treated as a hand-curated user-facing surface, so the generator reports the arm/declaration delta instead of overwriting it (release builds are now idempotent for this plugin)

#### Plugin ABI desktop v21 → v22 — `host-platform.reveal-in-dir` primitive; `system:open` permission retired (desktop; mobile stays at 11)

Same caliber as `pick-files` / `pick-folder`: revealing is a platform interaction that reads no data (the path is supplied by the caller), so it carries **no permission gate**, matching the rest of `host-platform`

#### Plugin ABI desktop v20 → v21 — `host-session` convergence retirement: `create` / `restart` removed (desktop; mobile stays at 11)
- `host-session.create(config-id)` (v6 legacy create) and `host-session.restart(session-id)` are removed along with their kernel executors: session creation orchestrates through `create-with-spec` only, and restart is now the plugin's own two-step orchestration (`remove` + `create-with-spec` carrying the same `sessionId`). This is the first **interface function removal** in the desktop ABI — older products (≤ v20) that still import these two functions are rejected at instantiation and must be rebuilt against the v21 SDK
- `create-with-spec` spec gains optional `sessionId` (JSON-level append, no interface change); a specified id that is still registered is refused explicitly (`session id already exists`) so the kernel arbitrates the fact while the plugin owns the ordering (`remove` first)
- Kernel business removed with it: `SessionManager::create_session_with_id` / `create_session_with_source_and_id` / `restart_session`, `DefaultNamingService` (`NamingService`), `DefaultConfigMapper` (`ConfigMapper`), `SessionStorage` (`SessionStore`) and the session manager's DB dependency — the kernel no longer reads the session config table at all
- Session config command face is plug-in-required: the plugin-private database is the only read/write path, the main-DB projection stops being written (it had no reader left) and the degrade branch is gone. The kernel `session_configs` table plus `host-session.config-list|get` stay as the plugin's one-shot legacy migration channel
- Restart keeps its external shape: the plugin emits `session-restarted` itself (`host-events.emit`, camelCase payload identical to the retired host `SessionRestartEvent`) **after** the `Created` lifecycle event, so the desktop frontend listener sees the same ordering as before
- Tests: closed-loop suites seed configurations after activation (the plugin-required face no longer tolerates the ordering that the old 5 s-timeout degrade path unknowingly hid), and all session-plugin closed-loop tests now take the shared private-DB serialization guard

#### Plugin ABI desktop v19 → v20 — `host-task` concurrency domain + optional `events-task` export (desktop; mobile stays at 11)
- New `host-task` interface (5 functions: `execute-batch` / `submit` / `status` / `cancel` / `list-jobs`; desktop-only dual-track deviation like v14-v19): WASM plugins cannot create OS threads and every host call is synchronously blocking — a plan of unit operations (`fs.read|read-dir|stat|exists|write` / `process.run-sync` / `http.fetch`, params are the verbatim request JSON of the underlying primitive, zero new DTOs) is handed to a dedicated host OS thread pool (`PLUGIN_TASK_POOL_THREADS` = 8, isolated from the tokio blocking pool) for true parallel execution
- Two shared unit-model APIs: `execute-batch` fans out and joins synchronously (blocks the Store exactly like `run-sync`, for fast ops only); `submit` returns `task-<hex>` immediately and reports progress/terminal events through the optional `events-task#on-task-event` export (probed after instantiation like `events-binary`/`events-ws`; old SDK products degrade to drop + warn + counter, `status`/`list-jobs` snapshots are the authoritative self-heal source)
- Dual-gate authorization: `task:run` gates the thread-pool resource itself; every unit passes its kind's existing domain gate again (`fs:read|write` + fs_auth with **no popup from pool threads** / `process:run` / `network:http`) — concurrency capability and data access stay decoupled
- Quotas (`PLUGIN_TASK_*`): 4 in-flight jobs per plugin, 256 units per plan, 1 MiB unit-result cap (truncated flag), default 600 s unit / 3600 s job timeouts, bounded 64-slot per-plugin callback queue (progress droppable with counter, terminal preferred, `status` authoritative), 64 retained terminal results
- Cooperative cancel / wall-clock timeout: phase flip stops new units (skipped entries in snapshots) while in-flight units finish and keep their results; deactivation purges all jobs and the callback queue (`task::purge_for_plugin` in `deactivate_plugin_inner`)
- Kernel primitive count 20 → 21 groups (process 2 → 3); re-entrancy discipline (spec §8) written into both host and SDK docs: pool threads never call into plugins (callbacks only via the serial dispatch task + instance lock), plugins must not synchronously wait for their own task events inside a guest call (use `execute-batch`), callbacks may re-`submit` within quota but should avoid callback storms
- Closed-loop fixture `packages/plugin-task-test` (wasm32-wasip3) + `test_task_*` host suite: parallel result ordering / event pipeline (started → completed) / status snapshot / cancel idempotence / legacy-product degradation / dual-gate denial

#### Engine-level PTY lifecycle: whole-registry reclaim on shutdown + live counting (desktop, session engine downsink P1 prerequisite)
- `host_api/pty.rs` gains two non-WIT engine primitives: `kill_all_registered` (kills and retires every registered plugin-private PTY across owners, emitting one `<owner>::pty:exit` per handle to its owner) and `live_count` (registered handles are live handles — the exit monitor retires them on termination). Both **share one implementation** with the existing per-owner reclaim, so the "only whoever removed the handle publishes the event" single-publisher invariant has no second copy
- The shutdown hook (`system/lifecycle.rs`, priority 10) now runs the whole-registry reclaim after the business-line `SessionManager::shutdown()` — **processes are reclaimed even when the plugin was already deactivated, timed out or trapped** (per-owner reclaim depends on the deactivation flow being reached, which shutdown does not guarantee)
- New `SessionManager::live_pty_count()` (`is_running() && !output_terminated()`) mirrors today's window-close guard criterion cell for cell (counts created-but-not-started `Starting`, counts `Running`, excludes killed/naturally-exited); it is the piece that lets that guard switch to an engine fact and stop depending on session records once the truth source moves

### Fixes

#### Desktop
- **Plugin re-activation while its view is open leaves the subtree on a revoked channel credential** — after a plugin is deactivated and re-enabled (or dev-watcher-reloaded) with e.g. the Session Center view open, the view's `onMounted` `load()` ran with the *pre-deactivation* `PluginContext`: `PluginViewHost` / `PluginSettingsSection` only `provide('pluginContext', …)` in their `setup`, and the old code's props-change `watch` re-provide is dead code — Vue's `provide()` only works when called synchronously during `setup` (verified against Vue 3.5 in a test probe). The stale context's channel token is revoked on deactivate, so every plugin-face command (`session.config.list` / `session.list` / storage…) was rejected with `缺少有效通道凭证` → user-visible `会话数据加载失败` + `发生了未知错误` toasts. Fix: (1) registry gains a reactive context projection + `contextIdentity(pluginId)` (stable per-object id, `contextsIndex` shallow ref, same pattern as `viewsIndex`); (2) both hosts now render the inner view through a keyed `PluginContextProvider` (new component) that re-mounts — and thus re-provides in `setup` — whenever the plugin's context object identity changes; (3) the loader registers the fresh context in the registry **before** `module.activate()`, so views (re-)mounting mid-activation always resolve the current context, and clears it again if activation fails. Regression tests: `PluginViewHost.test.ts` (re-activation re-provides the new context, same-object re-set does not churn) + `contextIdentity` contract tests in `registry.test.ts`; E2E-verified against the running dev app (plugin dev-watcher reload with the Session Center view open: zero `缺少有效通道凭证`, list commands re-ran on the freshly issued token)
- **Cross-plugin api drift check punished the wrong plugin** — `#[plugin_api]` compared trait vs manifest with *unconditional exact set equality*, so a plugin consuming another plugin's api had to mirror entries it never called. Adding the four session apis during the P1-b session-source sink-down turned `com.bedcode.file-transfer` red at build time (`ensurePluginWasm` fail-fast → desktop `tauri:dev` never started, `plugins:build` blocked, and merging dev to master/uat would have failed `test.yml`), even though that plugin calls exactly two of the peer's 31 apis (`consent-decide` / `trust-list`). The check is now **role-split**: a manifest inside the crate's own plugin package stays a declaration and still requires exact equality, while a peer manifest is a consumption mirror and only requires `trait ⊆ manifest` — calling an undeclared (renamed / removed) api still fails the build, adding one on the peer side no longer edits an unrelated plugin. Role is inferred from the resolved manifest path (no new attribute vocabulary) and named in the compile error. `SessionCenterApi` shrank 31 → 2. Rationale and both-direction probes: ADR 0017 v2, `.scratch/2026-09-23-session-engine-downsink/issues/13`
- **Terminal Session Center plugin: Tailwind utility classes were never compiled** — `bedcode-desktop/tailwind.config.js` still listed `./plugins/session/src/**` after the plugin directory was renamed (plus a `./plugins/scheduler/src/**` entry for a retired plugin) while `./plugins/terminal-session/src/**` was missing. Tailwind is compiled by the host only (no second `content` injection point, and plugin bundles ship no compiled Tailwind), so every class used *exclusively* by this plugin had no rule: 165 of its 405 class tokens are plugin-only and 158 of those were absent from the generated CSS — 9 Vue files / 77 class usages losing spacing, fixed sizes (`w-96`, `max-h-[440px]`, `h-[168px]`), grids (`grid-cols-[auto_1fr]`), z-index/positioning and state colours. `content` now points at `terminal-session` and the two dead paths are gone; a new guard (`src/__tests__/plugin/tailwindContentCoverage.test.ts`) locks `plugins/*` and the content list together in both directions
- **Two host design classes the plugin referenced never existed**: `wb-select` (four native selects in the terminal header / settings panel) and `wb-btn-secondary` (background-image picker) are defined nowhere — the host stylesheet ships only `wb-btn-ghost` / `wb-btn-primary` / `wb-mono` / `wb-section-title` / `wb-sidebar-section` / `wb-toolbar`. The dead names are removed: selects now carry `cursor-pointer` + `focus:border-brand` (the host form-control focus treatment) and the picker button uses `wb-btn-ghost`, the class the pre-migration markup used
- **`.plugin-icon` is a scoped class of the host's toolbar components** (scoped styles do not leak), so the three extension-point icon slots the plugin re-creates had no rule at all; the plugin now defines the same `font-size: calc(14px * var(--ui-scale)); line-height: 1` rule in its own scoped block

### Security

#### Desktop
- **Business sessions are now spawned on the `pty:spawn` / `pty:io` face, so the session plugin holds the arbitrary-command-execution bit (P1-b)**: creation moved from the host's `create-with-spec` executor (which wrapped argv itself) to `host-pty.spawn` driven by the plugin, and the two PTY permission domains are declared in the session manifest together with `dependencies: ["host-pty"]` and a `ptyQuota: 8` self-declaration. Consequences pinned: the host still performs no shell wrapping, argv is entirely plugin-computed (no new injection surface); the quota is arbitrated at load time and out-of-range declarations reject the manifest instead of being clamped; the terminal-input command kept all three gates it had (identity-bound credential, activated, `terminal:input`) — routing was moved, not loosened
- A user-installed copy can no longer shadow a bundled plugin with the same id: the two startup scans (packaged `resources/plugins/desktop`, then `app_data/plugins`) each kept their own `seen_ids`, so a duplicate id from the user directory silently replaced the built-in entry in the merge (the “duplicate id is rejected” comment only held *within* one scan; with the dir-name = manifest-id binding enforced, that check was in fact dead code). The shadowed plugin then read as `UserInstalled` — trust tier downgraded out of the build trust domain — and activation was refused by the approval gate (“requires user approval before activation”), which is exactly how the stale `file-install` copies of `com.bedcode.agent-hub` / `com.bedcode.ai-chatbox` under `app_data/plugins` blocked both bundled plugins. The two scans now share one dedupe set (`PluginLoader::load_builtin_and_user`): the built-in entry wins and the user copy is rejected with a log line
- Built-in `fs_auth` trusted-plugin whitelist seed retargeted from `com.bedcode.auto-task` to `com.bedcode.session` (the merged plugin is what writes agent integration files into user projects; leaving the seed behind would silently downgrade it to per-directory prompts)
- Auth layering documented and enforced in one place: pairing / QR orchestration lives in the plugin, while signing, verification execution, key custody (host-auth secret store) and the `pairings` / `connection_history` tables stay in the kernel
- The pairing / QR host **fallback implementation is retired** (2026-09-21, same batch as the command-face convergence): the `auth_center` pairing/QR bridge functions, `PairingService`, `QrTokenManager`, `utils/auth/pairing.rs` and their `AppContext` wiring are deleted. The fallback had no entry point left once the host Tauri commands were retired (leaving it would be zombie code and would suggest the host can still sign pairing codes); when the plugin is not active the frontend command face fails loudly instead. What remains host-side is the `host-auth` record face (key custody, device/history records) and the `auth-policy` capability — whose transport failure still falls back to allow (a designed degradation that keeps a plugin fault from killing every connection, not a bypass)
- Credentials still logged by length only; plugin permission list narrowed to 15 entries with every bit traced to a real consumer (two spec-listed bits with no call site were deliberately not declared)
- #### Permission vocabulary collapsed to one source, locks widened to every bit (desktop, wasm-core-audit ticket 01)
- The desktop SDK's `permission.rs` is now the only place permission vocabulary is written: a `PERMISSION_VOCABULARY` reflection table pairs each constant's identifier (via `stringify!`, so identifier and value cannot drift apart) with its string, and `VALID_PERMISSIONS` is derived from it by a `const fn` — adding a bit is a one-line change
- The packaging CLI and the host frontend read **generated** copies (`bin/permission-vocabulary.json`, `src/plugin/permission.vocabulary.ts`, produced by the SDK's `pnpm run gen:permissions`); the three hand copies measured 28 / 22 / 24 entries and are now all 30. `manifest-gen`'s UI registration table derives from the same artifact (A/B-compared byte-identical output on all four production plugins)
- Two bits the frontend genuinely enforces (`ui:pageToolbar`, `ui:fileHandler`) entered the source of truth together with `ui.registerPage → ui:sidebar`, which had existed only in the frontend copy: declaring them was filtered to nothing at grant time. `bus` / `fileservice` / `transfer` left the file-transfer manifest, and `bus` is documented as not being a desktop permission bit at all (mobile's SDK has `PERMISSION_BUS` — ADR 0018 divergence recorded, mobile untouched)
- `bedcode-plugin validate` is now on the build chain: rules extracted into `bin/manifest-validate.js` shared by the CLI and `scripts/plugin-build.js`, which aborts before compiling a plugin whose manifest declares vocabulary the host would silently drop
- Locks went from two permission bits to the whole vocabulary: five Rust locks (three-copy set equality; artifacts marked generated and genuinely imported; **every bit has an enforcement point**, derived by scanning host sources through the reflection table rather than a hand list; production + fixture manifests declare only known vocabulary; validate really runs in the build chain) and five frontend groups (every `requirePermission` call site in `context.ts` maps to exactly one bit under granted/ungranted/other-permission tri-state). Both were mutation-checked — deleting one method from a generated file reddens three groups, inventing a gateless bit reddens the enforcement lock
- Gate-denial cases added for the three domains that had none (`mdns` / `peer` / `database`), each paired with a granted positive control so an always-denying gate cannot pass as green
- #### Main-DB SQL isolation moved into the SQLite engine, `storage` stops being free (desktop, wasm-core-audit ticket 02)
- `Connection::authorizer` now arbitrates every table access while a plugin statement prepares: only `plugin_<id>_-prefixed` objects are reachable, everything else — `plugin_secrets` (plaintext host-managed keys), `pairings`, `connection_history`, `settings`, other plugins' tables — is denied at prepare time. The eight regex patterns remain, but their documented role is early failure with a readable message; **they are no longer the boundary**
- Escapes the regex layer could not see are now closed and each pinned by its own case: comma multi-table reads (`FROM own a, plugin_secrets b`), comma multi-table exfil writes into the plugin's own table, quoted/bracketed/`main.`-qualified identifiers, `ATTACH` (mount an arbitrary database), `PRAGMA database_list` (hands the host DB path to the plugin), direct `sqlite_master` / `sqlite_sequence` reads and `ALTER TABLE … RENAME TO` an outside name
- Policy calibrated by probe, not guesswork: DDL books itself into `sqlite_master`/`sqlite_sequence`, so catalog access is allowed only when the statement does not name a catalog table itself (comments and single-quoted literals are stripped before the check; quoted identifiers are kept, because `"sqlite_master"` is exactly the evasion form). `CREATE INDEX` also passes an implicit `Reindex` and `ALTER TABLE` calls `printf`/`substr` — denying those would have blocked legitimate DDL
- Two-layer split proven both ways: five red-first escape cases (run red against the old implementation before the fix) and two positive batteries proving the纵深 does not over-block (own-prefixed CRUD, self-join, quoted names, AUTOINCREMENT, index and view lifecycle). Rejections stay fail-visible and name only table/column — never the value
- `grant_permissions` no longer inserts `storage` for every plugin: that default grant is what made the main-DB and private-DB gates pass unconditionally. Permissions are now exactly what the manifest declares and the vocabulary knows, `database:main` is a separate high-risk bit for the main-DB face (declaring it grants no private-DB access and vice versa), and declarations filtered as unknown are logged at activation instead of vanishing
- Consumer inventory: no production plugin calls the main-DB face (`db_execute` / `db_query` family) — the four desktop plugins use `plugin_db_*` only — so the face is reclassified as first-party-on-request in AGENTS §7, joining ticket 03's per-bit confirmation list. The SDK self-check fixture and the headless e2e scaffold picked up the new bit
- Mobile fork recorded, not silently carried: the mobile SDK still auto-grants `storage` and has no `database:main`, so grant semantics now differ by platform by design of this ticket's scope
- #### Session and terminal actions became owner-scoped (desktop, wasm-core-audit ticket 04)
- `SessionManager` now keeps an opaque `session-id → creating plugin_id` registry, written in the same step as the session record and cleared with it. It deliberately does **not** join `SessionInfo` / `SessionInfoView`: ownership is a host-side access-control fact, not a display field, so the wire shape and the mobile client are untouched — and because `plugin_id` already reaches `host_impl` from Store state, no WIT signature moved and **the ABI does not bump**
- Enforcement order is permission gate → argument gate → owner gate, in `session_close` / `session_remove` / `session_rename` / `session_resize` / `session_annotate` and `terminal_send`: a third-party plugin holding `terminal:input` can no longer type into the terminal the user is working in. Rejections read `not owner of session …` — same wording family as pty / ws / mdns — and never echo the real owner id
- Contract narrowing, on purpose: closing or removing an unknown session id used to succeed silently; unknown ids can't be attributed, so they are refused like a foreign owner. Blind delete attempts across all ids no longer pass without a trace
- `session_lifecycle_register` required **no permission at all**: any activated plugin could attach a listener and enumerate every session id, name and working directory — the first link of the injection chain. It now asks for `session:read`, keeping the documented split (lifecycle = metadata, submitted input lines = plaintext credential surface)
- Annotation slots are now single-writer per session: the ticket proposed a `plugin_id + key` namespace, but the slot's read path feeds the kernel's outward DTO shape, so choosing whose `taskStatus` wins would push product semantics back into the kernel. With non-owner writes refused, per-session ownership achieves the isolation the item asked for without that regression; the deviation is recorded in the ticket
- Peer handles gained the owner column they were missing (`sess-<uuid>` was unguessable but not access-controlled): ownership is checked before touching the engine and before `require_app`, so a probe in a headless environment gets the same answer, and a refused `close` restores the handle rather than leaving someone else's connection detached
- Verified against the product path rather than assumed: all session creation (desktop UI, mobile HTTP/WS, timers) already funnels through `com.bedcode.session`'s own orchestration, so the plugin is by construction the owner of every session and its flows stay intact; file-transfer's `session-remove/rename/resize` entries are drift-check API mirrors with no call site
- #### The message bus became a real boundary: topic namespaces and the reply lane (desktop, wasm-core-audit ticket 05)
- Subscription used to be validated nowhere: the "owner-scoped" topics were a naming *convention*, so plugin B could subscribe `pty:exit.<A>` and eavesdrop on A's process exits, or publish to that same string and forge an exit A never had. The bus now decides access by **topic shape**: `<plugin-id>::<name>` is that plugin's inbox — only the owner (and the host) may subscribe or publish it, cross-namespace attempts are refused on the Rust side with the error returned to the guest, not dropped silently
- Mechanism chosen as B (namespace marker) over A (parse an owner segment and match it against the plugin table) precisely because A's verdict would depend on *timing*: while the victim is not yet activated — or not yet installed at all — a suffix lookup calls its topic a public one, so racing the first event is enough. A shape-based rule needs no registry and no ordering. `::` is unambiguous because `validate_plugin_id` allows only `[a-z0-9-]` segments, so a colon can never appear inside an id
- Host-directed events moved to the new shape (`<owner>::pty:exit`, `<owner>::ws:open|error|close|client-connect|client-disconnect`, `<owner>::mdns:found|lost`), and the shape now has **one definition**: the host composes topics with the SDK's `owned_topic`, so the byte-for-byte drift lock this repo needed for pty/ws no longer has anything to lock. `mdns` gained the helper it never had (its consumer hand-formatted the string)
- Legacy form fails loudly instead of starving quietly: a stale artifact subscribing `pty:exit.<own-id>` gets a rejection naming `<own-id>::pty:exit`. Letting it through would have meant "subscribed fine, receives nothing forever" — and the old string, now public, could still be published to by anyone, so a stale subscriber was also a spoofing target
- Inter-plugin reply lane (P1-4) closed on both sides. The reply topic was subscribable by any plugin and the SDK's correlation id is a per-instance monotonic counter (`req-1`, `req-2`, …), so guessing one was enough to read — or to answer — someone else's API call. Two rules now apply: `bedcode.api.reply.*` is **host-only to subscribe** (the reply subscription was always host-registered inside `host-api-call`), and `ReplyHandler` accepts a reply only when `msg.sender` equals the plugin that **declared** that api — `sender` is stamped by the host from Caller state, so a guest cannot forge it. A red-first case demonstrates the forged reply being returned to the caller before the fix
- The reply lane deliberately did **not** move into the caller's namespace: responders are other plugins and must be able to publish into it, and an "except: non-owners may publish" carve-out would void the inbox semantics the namespace exists for
- Fixed on the way: `api_call` registered its reply subscription *before* the gate ran, so every rejected call (undeclared target) leaked a subscriber entry and its consumer task. The owner is now resolved first, and a publish failure cleans up
- Consumer inventory of all four desktop plugins: only file-transfer subscribes directed events (two mdns topics, migrated to the SDK helper); the session plugin publishes only public lanes (`task:*`, `session:mode-changed`, which currently have no subscriber at all — the bus has no TypeScript-facing API, so no frontend consumer exists), and ai-chatbox / agent-hub never touch the bus. Test fixtures subscribe via the SDK helpers, so they follow the new shape by construction; the pty/ws fixtures now log-and-continue when their activate-time subscribe is refused, because the isolation cases instantiate one artifact under a second owner id and the guest can only name its compile-time id
- Mobile divergence recorded, not silently carried: mobile's `host-mdns` still publishes `mdns:found.<owner>` and the mobile bus has no namespace gate, so this ticket's desktop result is not a correctness argument for that side; the follow-up list (mobile SDK primitive + bus ACL + mobile file-transfer migration) is in the ticket
- `bus` remains **not** a desktop permission bit: access control lives in topic shape, which is checked on every call, rather than in an all-or-nothing grant
- #### Desktop approval chain wired onto the activation path (desktop, wasm-core-audit ticket 03)
- ADR 0020 had claimed "implemented (desktop 2026-08)" while `approval.rs` had zero production callers: activation granted the whole manifest (`grant_permissions`) and a zip-installed plugin was trusted with `process:run` / `pty:spawn` the moment it landed on disk. `activate_plugin` now runs `verify_approval` **before** preauthorization, writes `NeedsApproval` and refuses to activate when there is no approval record or when the directory hash moved since approval (`HashMismatch` also revokes the stale record and logs it)
- The effective set is enforced, not merely computed: user-installed plugins are granted `approved ∩ requested` (the permission manager holds that set, which is what every host-side gate consults), and the `storage` default grant inside `effective_permissions` is gone — the same default bit had already been dropped from `grant_permissions` in ticket 02
- Approval pins content, and the pin knows what is *not* content: `compute_dir_hash` skips the plugin's private SQLite database plus its `-wal` / `-shm` / `-journal` sidecars, which live inside the plugin directory (`app_data/plugins/<id>/plugin.db`) and change while the plugin runs — counting them made "approve → enable → enable again" look like a replacement attack and revoked the plugin's own approval. Code-bearing files stay pinned, and the new test pins both directions (runtime data ignored, a new `evil.js` still moves the hash)
- A pending approval is visible, not silent: `NeedsApproval` was already in the state enum and the locale tables, but nothing ever produced it. Plugins are now listed as "待授权", and both the list toggle and the detail page open the approval sheet before enabling (approve-then-enable, matching the mobile interaction), instead of failing with a bare error
- Permission copy coverage was a ticket prerequisite and is now complete: the display table covered 13 of 31 vocabulary entries, so the approval sheet would have presented permissions it could not name as "未知权限". All entries have zh-CN + en copy, and the four high-risk bits (`process:run` / `pty:spawn` / `terminal:input` / `database:main`) carry a consequence line and a red badge — high-risk emphasis, whole-manifest approval, per ticket 03's ruling (per-bit confirmation is not added)
- Trust tiers made explicit in code: only `UserInstalled` is gated; bundled resources (`FileScan` / `Wasm` / `StaticRegistry`) stay build-trusted, as ADR 0020's table says. Upgrades follow the mobile precedent instead of killing running setups: a persisted-enabled user plugin with no approval record is approved once at first boot with a `warn` trail naming the permission count; permission-list-change re-prompting is deliberately deferred (recorded in the ticket)
- Installation limits and content checks that were missing: archives are refused over 512 entries / 64 MiB total / 32 MiB per entry, measured by **bytes actually written** (declared sizes are not trusted; a `take(size + 1)` probe separates "exactly at the limit" from "over"), every failure path clears the temporary directory, and the WASM SHA-256 is verified when the manifest declares `wasm_hash` — a new optional desktop manifest field matching the mobile one, empty meaning the publisher declared nothing (skipped, debug-logged, content pinning still applies through the approval hash)
- Mobile untouched: it has had this gate since 2026-08; this is the desktop half of ADR 0020 plus the manifest field desktop was missing
- #### Frontend plugin channel binds identity by host-issued credentials (desktop, wasm-core-audit ticket 06)
- The `plugin_*` bridge trusted its `plugin_id` argument: any plugin frontend in the same webview could `invoke('plugin_storage_get', { pluginId: victim, key })`, and `plugin_invoke` did not even run a permission check — plugin A could drive plugin B's commands and read or overwrite B's storage. Identity is now resolved **from a credential, never from the argument**: the argument is only a *target*
- Two credential kinds, because "who called" is not verifiable on a Tauri command (no caller-script URL; host code and every plugin share one webview): a **loader session key** (host-frontend face) and per-plugin **channel tokens** (plugin face). The loader key goes to the **first caller** of `plugin_frontend_loader_session` after each page load, and `pluginLoader.loadAll()` fetches it *before importing any plugin module* — plugin code only starts running after its module is imported, so it can never obtain one. Tokens are minted via `plugin_channel_token(plugin_id, loader_session)` for running plugins and revoked on deactivate
- Every plugin-face command now carries `credential`: a plugin token authorises only its own plugin id (mismatch refused, both ids named in the error), while the loader key authorises any target (host duties: the config page reads/writes plugin storage, host `pluginInvoke` drives plugin commands). Missing, forged or revoked credentials are refused — there is no fallback to trusting the argument, and `plugin_invoke`'s host-side comment claiming the id "cannot be forged" is gone
- `plugin_fs_auth_respond` is now host-face only. The authorization-request event is broadcast, so an unbound respond command let any plugin frontend answer *its own* file-access prompt — the consent dialog would have been decoration
- `sandbox` retired instead of faked (ruling 2). The field promised an `isolated` mode while `loader.ts` skipped every non-inline plugin and no isolation implementation existed. It is gone from the plugin manifest (Rust SDK + both TypeScript copies), from the four bundled `plugin.json` files, from the loader branch and from the frontend types. Old artifacts still carrying the key load as usual (unknown key, per the "old end ignores unknown fields" rule) and the key is never re-emitted; tests on both sides pin that
- Boundary stated instead of implied: this closes the "one `invoke` line with a self-reported plugin_id" channel, not the fact that plugin frontends share a realm with the host (prototype/timing tricks stay theoretically possible — the reason the `isolated` promise is deleted rather than half-implemented). Host management commands (activate / install / uninstall / approve / dev-reload) remain unbound per ruling, and plugin-frontend Tauri event subscriptions cannot be bound to a caller; both are recorded in the ticket
- Tests: 7 registry cases (single-issue loader key, forged/empty credential, cross-plugin refusal, re-issue and deactivate revocation, page-load reset) plus a 4-case frontend contract suite asserting the credential actually travels on every plugin-face call; the loader-gating suite now asserts the retired `sandbox` field no longer gates loading
- #### File-system privileges stopped being global (desktop, wasm-core-audit ticket 07)
- Two "trusted" shortcuts did the actual work in `fs_auth`, and both were wider than their names: a **substring** rule let *any* plugin with `fs:read` touch any path containing a `.claude/` segment — including attacker-planted directories under `/tmp` — which hollowed out the "prompt for unauthorised directories" fallback; and the built-in plugin list (`terminal-session`, `file-transfer`) meant **every path**, so those two plugins' file reach was bounded by two permission bits and nothing else. The `path_whitelist` field behind layer 1 was permanently empty and had no writer
- Inventory first, because the ticket's own framing was wrong about who consumes what: the `.claude/` rule's real consumer is **`com.bedcode.agent-hub`** (it distributes skill copies into `~/.claude/skills` and `~/.pi/agent/skills` from a `~/.agents` source library) — not `terminal-session`, which was already covered by the plugin list. `file-transfer` turned out to call **no** fs primitive at all (transfers go over peer-net), so its privilege was decoration and is deleted rather than migrated
- Layers went from four to three, with no decorative one left: ① per-plugin, per-attributed **first-party integration directories** (`FIRST_PARTY_TRUSTED_DIRS`, every entry carries the comment naming the code that needs it) — either a home-relative prefix (component-bounded, so `~/.agents` does not cover `~/.agentsx`) or an exact **path segment** name (so `.claudex` and `x.claude` no longer match, unlike the old substring); ② persisted grants from the dialog; ③ the dialog itself. If `home_dir()` is unavailable the home-shaped entries stay closed instead of degrading to "that segment name anywhere"
- `check`, `check_batch` and `is_granted` now share one judgement function (`matched_layer`) and log **which layer** let a request through (`layer = first-party-dir | persisted-grant`); previously the three entry points hand-copied the same three checks, which is how they would have drifted apart
- The pool-thread promise in `manager/task.rs` was a comment, not a behaviour: task units called `fs::*` straight into the pipeline's `check`, so an unauthorised path opened a dialog **on a worker thread** and held a pool slot for up to 30s. Units now pre-judge the same two gates in pipeline order — missing declaration answers the byte-identical `permission denied`, missing directory names the way out (`host-fs.request-auth`) — and never prompt. Getting the order wrong sends a plugin to the wrong remedy, which is exactly what one of the existing dual-gate tests caught

- #### WASI preopen can now be declared read-only (desktop, wasm-core-audit ticket 07 second batch)
- The last write-everything corner of the sandbox is now declarable: `wasiPreopenDirs` entries take two shapes — a bare path string (writable, the only shape that existed, so every current manifest is unchanged) or `{ "path": "~/.ssh", "readonly": true }` (mounted `FsPerms::ReadOnly`, guest `std::fs` writes are refused by WASI `OpenMode` while reads and listing keep working). Shape precedent lifted from ticket 08's `{path, auth}` endpoint entries rather than inventing a second convention inside one manifest
- Deliberate deviation, recorded so it does not read as an oversight: the **default tier is writable**, not "strictest" as in ticket 08. Bare-string entries had exactly one mode before this change, and giving the object form a different default from the string form inside the same list is the kind of surprise that gets a plugin's own tightening wrong. `readonly: false` and omitting the key are one legal state
- Read-only is a **narrower capability, never a cheaper authorisation**: `resolve_preopen_dirs`'s `is_granted` filter and `preauthorize_plugin`'s prompt collection both ignore the tier, so an unauthorised directory of either tier still mounts nothing. That is the shortcut this ticket's ruling 3 rejected, now pinned by a mutation (letting `readonly` bypass the grant check reddens the ungranted-declaration case)
- Strictness added where silence used to be: an unknown key in an object entry (`read_only` mispelled, say) or a non-boolean `readonly` fails the build at `manifest-validate.js` **and** fails manifest parsing host-side instead of degrading into a writable mount. The host check is hand-written (`WasiPreopenDir::from_json`) rather than `derive(Deserialize)` because serde's `untagged` rejects without naming the offending key — and for a third-party zip that never saw our CLI, that parse is the only arbiter, so "data did not match any variant" is not a diagnosable answer
- Two places easy to get wrong and now locked: `${home}` expansion replaces the path *through* `with_path` so the tier travels with its entry (rebuilding the entry during expansion drops the mode before the mount, invisibly from outside), and the read-only tier still gets its directory created — `preopened_dir` requires an existing directory, so "read-only" implemented as "don't mount" would leave the plugin unable to read either. Activation-time preopen drift detection compares host paths only, which is sound because a tier change can only arrive with a manifest change, and a manifest change always re-instantiates

Preopen is declaration-driven and frozen for the instance's lifetime; `host-fs` is arbitrated per call. - #### The WASM content hash got a producer (desktop, wasm-core-audit ticket 14)
- Ticket 03 shipped the *check* (a declared `wasm_hash` is verified against the packaged wasm) but nothing ever declared it: the packaging CLI copied `plugin.json` verbatim, so the protection was opt-in per publisher and every in-repo plugin opted out. It is now produced by default, on the build chain
- Ruling A — **artifact only**: `packages/plugin-sdk-desktop/bin/wasm-hash.js` computes the SHA-256 of `<rustLibrary>.wasm` after the artifact directory is assembled and writes `wasmHash` into the **artifact** `plugin.json`. - Every assembly point calls the one implementation: the four desktop plugins' `scripts/build.js`, the dev hot-reload copy in `scripts/plugin-watch.js` (overwriting the artifact manifest with the source one would otherwise wipe the key), and the SDK CLI's `build --resources-dir`. `scripts/plugin-build.js` deliberately does **not** inject a second time — it delegates to `pnpm run build`, and two writers of one field is how it drifts

#### Desktop
- **New `bench/` bridge-benchmark project measures the wasm ↔ host ↔ frontend path (21 scenarios / 7 groups, no product code touched)** — the existing perf probes each covered one segment of one link (`terminal_output_perf.rs` on PTY output consumption, `ws_output_perf.rs` on WS frame throughput) and all of them run headless, so the cost distribution of a full round trip (`invoke` → host → wasm → host primitive → event → frontend) had no data behind it. First baseline (debug host, 5 iterations, medians): `nop` round trip **56 µs** (0.3% of a 16 ms frame — the command face is not a bottleneck), 1 MiB synchronous return **1.77 ms** (~1.7 ns/B), single `api_call` **359 µs** (638 µs with a 64 KiB reply), 1 MiB `ring-fetch` drain **19 ms** with only 31% of it inside the guest, `execute-batch` of 64 statements 343 µs. Two findings are filed as follow-ups rather than silently absorbed: a **512-message bus burst delivers only 20.7%** (subscriber queue cap 64, drop is warn-only and invisible to publishers/subscribers), and **`host-storage` round-trips 1 MiB in 26 ms** (~25 ns/B, an order of magnitude worse than crossing the WASM boundary — so it must not be used as a large-object cache). Full table and derivations in `.scratch/2026-09-26-wasm-bridge-bench/report.md`

- **Follow-up measured on the same project: the Tauri IPC leg, not the WASM boundary, is the expensive one; a slow guest call blocks the whole plugin instance.** The webview layer (`e2e/specs/bench.spec.ts`, now green — 2 scenarios inside a real app window) measures the *same* commands through the app's own frontend wrappers (`src/plugin/commands.ts` / `src/plugin/events.ts`). Result: a `nop` round trip is 54 µs inside the host but **560 µs from the real frontend** (IPC + frontend bridge ≈ 0.5 ms), and a 1 MiB command return goes 1.87 ms → **27.7 ms** (≈ +24.6 ns/B) — a payload crossing the webview↔host boundary costs **an order of magnitude more** than crossing the WASM boundary, so any design that ships a large object back through the command face must budget ~25 ms/MiB. On the event leg, chunking shows **no** front-end advantage either: 1 MiB as one frame 37 ms, as 64×16 KiB 27 ms, as 256×4 KiB 33 ms — the case for chunked delivery (output-ack / sharded push) is smooth rendering and ack-ability, not throughput. Scenario **G2** (new) quantifies the concurrency risk the plugin-concurrency-model spec is built on: while one 26 ms `storage` call is in flight, a 50 µs `nop` on the same instance takes **26.1 ms (167×)**, and 4 concurrent slow calls take 4.04× a single call — fully serialized. G2 is proposed as that spec's acceptance baseline (after the event-loop-owner model it should fall to ~1×). Getting the webview layer to run required three fixes, documented in the spec: the debug binary loads `devUrl`, so a vite dev server must be running; `browser.tauri.execute` only carries the function source, so Node-side values must be interpolated into the body; and the loader-session credential is first-caller-wins, so the measurement borrows the app's own already-cached one
- **`bench_channel.rs`: a debug-only host command measures the third Tauri transport (`tauri::ipc::Channel`), and it wins by 4x — with a 6x trap in the obvious spelling.** The product uses two Tauri transports (command return values, `app_handle.emit`) and **zero** Channels, even though the desktop app once shipped a Channel-based terminal output stream (`commands/terminal_stream.rs`, retired 2026-09-22 with the session downsink — the reason was architectural, not performance). Since the output-ack follow-up P2 ("host-side push") will have to pick a transport, the benchmark now measures all three over the same 1 MiB: **Channel `Response`/raw 7.0 ms** (ArrayBuffer, ≥1024 B bodies take tauri 2.11's `ChannelDataIpcQueue` + webview `fetch` path) vs event emit 33 ms vs command return 28 ms. The trap: `Channel<Vec<u8>>` is **100 ms** — `IpcResponse` has a blanket `impl<T: Serialize>` (`ipc/mod.rs:181`), so `Vec<u8>` is serialized as a **JSON array of numbers** and the webview receives `[object Array]`, not bytes; real bytes require `Channel<Response>` + `InvokeResponseBody::Raw`. A second data point: chunk size has a floor — 4 KiB×256 (52 ms) is 3× slower than 16 KiB×64 (17 ms) for the same 1 MiB, so streamed pushes should not go below 16 KiB.
