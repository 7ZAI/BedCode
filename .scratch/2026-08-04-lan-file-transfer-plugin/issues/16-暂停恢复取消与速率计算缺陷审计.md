## Bug 1（🔴）：dial 失败路径 `unregister_pause` 缺失

### 位置

`bedcode-desktop/src-tauri/src/peer_transfer.rs:828-904` `drive_send_session`（移动端同构）：

```rust
let pause_slot = PauseSlot::new();
session_app.state::<PeerTransferState>().register_pause(&session_batch_id, Arc::clone(&pause_slot));
let session = tauri::async_runtime::spawn(async move {
    let conn: Connection = match dial_for_send(&node, &record).await {
        Ok(conn) => conn,
        Err(detail) => {
            settle_failed(&session_app, &session_batch_id, &detail, epoch).await;
            return;   // ← 缺 unregister_pause
        }
    };
    let cancel = session_app.state::<PeerTransferState>()
        .cancel_token_of(&session_batch_id).unwrap_or_else(CancelToken::new);
    let _ = bedcode_peer_net::send_batch(conn, session_batch_id, sources,
        events_tx, cancel, encrypt, Some(pause_slot)).await;
});

// 事件转发循环
while let Some(event) = events_rx.recv().await {
    match event {
        TransferEvent::Terminal { batch_id: bid, .. } => {
            app.state::<PeerTransferState>().unregister_pause(&bid);  // ← 只有这里摘除
            apply_terminal(&app, &bid, state, epoch).await;
            break;
        }
        ...
    }
}
```

### 根因

`register_pause` 在 dial 之前调用（为了让暂停命令能在会话内生效）。若 dial 失败：

1. `settle_failed` → `apply_terminal` → status 置 "failed"；
2. 但 `unregister_pause` 只在 `drive_send_session` 的 `Terminal` 事件分支执行；
3. dial 失败路径 `return` 不进入事件循环（session 任务直接返回，不 emit Terminal），pause_slot 永久驻留 `pauses` HashMap。

### 后果链

后续操作行为：

| 用户操作 | 期望 | 实际 |
|---|---|---|
| `pause_peer_transfer(failed_id)` | 拒绝对已终态任务暂停 | `task.dto.status != "running"` 早退 `Ok(false)` ✅ |
| `cancel_peer_transfer(failed_id)` | 直接 mark cancelled | `cancel_token_of` 若 sessions 已 unregistered → 走乐观路径 mark cancelled 返回 `Ok(true)`；若未 unregistered → 走 Live 路径发 token，token 唤醒无人消费 |
| `retry_peer_transfer(failed_id)` | 新会话替换旧 | 新建 batch_id，旧 pause_slot 泄漏但影响面有限 |

更严重的场景：**pause_slot 残留导致后续 resume 误判活跃**（罕见但可能）：dial 失败后任务已 failed，pause_slot 仍驻留 `pauses` HashMap；用户对同类 batch_id 再次发起传输（重试新建 batch_id 不受影响，但若 batch_id 复用或对端后续建立新会话），`pause_slot_of` 误命中陈旧 slot，resume/新会话暂停门控错位。

另注：dial 失败发生在握手前（对端未开始推流），不存在"对端仍在推流"场景——那是 send_batch 内部失败，会走 Terminal 事件正常摘除。

### 修复建议

在 `settle_failed` 错误路径显式摘除 pause_slot：

```rust
Err(detail) => {
    session_app.state::<PeerTransferState>().unregister_pause(&session_batch_id);
    settle_failed(&session_app, &session_batch_id, &detail, epoch).await;
    return;
}
```

或在 `apply_terminal` 内统一处理（更保险）——但需区分 `user_paused` 分支（该分支不摘 pause_slot 是刻意的）。

## Bug 2（🟡）：`pause_peer_transfer` 无活动会话时状态处理（描述已更新）

### 现状核对（2026-09 重构后）

`PauseRoute` 已重构为 `Serve` / `SendSession` 两分支（无 `Live`/`Old`），当前代码（293-357 行）：

```rust
match route {
    // 服务侧拉取记账任务（sources 空）：门控入口在 serve 暂停注册表
    PauseRoute::Serve => match super::peer_receive::handler_and_config(&app).await {
        Some((handler, _)) if handler.set_serve_paused(&batch_id, true).await => {
            publish(&app);
            Ok(true)
        }
        _ => {
            // 无活动 serve 会话（对端已断开/会话已结束）：还原状态，避免假暂停
            set_running_status(&app, &batch_id).await;
            Ok(false)
        }
    },
    // 本端发起的发送会话：门控暂停（写 Pause 帧并停推流，连接保持）；
    // 无活动会话回落取消令牌
    PauseRoute::SendSession => {
        let handled = if let Some(slot) = state.pause_slot_of(&batch_id) {
            slot.send(PauseCmd::Pause).await
        } else {
            false
        };
        if !handled {
            if let Some(token) = state.cancel_token_of(&batch_id) {
                token.cancel();
            }
        }
        publish(&app);
        pump_send_queue(app.clone()).await;
        Ok(true)
    }
}
```

### 实际行为 vs 原审计描述

| 场景 | 原审计描述 | 实际行为 |
|---|---|---|
| Serve 分支无活动会话 | "同样无回退" | ✅ **已回退**：`set_running_status` 还原 running 并返回 `Ok(false)` |
| SendSession 无 slot | "任务卡死在 paused" | ⚠️ **降级合理**：任务保持 paused，会话被取消（`token.cancel()`），`apply_terminal` 的 user_paused 分支不落终态，任务可后续恢复/重试 |
| `slot.send` 返回 false（通道断开） | "静默失败" | ⚠️ **存在**：`handled=false` 时回落 cancel token，不会假成功，但任务仍显示 paused |

### 残留风险（低危）

`slot.send` 返回 false 时：任务置 paused、会话被取消、返回 `Ok(true)`。用户看到"已暂停"但实际会话已终止（可恢复/重试）。原描述"任务永久卡死"不成立——`apply_terminal` 的 user_paused 分支保留任务，用户可恢复。

### 可选改进

`slot.send` 失败时回退 status 到 running（与 Serve 分支一致）：

```rust
PauseRoute::SendSession => {
    let handled = if let Some(slot) = state.pause_slot_of(&batch_id) {
        slot.send(PauseCmd::Pause).await
    } else {
        false
    };
    if !handled {
        if let Some(token) = state.cancel_token_of(&batch_id) {
            token.cancel();
        }
        set_running_status(&app, &batch_id).await;  // ← 回退 status
        publish(&app);
        return Ok(false);
    }
    publish(&app);
    pump_send_queue(app.clone()).await;
    Ok(true)
}
```

## Bug 3（🟡）：Live 恢复不检查 `slot.send` 结果

### 位置

`peer_transfer.rs:417-422` `resume_peer_transfer` Live 分支：

```rust
ResumeMode::Live => {
    if let Some(slot) = app.state::<PeerTransferState>().pause_slot_of(&batch_id) {
        slot.send(PauseCmd::Resume).await;  // ← 结果未检查
    }
    set_running_status(&app, &batch_id).await;
    Ok(true)  // ← 无条件返回 true
}
```

### 触发路径分析（2026-09 核验）

1. 用户 pause → status = paused，`token.cancel()` 触发引擎写 Cancel 帧；
2. 引擎 `Terminal(Cancelled)` 到达 → `apply_terminal` 检测 `user_paused = true` → 提前 return（不落终态）；
3. `drive_send_session` 事件循环在 Terminal 分支已 `unregister_pause`（941 行，不检查 epoch）；
4. 因此正常路径 pause_slot 会摘除，`peer_transfer_state_has` 返回 false → 走 Redial 分支。✅

**原审计假设的 epoch 不匹配场景不成立**——事件循环的 `unregister_pause` 在外层、不检查 epoch，任何 Terminal 事件到达都会先摘除 pause_slot。

**真正残留的缺陷**（低概率）：`slot.send(PauseCmd::Resume).await` 的返回值未检查。若 pause_slot 存在但命令通道已关（`cmd_rx` 被会话循环 `take_receiver` 取走后 channel 已 close，`send` 返回 false），则：

- 状态被无条件置回 running（`set_running_status`）；
- 返回 `Ok(true)` 假成功；
- 实际数据面未续流（无 Resume 帧发出）。

该场景要求 slot 存在但会话循环已死——与 Bug 1（dial 失败不摘 pause_slot）组合时可能出现：dial 失败后 pause_slot 残留，用户恢复时 `pause_slot_of` 命中但 `send` 失败。

### 修复建议

`resume_peer_transfer` Live 分支检查 send 结果：

```rust
ResumeMode::Live => {
    let slot = app.state::<PeerTransferState>().pause_slot_of(&batch_id);
    let sent = match slot {
        Some(slot) => slot.send(PauseCmd::Resume).await,
        None => false,
    };
    if !sent {
        // 会话已死：回落重新拨号路径（或保持 paused 待用户重试）
        return Ok(false);
    }
    set_running_status(&app, &batch_id).await;
    Ok(true)
}
```

或改用 `sessions` 表判活（比 pause_slot 更可靠，`register_session`/`unregister_session` 在 epoch 校验内调用）：

```rust
fn peer_transfer_state_has(app: &AppHandle, batch_id: &str) -> bool {
    app.state::<PeerTransferState>().session_is_current_any(batch_id)  // 新增：不校验 epoch
}
```

## Bug 5（🟢）：retry / Redial resume 把 `transferred_bytes` 归零

### 位置

- `peer_transfer.rs:805 retry_peer_transfer`：`task.dto.transferred_bytes = 0;`
- `peer_transfer.rs:454 resume_peer_transfer` Redial 分支：`task.dto.transferred_bytes = 0;`

### 场景

1. 任务已传到 50%（`transferred_bytes = 5000`，接收端 `.part` 保留 5000 字节）；
2. 用户取消 / 失败 → 用户点重试（或恢复）；
3. 新会话启动：引擎 `RateTracker::new()` 归零，`transferred_total = 0`；
4. 引擎发 `Offer`，接收端扫 `.part` 得 offset=5000，回 `StartFile{offset: 5000}`；
5. 引擎 `transferred_total += 5000`，`sync_base(5000)`，emit `Progress{transferred: 5000}`；
6. `update_progress` 更新 `transferred_bytes = 5000`。

在 step 3-6 之间（100~500ms），UI 显示 `0% 0 bytes`——**视觉断层**，但数据不丢（`.part` 是断点真源）。

### 修复建议

**方案 A（推荐）**：不重置 `transferred_bytes`，等 Progress 首帧自然对齐：

```rust
// retry_peer_transfer
task.dto.status = "pending".to_string();
task.dto.rate_bps = 0.0;
// 保留 transferred_bytes——引擎 Progress 首帧会重设为 offset
```

**方案 B**：UI 层暂存旧值，Progress 首帧到达后一次性对齐（需前端配合）。

方案 A 更简单，且与引擎 `sync_base(offset)` 语义一致。

## Bug 6（🟢）：RateTracker 对"对端静默暂停"无感知

### 位置

`packages/peer-net/src/transfer.rs:383-443 RateTracker`：

```rust
pub(crate) fn sample_at(&mut self, total_bytes: u64, now: std::time::Instant) -> f64 {
    let elapsed = now.saturating_duration_since(self.window_start).as_secs_f64();
    if elapsed < self.window.as_secs_f64() {
        return self.last_rate;
    }
    let delta = total_bytes.saturating_sub(self.window_bytes);
    let rate = delta as f64 / elapsed;
    ...
}
```

### 场景

对端异常静默（不发送 Pause 帧，也不发送 Data 帧，但连接未关闭）：

1. 本地发送端 `frame_rx.recv()` 分支拿不到帧；
2. `read()` 分支持续写数据到 TCP 缓冲（对端不 ACK 时 TCP 层背压，但应用层不知）；
3. `RateTracker::sample` 分子 = 新写入字节（少），分母 = 真实 elapsed（含空等时间）→ **速率虚低**；
4. UI 显示"传输突然变慢"。

### 判定

**设计如此，可接受降级**。RateTracker 不区分"没数据"和"发不出去"，这是纯发送视角。真正的对端主动暂停会走 wire Pause 帧回来，本场景是"对端异常静默"。

### 可选改进

在 `RateTracker::sample` 增加"空窗口"检测：若 `delta == 0` 且 `elapsed > 2 * window`，返回 0 或标记 `stalled`，前端显示"连接异常"而非"变慢"。

## Bug 7（🟢）：恢复后前 500ms 速率显示 0

### 位置

`transfer.rs RateTracker::sync_base_at`：

```rust
pub(crate) fn sync_base_at(&mut self, total_bytes: u64, now: std::time::Instant) {
    self.window_start = now;
    self.window_bytes = total_bytes;
    self.last_rate = 0.0;  // ← 归零
}
```

### 场景

1. 用户恢复 paused 任务 → Live 分支 `slot.send(PauseCmd::Resume)`；
2. 引擎 `select` 分支 `cmd = Resume` → 写 Resume 帧，继续推流；
3. 推流继续 → `sample` 检测 `elapsed < 500ms` → 返回 `last_rate = 0.0`；
4. UI 显示 "0 B/s" 直到窗口填够 500ms。

### 判定

**设计如此，可接受**。RateTracker 的窗口平均语义要求"新窗口从零起算"，否则恢复后的速率会包含暂停前的字节导致虚高。

### 可选改进

前端 UI 在 paused→running 转变时显示 "--" 或"..."（而非 "0 B/s"），提示"正在恢复"。需前端配合（`useTasks.ts` 或组件层）。

## Bug 8（🟢）：`set_pause_status` 只匹配 "running"

### 位置

`peer_transfer.rs:933-945`：

```rust
async fn set_pause_status(app: &AppHandle, batch_id: &str, paused: bool) {
    let state = app.state::<PeerTransferState>();
    {
        let mut inner = state.inner.lock().expect("peer transfer lock poisoned");
        if let Some(task) = inner.tasks.iter_mut()
            .find(|t| t.dto.batch_id == batch_id && t.dto.status == "running")
        {
            task.dto.status = if paused { "paused" } else { "running" }.to_string();
            task.dto.rate_bps = 0.0;
            task.dto.updated_at_ms = now_ms();
        }
    }
    publish(app);
}
```

### 场景

对端发 Pause/Resume 帧，但本端任务不在 running 状态：

- 本地 pending（尚未建立会话）：对端理论上不应发 Pause，除非对端状态错乱；
- 本地 paused（本地先暂停）：对端可能发 Resume 试图继续，本端应忽略（尊重本地暂停意图）；
- 本地 failed/cancelled（会话已终止）：对端可能迟到 Pause/Resume，本端应忽略。

### 后果

事件被静默丢弃，无日志。若发生上述错乱场景，排障困难。

### 修复建议

```rust
async fn set_pause_status(app: &AppHandle, batch_id: &str, paused: bool) {
    let state = app.state::<PeerTransferState>();
    {
        let mut inner = state.inner.lock().expect("peer transfer lock poisoned");
        let Some(task) = inner.tasks.iter_mut()
            .find(|t| t.dto.batch_id == batch_id)
        else {
            tracing::debug!(batch_id = %batch_id, "set_pause_status: task not found");
            return;
        };
        if task.dto.status != "running" {
            tracing::debug!(
                batch_id = %batch_id,
                current = %task.dto.status,
                paused,
                "set_pause_status: task not in running state, ignored"
            );
            return;
        }
        task.dto.status = if paused { "paused" } else { "running" }.to_string();
        task.dto.rate_bps = 0.0;
        task.dto.updated_at_ms = now_ms();
    }
    publish(app);
}
```

## 实现得好的地方（非缺陷，记录供后续参考）

1. **RateTracker 窗口平均**（500ms）：摊平采样抖动，`sample_at` 纯函数式便于单测；`sync_base` 处理续传基线跳变，防速率尖峰失真。
2. **读半独立任务**（`spawn_frame_reader`）：`read_exact` 非取消安全，通过 mpsc 通道只交付完整帧，pause/select 抢占不会吞半帧。
3. **`CancelToken::cancelled()`** 注册-再查双检：消除"取消发生在注册前"的丢失窗口；parent 链支持层次化（节点 stop 时子令牌一并触发）。
4. **`.part` 断点真源**：三类起点（target 完整 / target 尺寸不符 fail-fast / .part 续传），脏 `.part`（超过 meta.size）弃用，`truncate(offset == 0)` 清尾字节。
5. **`next_frame_handling_pause`**：等待控制帧期间同时消费本地 pause 命令 + 容忍对端 pause 帧，避免"等 StartFile/FileDone/BatchDone 时收到 Pause 帧被误判协议违规"（真机已验证的坑）。
6. **`apply_terminal` 的 user_paused 分支**：用户暂停触发的引擎 Cancel 不落终态，只归还并发槽 + 推进队列，任务保留可恢复。
7. **epoch 陈旧会话防护**：`session_is_current` 拦截取消后立刻重试时旧 Cancelled 事件覆盖新状态。
