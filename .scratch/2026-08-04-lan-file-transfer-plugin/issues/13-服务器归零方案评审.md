# 服务器归零方案评审

Type: review
Status: evaluated
Related: `docs/adr/0021-mobile-file-server-zero-transfer.md`

## 结论

- **传输速度：✅ 等价**——数据路径与现实现完全同构（手机↔桌面直连 HTTP，WS 不插入字节流），吞吐能力不受影响，单流打满 WiFi 的结论（01 选型已论证）原样成立。
- **功能替换：✅ 可全覆盖，但不是零成本置换**——三处真实差距需要专门设计与排期，最大的工作量在「手机端双向 HTTP client 传输栈」这个全新组件。

## 评审事实基础

- 传输加密当前是 **MVP 明文直通（`PassthroughCipher`），密钥协商未实现**——加密是"未来缝"，不是现实差距；未来接入 AES-GCM 时两端实现同源、与发送方向无关，不构成替换障碍。
- 手机端**不存在任何文件传输方向的 HTTP client 代码**（现有 reqwest 仅用于插件包下载 `/plugin/downloader.rs` 与服务端内部）——"手机端双向客户端栈"是新方案的主要新增量。

## 一、速度论证（硬指标）

核心前提：WS 只承载 intent/进度/取消元数据，大文件字节流全程走 HTTP，协议不变（Range 206 + session append + HEAD 指纹比对）。

| 方向 | 现状（手机 server） | 新方案（手机 client） | 吞吐对比 |
|---|---|---|---|
| 桌面加载手机文件 | 桌面 reqwest 拉手机 server | 手机 POST/PUT 桌面 session | 对称，直连 |
| 桌面推文件给手机 | 桌面 POST 手机 server | 手机 GET 桌面 + Range | 对称，直连 |
| 并发 | 手机接受 N 条连接 | 手机开 N 条 reqwest 会话 | 对称 |

- WS 控制面只传元数据（offset/速率），微秒级开销，不构成瓶颈。
- 唯一新增的速度风险：**手机主动发起 + 后台/Doze 限流**（长连接保活、持续吞吐可能被系统压制）——对策：前台服务 + 分块断点续传兜底，与 01 调研结论一致；且现状手机做 server 时同样依赖 App 进程存活，**风险同源，不是新引入**。

结论：速度硬指标满足，不存在 WS 中转或协议降级导致的吞吐损失。

## 二、全功能覆盖矩阵

| 功能 | 现状 | 新方案 | 覆盖 |
|---|---|---|---|
| 目录浏览 list | 桌面直连 GET | WS 请求 → 手机回 JSON（list 数据量小，毫秒级延迟） | ✅ 需新增 list 消息类型 |
| 下载（手机→桌面） | 手机 server GET Range | 手机 POST/PUT session | ✅ 语义平移 |
| 上传（桌面→手机） | 桌面 POST 手机 server | intent → 手机 GET | ✅ 语义平移 |
| 断点续传 | 两端 session/Range/HEAD 指纹 | 语义不变，接收端游标实现搬迁 | ✅ |
| 批/审批（ADR 0016） | 接收端宿主仲裁 | **触发点需重构** | ⚠️ 见差距 2 |
| 队列分类/传输历史 | 两端各维护 | 数据源从 server sessions 迁到 client 任务 | ✅ 可迁 |
| 通知栏应答（接受/拒绝） | PendingIntent 路由 | intent 到达 → 手机确认 → 执行 | ✅ 可保留 |
| 传输加密 | MVP 明文直通，密钥协商未实现 | 不变；未来 AES-GCM 时两端同源、方向无关 | ✅ 无新增差距 |
| 进度推送 | server 流式进度 | 手机回推 progress（WS） | ✅ 同模式 |
| 取消/暂停/重试 | 两端直连控制 | WS cancel / 重发 intent | ⚠️ 实时性依赖 WS 链路（局域网可接受） |

## 三、三处真实差距（非零成本）

1. **手机端双向 HTTP client 传输栈是全新组件**：现状手机只有 server 代码；新方案手机要新写 GET-client（下载落 SAF/MediaStore + 本地已写字节游标）和 POST/PUT-client（上传带 session 续传 + 重试编排）——这是方案里工作量与测试矩阵最大的部分。
2. **审批触发点重构（ADR 0016 联动）**：0016 的模型假设「发送方直打接收方端点 → 接收宿主仲裁」。新方案手机 pull 化后，手机既是执行者又是接收端，「批量请求→仲裁」在手机侧隐式化（用户已在手机上确认保存位置）；反之桌面收手机上传时仲裁仍完整保留。**需要把「接收端仲裁」按新发起拓扑重新落到两端**，否则 ask 模式防绕过（无批准批 ID 的 session 创建 403）逻辑会失配。
3. **桌面端从「数据驱动者」退为「协调者」**：桌面 UI 的进度/队列/速度显示全部依赖手机经 WS 回传——手机退后台/被杀则面板停更，回传滞迟则进度抖动。需要心跳/超时兜底 + 乐观更新，可靠性依赖面从「桌面进程」移到「手机进程 + WS 链路」。

## 四、建议落地顺序

按迁移不是置换：① 建手机端双向 client 传输栈 + 断点游标（先落地手机自主发起两方向，价值最高、风险最低）→ ② 建 intent 消息与手机 responder → ③ 桌面发起方向切 intent 驱动 + 审批触发点重构 → ④ 删 server.rs + actix 依赖，清理挂载生命周期。每步独立可验证，速度基准在 ① 完成后即可用现有测试矩阵回归。

**风险缓释**：前台服务常驻 + 心跳保活；Doze 按 01 的「暂停-待续传」策略；手机端多任务并发加优先级调度，避免多条大流互相饿死。

## 评审结论一句话

方案在架构与性能上经得起推敲：**可行，速度等价，功能全覆盖，但按「一次明确定范围的迁移」立项，核心新增量是手机端客户端栈与审批触发点重构**。
