# 自动任务图编排（auto-task 插件 DAG 演进，去 hooks）

Status: ready-for-agent

> 本规格由 auto-task 插件审核结论汇编而成，实现者无需再做重大架构决策。领域词汇与决策依据见 `CONTEXT.md`「自动任务 (Auto Task)」节、`docs/adr/0004-task-episode-model-command-filter.md`、`docs/adr/0003-plugin-host-session-create-timer.md`、`docs/adr/0022-plugin-host-interface-primitive-boundary.md`。
>
> 核心结论：把 auto-task 从「常驻交互式会话 + hooks 推断状态」演进为「任务图（DAG）编排 + 进程级执行」。任务边界从「agent 会话内的一次轮次」扩展到「一个非交互 agent 进程」，进程退出码（exit code）成为权威终态，hooks 从编排链路的必要条件降级为交互式场景的可选增强。

## Problem Statement

当前 auto-task 插件依赖四套 agent 集成脚本（Claude Code hooks / pi 扩展 / opencode 插件 / Codex hooks）把任务状态从 agent 内部「上报」回插件。这套机制存在结构性脆弱：

1. **状态是推断而非观测**：任务何时完成由 hook 事件序列猜出，插件为此堆叠了时序保护、重复推送幂等、subagent 退出回声、`background_tasks` 版本差异判断等大量补丁，复杂度与维护成本持续上升。
2. **改写用户项目文件**：会话创建时向 `.claude` / `.pi` / `.opencode` / `.codex` 写入配置与脚本，多会话/多实例并发时存在误删竞态，且污染用户仓库。
3. **依赖 agent CLI 的实现细节**：每个 agent 的 hook 事件语义不同且随版本漂移，四套脚本各自维护一份状态机，语义同步靠人工。
4. **单终端单任务串行**：一次只能驱动一个 prompt，无法表达「任务 A 完成后并行跑 B、C，再汇总到 D」这类依赖关系。

用户真正想要的是：**定义一组有先后依赖的任务，系统可靠地按依赖顺序执行它们，把上游结果传给下游，失败可重试、可断点续跑，全程无需往项目里塞任何 hook 脚本。**

## Solution

引入**任务图 (Task Graph)** 编排能力：用户把多个任务组织成一张有向无环图（DAG），每个节点由独立的非交互 agent 进程执行，进程退出码即节点终态，节点结果（输出文件/结构化摘要）经模板变量注入下游节点。

- **任务图是现有任务队列与定时自动任务的超集**：单链无分支的图等价于今天的队列；图可绑定触发时刻（取代定时自动任务的一次性触发），也可手动/入队触发。
- **节点执行 = 非交互进程**：宿主已有 `process_run` 原语（异步 spawn、stdout/stderr 落盘、`on_process_done` 回调携带 exit code、进程组 kill、超时、审计日志）。节点跑 `claude -p "prompt"` / `codex exec` / `opencode run` / `pi -p`，**任务边界 = 进程边界，exit code 是权威终态，hooks 在编排路径上被彻底移除**。
- **交互式场景不受影响**：用户在人机对话（PTY 会话）里的体验保持现状；hooks 若保留，仅作移动端「忙碌/空闲」粗粒度指示，不再承载调度信号。
- **编排引擎全部落在插件层**（遵守 ADR-0022）：宿主零新增能力，只复用既有的进程原语；拓扑排序、就绪计算、状态机、结果传递、重试/断点/并发全部是插件自持逻辑，用插件数据库持久化。

## User Stories

1. 作为用户，我希望能把多个任务定义成一张有依赖关系的图（A 完成后才能跑 B、C），这样系统能自动按正确顺序执行，而不是我手动一个接一个提交。
2. 作为用户，我希望任务图支持并行节点（依赖同一前驱的多个节点同时执行），这样互不依赖的任务能一起跑，缩短总耗时。
3. 作为用户，我希望每个图节点作为一个独立进程运行，进程正常退出即视为成功，这样任务状态由客观事实（退出码）决定，而不是猜测。
4. 作为用户，我希望上游节点的执行结果能自动注入下游节点的 prompt（如"基于上一阶段结论继续"），这样多阶段任务能串成一条流水线。
5. 作为用户，我希望节点能约束输出为结构化 JSON，并按字段把结果传给下游，这样下游能精确消费上游产物而非全文粘贴。
6. 作为用户，我希望某个节点失败后可以按配置自动重试，这样偶发失败（网络抖动、限流）不会让整张图作废。
7. 作为用户，我希望节点可以配置超时时间，超时自动终止该进程并标记失败，这样失控任务不会无限占用资源。
8. 作为用户，我希望图执行中断（应用退出、进程崩溃）后重启能从失败/未完成的节点继续，而不是从头重跑，这样长任务不会白费。
9. 作为用户，我希望可以取消一张正在运行的图，取消时连同所有正在运行的节点进程一并终止，这样我不需要逐个去杀进程。
10. 作为用户，我希望在定义图时选择「某节点失败则跳过其下游」，也能选择「立即中止整张图」，这样我能按任务语义决定失败传播策略。
11. 作为用户，我希望整张图不需要向我的项目写入任何 hook 配置或脚本文件，这样我的仓库保持干净，也不会因多会话并发被误删配置。
12. 作为用户，我希望任务图能绑定一个触发时刻，到点自动新建执行实例并跑完整张图，这样它能替代现有的定时自动任务。
13. 作为用户，我希望现有的普通任务队列（FIFO）继续可用，因为它是任务图在"单链"场景下的自然形态。
14. 作为用户，我希望在移动端也能看到任务图的整体进度（哪些节点完成/运行中/失败），这样我远程就能掌握编排执行情况。
15. 作为用户，我希望每个节点执行过程有独立的输出日志可查，这样排障时能定位到具体节点而非整张图。
16. 作为用户，我希望任务图可以复用现有会话配置里的执行 agent 选择，这样不同节点可用不同 agent 执行（如分析用 Claude、生成用 Codex）。
17. 作为用户，我希望节点支持携带环境变量与工作目录，这样执行上下文与任务定义解耦。
18. 作为用户，我希望任务图定义可以保存并重复触发，这样常用编排流程只需定义一次。
19. 作为用户，我希望每次图触发都生成一份独立的运行记录（含每节点状态与时间线），这样历史可审计、可对比。
20. 作为用户，我希望任务图在无人值守执行时不需要任何人守在终端前点击确认，这样真正的自动化才成立。
21. 作为用户，我希望手动触发图执行时也能看到实时的节点状态流转，这样我能判断当前跑到哪一步了。
22. 作为用户，我希望节点失败信息（退出码、超时标记、输出摘要）被记录并可回看，这样我知道为什么失败而不用重现现场。
23. 作为用户，我希望任务图的执行不依赖桌面端 webview 存活（窗口关闭只进托盘），这样长编排任务不会因关窗而中断。
24. 作为用户，我希望定义图时能指定节点的重试次数与重试是否重新生成依赖输入，这样重试语义可控。

## Implementation Decisions

### D1. 执行模型切换：节点 = 非交互进程（核心决策）

每个图节点通过宿主 `process_run` 原语执行一个非交互 agent 进程。进程 `exit code == 0 && !timed_out` 判为成功，否则判为失败。进程退出是权威终态，不存在"状态推断"。宿主 `on_process_done` 回调（携带 run_id、exit_code、timed_out）驱动节点状态收敛，属事件推送而非轮询。

- 非交互进程不继承交互式会话的上下文，节点之间通过「结果传递」而非「记忆延续」衔接——这是任务图编排的确定性语义，取代现有「上下文清理」机制（该机制在 DAG 路径上自然消失）。
- 各执行 agent 的非交互入口（启动参数、退出码语义、流式输出）收敛到一个薄的执行适配层，只负责"拼启动参数 + 读退出码 + 定位输出文件"，不解析任何生命周期事件。

### D2. 编排引擎位置：插件层，宿主零新增能力

遵守 ADR-0022（宿主接口只暴露无业务语义的基础能力）：宿主现有的 `process_run` / `process_kill` / `on_process_done` 已是满足需求的引擎原语（spawn/kill/输出落盘/退出码），DAG 的图模型、拓扑排序、就绪计算、状态机、结果传递、重试/断点/并发编排全部在插件内实现，用插件数据库（plugin_db）持久化。宿主无需任何 ABI 变更；仅需插件 manifest 增加 `process:run` 权限声明。

### D3. 数据模型（插件自管 DB，来自原型讨论）

图定义与运行实例分离（与「计划任务」插件"任务定义 / 执行记录分离"同源思路）：

- **图节点定义表**：节点 id、所属图 id、任务发起输入（支持模板变量）、执行 agent、依赖节点列表（JSON 数组）、重试次数、超时毫秒、排序位置。
- **图运行实例表**：每次触发为整张图的每个节点生成一行运行记录（幂等 + 断点续跑）。字段：运行 id、图 id、节点 id、状态、宿主进程 run-id、退出码、输出文件路径、已尝试次数、起止时间。

运行态落库，应用重启后按"仅非终态节点"恢复执行（断点续跑）。

### D4. 节点状态机（来自原型讨论）

```text
pending ──(所有依赖节点 succeeded)──▶ ready ──(process_run 返回 run-id)──▶ running
running ──(exit 0 且未超时)──▶ succeeded
running ──(exit != 0 或超时，attempts 未耗尽)──▶ ready（重试）
running ──(exit != 0 或超时，attempts 耗尽)──▶ failed
failed ──(失败传播策略=跳过下游)──▶ 下游节点 skipped
running ──(用户取消)──▶ cancelled（连带 kill 进程组）
```

图整体终态 = 所有节点进入 `succeeded / failed / skipped / cancelled` 之一。

### D5. 结果传递契约

节点输出文件（process_run 落盘产物）是节点的可寻址结果。下游节点的任务发起输入支持模板变量引用上游结果：

- 全文引用：注入上游输出全文（默认）。
- 结构化引用：节点约束输出为 JSON，插件解析后按字段引用（如引用某节点输出的 `summary` 字段）。
- 未解析的引用在提交前校验失败（图定义错误早暴露，不等到运行期）。

### D6. 失败传播、重试与取消

- 失败传播策略按图配置：`fail-fast`（任一节点失败即不再启动新节点，运行中节点照常收敛）或 `continue`（跳过仅依赖失败节点的下游）。
- 节点级重试：按节点配置的次数与超时独立生效；重试复用同一运行记录行（attempts 递增），不新建行。
- 取消：遍历运行中节点调用 `process_kill`（进程组整树终止，宿主已实现），节点置 cancelled。

### D7. 与现有队列 / 定时自动任务的关系

- 任务队列 = 单链（每个节点只有一个后继）任务图的退化形态。演进后，队列与图共用同一执行引擎；现有队列交互（添加/移除/排序/自动执行开关）作为图编辑器在单链下的简化视图保留。
- 定时自动任务 = 绑定触发时刻 + 指定会话配置的一次性图执行。现有"新建会话再注入 prompts"的路径迁移为"到点触发图运行"，复用同一执行引擎，移除对 `session_create` + `Created` 事件匹配 + 首轮下发兜底等交互式专属机制的依赖。
- 迁移采用并存过渡：旧路径（交互式会话 + hooks）与图执行路径并存，直到图路径覆盖队列与定时两类场景后再退役旧路径。

### D8. hooks 的去留

编排路径（图节点）完全不依赖 hooks。交互式路径（PTY 人机对话）的 hooks 若保留，仅作状态指示（忙碌/空闲）供移动端显示，不再作为调度信号源；现有交互式路径的状态同步时序保护逻辑可在图路径稳定后退役。四套集成脚本的"任务状态上报"职责随编排迁移逐步废弃。

### D9. 事件与移动端同步

复用现有 SyncEvent 三通道（消息总线 / emit_event / broadcast_sync）广播图级与节点级状态变更。移动端新增「任务图进度」视图：以图运行实例为粒度展示节点拓扑与实时状态，不做编辑（编辑为桌面端能力，与现有预设/预存任务的分工一致）。

### D10. 权限面变化

manifest 权限增加 `process:run`（宿主已实现门禁与逐次审计日志）。现有 `terminal:input` / `terminal:observe` 等在编排路径上不再需要，但交互式路径仍依赖，暂保留；待旧路径退役时同步收敛权限。

## Testing Decisions

### 好测试的标准

只测外部行为，不测实现细节：给定一张图定义 + 一组完成事件序列，断言节点状态流转与下游触发顺序；不断言内部用什么数据结构存图、用什么 SQL 查询。执行侧通过注入 fake 执行器记录"应启动什么进程、以什么顺序、携带什么参数"，不真正 spawn 进程。

### 测试接缝（seam）

**唯一主接缝 = 图编排器的公共接口**（提交图 / 上报节点完成 / 取消图）。拓扑排序、就绪集合计算、状态机转换、结果模板渲染全部收敛为该接口背后的纯逻辑，直接做 Rust 单元测试；执行引擎通过一个薄的执行器抽象（对 process_run 的隔离层）注入 fake 实现完成调度行为测试。宿主进程集成行为复用宿主侧既有测试，不重复覆盖。

### 被测模块

- **拓扑与就绪计算**（纯函数）：环检测、依赖解析、就绪集合随完成事件增量的正确性。
- **状态机转换**：D4 状态机的全部合法迁移与非法迁移拒绝（表驱动测试）。
- **结果模板渲染**：全文引用、结构化字段引用、未解析引用报错。
- **执行调度**（fake 执行器）：失败重试、超时、取消、fail-fast / continue 传播、断点续跑（从运行实例表恢复非终态节点）。
- **执行适配层**：各 agent 非交互启动参数与退出码映射（纯函数，表驱动）。

### 测试先例（prior art）

- 插件 Rust 层纯函数测试：现有 `agent.rs`（agent 识别、命令过滤的断言式单测）与 `hooks.rs`（配置合并/版本标记的纯函数测试）同模式。
- 宿主进程原语集成测试：`host_impl/process.rs` 既有 spawn/kill 集成测试（真实 spawn echo、进程组 kill），图执行引擎不在插件侧重复此类进程级测试，宿主能力由宿主测试兜底。
- 状态机表驱动测试：现有调度状态机的测试风格可迁移。

## Out of Scope

- **交互式会话的 hooks 重写**：本规格只移除编排路径的 hooks 依赖；交互式 hooks 的降级/退役是图路径稳定后的独立任务。
- **移动端图编辑**：移动端只读展示图进度，图的定义/编辑是桌面端能力。
- **节点结果持久化语义（缓存跳过）**：同输入复用历史输出（memoization）不在本规格内。
- **多工作会话池 / 跨图并发调度**：并发仅限单图内无依赖节点；多图并发的资源调度与配额不在本规格内。
- **与计划任务插件（com.bedcode.scheduler）的整合**：两者触发机制（cron 通用任务 vs 图编排）保持独立，统一触发抽象不在本规格内。
- **token 用量回填**：任务记录的 input_tokens / output_tokens 列仍预留不解析（见 ADR-0004），图执行不改变此现状。
- **核心宿主 ABI 变更**：本规格坚持宿主零新增能力；任何需要新原语的能力（如跨图调度）均推迟。

## Further Notes

- 迁移策略建议分阶段：先以「单链图」替换定时自动任务的执行路径（`session_create` → `process_run`）验证进程级执行的可行性，再引入图模型与拓扑调度，最后退役旧 hooks 编排路径。
- 执行适配层是剩余的外部依赖面（各 agent CLI 的非交互 flag 与退出码语义），比现有四套 hook 脚本简单一个数量级，因为它只关心进程启动与退出，不解析生命周期事件。
- 任务图的引入不改变 ADR-0004 的任务记录语义：图节点成功/失败仍产生任务记录（来源标记为图执行），图节点与任务记录是"执行单元"与"归档视图"的关系，与现有"队列项 = 任务记录同一实体"保持一致。
- 上下文清理（`/clear`）机制在 DAG 路径上消失后，交互式路径仍需要它；相关 agent profile 字段与调度分支在旧路径退役前保持不变。
