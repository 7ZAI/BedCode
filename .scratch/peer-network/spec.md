# Spec: 对等网络与文件传输迁移

Status: ready-for-agent

词汇表依据：CONTEXT.md「对等网络」节（对等网络/对等节点/直连/节点身份/可信对端/首次连接确认/节点发现/在线/能力通告）及改写后的「文件传输」节。决策依据：docs/adr/0001（传输栈）、0002（信任模型）。

## Problem Statement

BedCode 目前的文件传输只能在移动端与桌面端之间进行，且连接完全依附于终端主机链路：桌面端是恒定中心，移动端之间即使处于同一 WiFi 也无法互传。用户在局域网内拥有多台安装了 BedCode 的设备（多台手机、手机+桌面、甚至双桌面），却无法让它们两两直接交换文件；传一个文件必须以完成整套终端配对为前提。

## Solution

在宿主两端内置一套对称的**对等网络**：任意节点在同一网络内通过 mDNS 互相发现、展示能力通告，经一次应用内确认建立逐对信任后即可直连，双向传输文件——浏览并拉取对方的共享目录、向对方推送文件、一次操作扇出发送给多个接收方。文件传输插件从宿主 intent 协调管线整体迁移到该层；终端远程控制链路原样保留。

## User Stories

### 发现与在线

1. 作为任一端用户，我要在设备列表中看到同一网络内所有正在运行 BedCode 的节点（设备名 + 短指纹），以便确认即将连接的是哪台设备。
2. 作为任一端用户，我想看到附近节点是否具备文件传输能力（能力通告），以便知道谁能与我互传。
3. 作为任一端用户，我希望设备列表来自发现缓存、随时可查，以便不必先建立连接才知道附近有谁。
4. 作为移动端用户，我希望 App 退到后台后我的在线状态如实反映 mDNS 可见性，以便对方不会向已离开的设备发起传输。

### 信任

5. 作为发起方，我想点击发现列表中的设备发起连接，以便与其建立传输关系。
6. 作为被连接方，陌生节点首次连接我时我要收到应用内确认弹窗，以便决定是否信任它。
7. 作为被连接方，拒绝确认后我希望本次连接失败、对方可稍后重试，以便保留考虑余地。
8. 作为任一端用户，已建立信任的对端再次连接时不再弹任何窗，以便日常互传零打扰。
9. 作为任一端用户，我可以在设置中查看全部可信对端并撤销其中任意一个，以便随时收回权限；撤销后对方重连需重新确认。
10. 作为已有终端配对关系的用户，我的手机与桌面在对等网络中应自动互信、免首次确认，以便不为传文件重复做一遍配对。
11. 作为任一端用户，未信任的已发现节点应无法向我发送传输请求或浏览共享目录，以便免受同网陌生节点骚扰。

### 传输

12. 作为发送方，我可以向单个可信对端发送一个或多个文件，以便分享内容。
13. 作为发送方，我可以一次选择多个接收方扇出发送同一批文件，以便不必重复操作；各接收批相互独立、成败互不影响。
14. 作为接收方，收到的传输批按我的接收策略放行：每次询问（默认，接受全部/拒绝全部、超时自动拒绝）、直接接收、直接拒绝。
15. 作为接收方，询问弹窗应展示批内文件清单与总大小，以便知情决策。
16. 作为任一端用户，传输中断后重试应从断点（接收端已写字节）续传而非从头开始，以便大文件不白传。
17. 作为发送方，我可以随时取消进行中的发送任务。
18. 作为接收方，我可以拒绝待批准的请求、取消进行中的接收。
19. 作为任一端用户，我想看到每个传输任务的实时进度、速率与状态，以便了解传输情况。
20. 作为接收方，收到的文件统一落入本机下载目录（移动端 MediaStore.Downloads、桌面端 Downloads\BedCode\），以便在系统文件管理器中找到它们。
21. 作为桌面端用户，我可以在设置中更换接收落点文件夹，以便按自己的磁盘规划存放。

### 浏览与暴露

22. 作为任一端用户，我可以浏览可信对端的共享目录并拉取其中的文件，以便按需获取而不是等对方推送。
23. 作为移动端用户，我可以用系统目录选择器添加/移除共享目录条目，授权持久化、重启后仍有效；app 私有下载目录作为免授权条目始终可用。
24. 作为桌面端用户，我可以把任意文件夹设为共享目录暴露给可信对端，以便与手机对称地提供文件。
25. 作为任一端用户，我的共享目录对可信对端恒只读，以便对方永远无法改写我的文件。

### 记录与兼容

26. 作为任一端用户，全部终态传输任务（完成/失败/被拒/取消）进入传输历史、封顶滚动淘汰、可一键清空，以便事后追溯。
27. 作为任一端用户，远程终端控制功能应完全不受本次改造影响，以便既有工作流不变。
28. 作为任一端用户，升级到新版后既有的传输历史与本机配置应保留，以便无缝过渡。

## Implementation Decisions

1. **通用层归属**：对等网络是宿主两端内置的核心服务，不是插件私有物；file-transfer 是首个上层消费者，未来投送/同步等能力挂载其上。
2. **拓扑**：直连 mesh，无中心协调者；不做中继路由，只服务直连可达的对端。扇出发送落地为 N 条相互独立的传输批，「群发」仅是界面编排概念，无组会话实体。
3. **信任模型**（ADR 0002）：两级信任。未信任节点纯可见零交互；首次连接由被连接方应用内弹窗确认（不强制扫码）；信任关系逐对、双向、持久（本地存对方节点 ID）、设置中可撤销。节点身份 = Ed25519 长效密钥对，节点 ID 即公钥指纹，重装即新身份。已有终端配对的设备对免确认自动互信。
4. **新旧链路边界**：文件传输整体迁移到对等网络，`Message::FileService` intent 协调管线与旧 announce 机制在切换版本中删除；终端控制链路（mDNS 发现、配对码/QR/生物认证/JWT、WS）原封不动；桌面端同样运行节点服务，天然获得桌面↔桌面传输。
5. **传输栈**（ADR 0001）：对称化现有 actix-web 4 HTTP+WS 栈。单 TCP 端口承载数据面（HTTP，含 Range 断点续传与上传 session 语义）与控制面（同端口 WS upgrade）。TLS 用 rcgen 从节点 Ed25519 密钥生成自签证书，自定义 rustls verifier 校验对方证书指纹 = 节点 ID 且在可信列表内才放行；首连确认发生在 TLS 握手之后的应用层。
6. **实现种子**：以 git 标签 v2.0.0 中移动端 actix 服务端代码为种子恢复改造（server/upload/auth/cipher/announce/notify 一族模块当时完整走通双向上传下载），剥离其对宿主 WS 与 Announce token 的依赖，替换为对等信任层；两端同框架无冲突。
7. **节点发现与在线**：独立 mDNS 服务类型，与终端链路的 `_bedcode._tcp` 并存互不感知；每节点同时广播自身并浏览他人。记录 TXT 载荷含设备名、协议版本、能力位图（文件传输为首 bit）。在线 = 发现记录可见；连接按需建立（点击连接或发起传输时握手），空闲超时自动断开；节点列表来自发现缓存。Android 收多播需 MulticastLock。
8. **共享目录**：两端对称同构——移动端 SAF URI 条目（持久授权）+ 私有下载目录特殊条目；桌面端为用户选择的文件夹。仅可信对端可浏览，恒只读。
9. **下载目录**：移动端默认 MediaStore.Downloads（失败回退 app 私有目录）；桌面端可配置文件夹，缺省 `Downloads\BedCode\`，逐次不弹窗。
10. **接收策略**：维持全局单开关粒度（每次询问默认/直接接收/直接拒绝），不区分对端；与信任层正交。可信对端免询问白名单留作后续选项。
11. **共享 crate**：新建 `packages/peer-net`（crate 名 `bedcode-peer-net`），两端 src-tauri 以 path 依赖引入；节点服务（监听/TLS 身份/发现/信任存储/传输会话引擎）全部在其中，不在某一端长出来再搬。
12. **迁移节奏**：四阶段并行开发、单点切换、同版删除——Phase 1 恢复+去 host 化+身份层；Phase 2 mDNS 发现模块；Phase 3 插件前端切换（发现列表/信任 UI/传输页）；Phase 4 功能对齐验收后删除旧管线。开发窗口内旧链路冻结（只修不加）。
13. **i18n**：新增 UI 文案同步 zh-CN 与 en；composable 无中文硬编码。

## Testing Decisions

好测试只断言外部行为，不测实现细节。三条接缝（已与开发者确认）：

1. **主接缝（唯一新增）：双节点对打 harness** —— 在进程内起两个真实节点实例、回环端口互指，从节点公共 API 最高处驱动全部行为：首连闸门（未信任必须出确认、接受后落库、重拨静默）、身份拒止（指纹不在可信列表则 TLS 拒绝）、传输批生命周期（协商→接收策略三分支→进度→取消）、断点续传（中途掐断后续传自接收端已写偏移）。mDNS 多播在 CI 不可靠，发现的测试入口是向节点注入一条已发现记录——与 mdns 守护回调喂给主流程的是同一通路；真实多播只留冒烟测试、不进断言。
2. **复用缝：无头纯函数单测** —— 批状态机校验、TTL 清扫等纯逻辑沿用移动端 file_service 现有惯例（模块不依赖 tauri/actix，独立单测）。
3. **复用缝：前端 vitest** —— 插件前端的设备列表/信任管理/传输编排 composables 与 stores 走现有 vitest 套件（统一用 test:run 一次性执行），只测编排逻辑不测渲染。

Prior art：桌面端既有集成测试风格（broadcast_shutdown、http_auth_biometric、ws_auth_rules 等 tests/ 文件）；移动端 file_service 纯函数模块与其单测；bedcode-desktop 前端 vitest 套件。

## Out of Scope

- 中继路由、跨子网手动 IP 直连（后续版本）
- WebRTC / libp2p / 公网真 P2P（另一战场，见 ADR 0001 结尾；届时另立 ADR）
- 可信对端自动接收白名单（v1 接收策略保持全局粒度）
- 与 LocalSend 等第三方工具互操作
- 终端控制链路的任何改动（认证方式、隧道、会话）
- 首连强制扫码
