## Comments

### 2026-09-19 实施落地

**1. `plugins/session/rust/src/pairing/`（语义落插件）**

- 四模块自 devices **逐字节搬入**（`code.rs` / `qr.rs` / `jwt.rs` / `keys.rs` + `mod.rs` 重写），仅改文件头归属字样。依赖同批锁定（`hmac 0.12` / `sha2 0.10` / `base64 0.21` / `hex 0.4` / `getrandom 0.4`）——窗口内两份副本若因依赖漂移行为分叉，票 06 删旧即丢变更。
- **expand 步的重复副本（有意的临时态）**：devices 的 `policy`（auth-policy 导出）依赖 `pairing::jwt` 与 `trust::store`，`trust` 依赖 host-storage 属主命名空间。若本票把 pairing 从 devices 摘走，要么 `policy` 悬空，要么把票 05 的 trust 搬迁提前做掉。故本票**只搬入不搬出**：pairing 语义在会话中心生效并被桥接调用，devices 副本作为 `policy` 的编译依赖暂留，票 06 随 devices 整体退役一并删除。判据：改这两份副本的任何语义必须同步两处，否则退役即漂移。
- 互调 api 面八项（`#[plugin_api]` + `#[api(...)]`，宏编译期与 `plugin.json` 比对）：`pairing-code-{generate,status,verify,clear}` + `qr-code-{generate,status,verify,clear}`；`permissions` 追加**仅** `auth`（host-auth secret-store）。
- `session.status` 命令的 `skeleton: true` → `domains: ["pairing"]`（骨架期结束的自我声明）。
- `pairing/jwt.rs` 加模块级 `#![allow(dead_code)]` + 理由：签发/验签的生产消费方（`policy` 裁决）随票 05 才搬入，本票只有 `now_secs` 与对照向量被用；票 05 后应收窄到具体项。
- **未搬命令面**（`session.pairing.*`）：生产消费方是宿主桥接（走 api 面），devices 那份 `devices.pairing.*` 命令的用途是闭环测试便利。P3 前端经 `plugin_invoke` 真正需要时再按实际语义追加，避免无消费方的审计噪音。

**2. 宿主桥接改指（`src-tauri/src/utils/auth/auth_center.rs`）**

- 拆成**两个目标 + 两个锚点**，各自探活、互不牵连（D7 域隔离）：
  - `SESSION_PLUGIN_ID` / `SESSION_PAIRING_MARKER_API`（`com.bedcode.session.pairing-code-status`）→ 配对码四条 + QR 三条桥接函数的门与转发目标；
  - `AUTH_CENTER_PLUGIN_ID` / `AUTH_CENTER_MARKER_API`（锚点由 `pairing-code-status` 改指 **`list-trusted-devices`**）→ `enforce_connection_policy` 的 capability 导出目标与 `sync_pairing_*` 镜像同步目标。锚点换到 trust 域 api 是刻意的：配对面 api 即将随 devices 退役，用「配对码状态」探「trust/policy 是否可用」是借来的判据，devices 侧删 pairing 时会静默变假 → policy 永久从宽（fail-open）。
  - 两常量收敛为一个的动作记在票 05（trust 搬迁）+ 票 06（退役）。
- 宿主命令面 / server 端点**零改动**：`commands/system.rs`（配对码四）、`commands/qr.rs`（QR 三）、`controllers/auth_controller.rs`（pairing / verify / qr-connect）本就调桥接层，改指由常量完成——这正是票 11 桥接层留的接缝。TTL get/set 仍留宿主 DB 设置域（spec D3）。
- `log_fallback` 文案去「auth center」专指（`api = %api` 字段已带目标），`call_api` 的 5s 超时与降级形状不变。

**3. 对照测试抓出的真实分叉（本票最有价值的一条）**

双轨矩阵里宿主轨的 QR 拒绝原因是 `AppError::Auth(..).to_string()` = `"Authentication error: Invalid QR token"`，插件轨（guest 无 AppError）是 `"Invalid QR token"` → 逐字段比对直接红。二者只在「子串分类未命中 → 原文透传给用户」这条边上可见，但它是双轨等价的硬分叉。修正：桥接层新增 `qr_reject_reason()`，降级轨剥 `Auth` 前缀、其余变体保留完整 Display（不吞上下文）。全仓无消费者依赖该前缀（grep 命中仅 `system/error.rs` 的 `#[error]` 定义本身）。
