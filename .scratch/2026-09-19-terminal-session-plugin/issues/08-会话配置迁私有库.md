## Comments（2026-09-20 开工：设计决策与风险排期）

### 1. 开工前实测的关键风险（必须先处置，否则票 08 会打挂会话创建）

内核**会话启动路径直接读主库配置表**：`session/session_manager.rs:296-302`（`create_session_with_source_and_id`）→ `self.storage.get_config(config_id)`，取不到即 `Config not found`。也就是说**配置真源一旦只活在插件私有库**，任何「迁移后新建/修改的配置」都无法启动会话——而票 09（`create-with-spec`，把 launch spec 交给内核）才是解除该依赖的那一步，票序上晚于本票。

### 2. 采用的处置（本票设计决策）

**插件私有库 = 真源；主库 `session_configs` = 宿主维护的派生投影（镜像），仅供内核 PTY 启动路径消费，票 09 落地后删除。**

- 语义归属：产品语义（校验、排序、展示组织、迁移）全在插件侧；主库那一份不再被任何产品路径读作真源，只作为「引擎输入投影」存在。
- 与票面「主库旧表本期只读保留（contract 留给收尾票）」的关系：**读侧**契约不变（仍是只读的投影、无人再把它当真源）；**写侧**由宿主桥接层在转发成功后同步投影（单写者 = 宿主，插件不碰主库——插件也碰不到：主库表名强制 `plugin_id_` 前缀，`host_impl/database.rs` 前缀校验会拒）。
- 这样本票**不需要等 09**：前端/移动端可见行为、会话启动路径全部不变，即可完成「真源下沉 + 命令薄转发」。
- 反对的备选：把 09 提前（`create-with-spec` 先落，内核不再读配置）——票序倒置且 09 的 spec 契约（launch spec-json）本票无消费方，收益为负。

### 3. 迁移设计（一次性 + 幂等，两者都成立）

- **一次性**：插件私有库内以元数据键作版本戳（范式同宿主 `peer_migration.rs:52-55` 的「键存在性 = 已迁移」），迁移成功后写 `config.migrated_at`；**再激活不重跑**——否则「插件侧删除某配置 → 下次激活又被 legacy 行重新导入」会造成删除无法生效。
- **幂等**（可对同一旧库重复执行且结果一致）：迁移逐条按 `id` 判存在（`INSERT OR IGNORE` 语义），marker 之外的重复执行也不会产生重复行；marker 写入失败/进程崩溃后重跑同样收敛。
- **旧数据来源**：插件不能 SQL 主库（前缀隔离），因此经本规格票 07 新增的 `host-session.config-list`（取 id 清单）+ `config-get`（取全量行）读取——这正是票 07 与票 08 的接缝，也回答了「票 07 的配置面在 08 之后是否还有消费者」：**有，作为插件访问 legacy 主库配置的唯一合法通道**（迁移期 + 宿主降级轨）。
- 迁移失败：activate 返回 Err（D7：任一步失败落 Degraded，不静默 Activated）。

### 4. 宿主命令薄转发（4 个命令签名/返回形状不变）

`commands/session_config.rs` 的 `create/list/get/delete/update` → 新增桥接（模式同 `utils/auth/auth_center.rs`：探活锚点 + JSON-RPC 互调 + 降级 + `warn` 留痕）：

| 命令 | 插件可用 | 插件不可用（降级） |
| --- | --- | --- |
| list / get | 转发插件（真源） | 读主库投影（迁移前行为，无单点） |
| create / update | 转发插件 → 成功后宿主写主库投影（保持内核启动路径可用） | 仅写主库（迁移前行为） |
| delete | 转发插件 → 成功后删主库投影 | 仅删主库 |

同步事件（`ConfigCreated/Updated/Removed` 广播给移动端）保持由宿主发出，事件形状不变。
