### 2. 三处当场裁决

**① 旧 HTTP 前缀：保留别名兜底，本票不切断。**

| 维度 | 保留（选定） | 切断 |
| --- | --- | --- |
| 改动量 | 零（票 16 已落 30 行：一张别名表 + 一个纯函数 + 4 用例） | 删该 30 行 + 4 用例 |
| 移动端 | 零改动继续可用（M1 延后触发） | 任务面板 7 个调用面当场 404（M1 提前） |
| 已部署 hook 副本 | 模板版本 bump 后下次注入自动改指；窗口期由别名表兜住 | 窗口期内状态推送**静默丢失**（agent 不报错，只是不再同步）——比 404 更难排查 |
| 审计歧义 | 「谁在应答」需两条日志字段区分（`plugin_id` 属主 / `requested_plugin_id` 请求前缀）；旧路径退役后仍可路由，易误判旧插件还在 | 无歧义 |

歧义代价已在 `plugin-http-endpoint-trust.md` §3 记由，**切断时机并入移动端适配专项**：
那时改移动端 api 基址一处 + 同批删宿主别名表，两侧一起清零。

**② `manifest-gen` 命令面口径取 ①（人工裁剪优先）。** 判据是宿主侧事实：
`plugin_invoke` **不校验**命令是否声明，本插件前端今天就在调 21 条未声明臂
（`session.config.*` / `session.pairing.*` / `session.devices.*` …）——所以
`invoke_command` 的臂集合 ≠ 可调面 ≠ 用户可见命令面。方案 ②（56 条全量声明）会把
宿主桥接与闭环调试臂 advertise 成产品命令，且与票 13–15 四处手工 pin 全面冲突。
选 ①：manifest 已声明 commands 即视为人工裁剪面，生成器只报差集。
臂数与本票实测：今天跑 `node packages/plugin-sdk-desktop/bin/cli.js manifest`
（release 路径调的同一个 `generateManifest`）对 `com.bedcode.session` 报
「未声明的 `invoke_command` 臂 28 个」，加上已声明 28 条 = **56 臂**。旧逻辑是
`contributes.commands = 全部臂`，即 release 构建会把这条 manifest 覆写成 56 条
（票 16 §8 实测的「28 → 56」与此同源）；新逻辑产出「28 条声明原样保留 + 28 条差集
进报告 + 零写回」。
**release 路径幂等已实测**（票 16 §8 的「构建即写坏 manifest」正式收口）：
`node packages/plugin-sdk-desktop/bin/cli.js manifest` 在 `plugins/session/` 连跑两次，
第二次输出「plugin.json 已是最新，无需更新」且文件逐字节不变。代价是把
`permissions` 的顺序交给生成器（ASCII 升序，`ui:input` → `ui:settings` →

### 3. 跨私有库搬运（票 16 §7 挂账）

**为什么必须在宿主**：私有库按插件 id 分文件，插件侧无跨库通道（也不该有——那会让
一个插件读到另一个插件的数据）。形状沿用 `peer_migration.rs`：存在性即版本戳、
best-effort 不阻断启动、可对旧库重跑。

- **顺序前提**：跑在 `PluginHost::new()` 之后（`lib.rs` setup 内 `app.manage(plugin_host)`
  处）。合并插件 `activate` 里的库内改名（票 16 `schema::migrate_via_host`）与建表已
  完成，目标表此刻才存在。目标库文件压根不存在（插件从未激活）→ 本轮整体跳过，
  下次启动再搬：**搬运的前提恰恰是接管方已把自己的表建好**。
- **幂等戳**：目标库 `plugin_meta` 写 `task_data.migrated_from=com.bedcode.auto-task`，
  值 = 本次搬运摘要（各表插入行数 + 缺失/失败清单）。戳**最后写**——中途崩溃则下次
  重跑，`INSERT OR IGNORE` 保证同主键不二次插入。
- **按列名交集拷贝，不用 `SELECT *`**：旧库可能是若干个版本前的形状，任一侧加过一列
  就会让位置对位整表失败；交集让老数据照样落地。无交集 → 显性失败（两库不是同一域，
  静默跳过更糟），失败按表登记且不短路其余表。
- **不替插件建表**：目标表缺失只登记 `missing_target`，绝不 `CREATE TABLE`——那等于
  宿主替插件决定 schema（违 D2/D3）。
- **并发**：目标库另开连接 + `busy_timeout(5s)`，兜住启动期插件 tick 的并发写。
- **已知副作用（记由，不修）**：`recover_creating_jobs`（creating 随进程销毁 → failed）
  先于本迁移跑完，故此刻拷进来的 `creating` 行不会被那一轮兜底，改由定时域静默看门狗
  在后续 tick 收口；不补跑第二轮恢复，避免与 tick 竞争。
- **改名清单的真源在插件**：宿主 `TASK_TABLE_COPIES` 是消费方副本，由
  `task_table_copies_match_plugin_rename_list` 读 `plugins/session/rust/src/schema.rs`
  源码逐条对账（跨语言漂移即红）。

### 4. 模板版本 bump 的双向锁

票 16 把 bump 压到本票，是因为双轨期「最后一次写的人决定 hook 打到哪个前缀」。本票
auto-task 后端已退役 → 只剩一个写者，可以安全递增。风险换成了**「脚本首行标记与 Rust
常量不同值」**：只改常量则部署副本每轮被重写（无谓 IO + 抖动），只改脚本则旧副本被
判定为最新而**永不改指新前缀**（现象是任务不同步，静默）。故：

- `shipped_hook_scripts_point_at_this_plugin` 增加逐脚本断言「首行标记 == 对应常量」；
- 两处 `*_hook_version_marker_matching` 用例的标记改用 `format!("…{CONST}")` 取常量，
  非匹配样本改成 `99999`（原来写死相邻数字，bump 后会「非匹配样本恰好等于新版本」而假绿）。

### 5. 广播对照用例退役

`include_str!` 读旧插件四个模块做逐构造比对的用例已删。替代不是「另一份源码扫描」，
而是分层看：

| 保护 | 承接者 |
| --- | --- |
| 载荷形状（字段名/大小写/缺字段） | 结构性闸门：宿主 `host_impl/events.rs::broadcast_sync` 把载荷反序列化为 SDK `SyncEvent`（与插件同一类型，serde 表示即线协议）+ 穷尽 `From` → `DesktopSyncEvent`。改坏了要么显性 broadcast error，要么编译不过 |
| 触发时机（推进路径没被删） | 新用例 `broadcast_trigger_points_are_pinned`：四个 SyncEvent 变体按 4/2/1/1 钉死，`bus_publish(` 与 `emit_event(` 各 9 且**必须成对**（漏一侧 = 总线或前端事件单边失声） |
| 端到端可达 | 票 16 的 `test_session_task_http_and_scheduled_closed_loop` 与票 15 的 `test_session_task_domain_closed_loop` |

点数静态计数**只能这样**：无头 harness 里 `AppContext::try_global()` 未 init，
`broadcast_sync` 必然返回 Err，S1 观测不到同步通道出口（票 16 §10 同一根因）。

### 6. UI 搬迁顺带修掉/钉住的三件事

1. **共享 router 改走 SDK**：旧实现直接读 `window.__BEDCODE_SHARED__.router`。搬进
   `plugins/session/` 会撞本插件工程既有的 C4 红线用例（禁手写共享运行时全局），
   故新增 `src/utils/route.ts` 收口 `getRouter()`（未初始化时 null 语义，dev-shell /
   vitest 不炸），弹窗与工具栏两处消费者共用。
2. **发现并修掉一处漏释放**：入口的 `events.on('task:status-changed' | 'session:mode-changed')`
   在旧实现里丢弃了返回值，`deactivate` 不释放 → 插件重载后监听重复计数。新用例
   `deactivate 释放全部贡献面` 把「贡献面 dispose 集合」与「事件订阅 dispose 数量」分开
   钉死，正是它当场暴露的（首跑 6 订阅 / 4 释放）。
3. **两条同源护栏**（票 17 的 28 条命令改名 + 122 个 key 前缀改名都是机械改写，
   编译期抓不到）：`前端调用的每条命令在 Rust 分派表里有同名臂`、
   `前端 t() 用到的每个文案 key 都在两语言表里`。

另外两处**刻意不变**：状态/模式变更的入口监听仍只做日志留痕（旧实现即如此，弹窗与
历史视图各自注册数据刷新），日志前缀统一为 `[Session Center/task]`；旧实现里
`statusMessages` 硬编码中文映射被去掉（改为直接记 `taskStatus` + reason），因为
AGENTS §6 不允许组件内硬编码用户可见中文，而这两行本来只进控制台。

### 8. 三域端到端手工验证清单（待人工，本票未跑）

无头环境不具备真 GUI 与真 agent CLI 会话，以下必须人工在 `pnpm run tauri:dev` 上走一遍。
每条都写「看什么算过」，避免变成随手一点：

1. **贡献面秩序**：侧边栏顺序 = 设备配对 → 连接历史 → 终端会话 → Agent任务 → 服务器 →
   插件管理 → 设置；宿主内置「设备配对 / 终端会话」入口不出现（被同 order 让位），
   深链 `/sessions`、`/devices` 仍可达。
2. **配对贯穿线**：生成配对码 + QR → 移动端（或 curl 客户端形态）扫码/输码配对 →
   已配对设备列表出现该设备 → 撤销。日志里无 `auth fallback` warn（认证未走降级路径）。
3. **建会话 + hooks 安装**：在含 `.claude` / `.codex` / `.pi` / `.opencode` 的项目目录
   建会话并启动 → 该目录下的集成文件被写入/重写，**首行标记等于 §4 的新版本号**，
   脚本内 `PLUGIN_ID` 是 `com.bedcode.session`。
4. **模板 bump 的重写腿（票 16 遗留）**：事先手动把某个项目里的副本标记改回旧值
   （如 `@bedcode-template-version 1`）→ 启动会话后必须被重写为新标记与新前缀；
   用 `curl -s -X POST localhost:PORT/api/plugin/com.bedcode.session/task-status`
   验证新前缀端点应答（`plugin_id` = `com.bedcode.session`）。
5. **队列跑一轮**：终端工具栏出现「自动任务」按钮（仅适配 agent 会话；非适配会话不得
   出现）→ 打开弹窗 → 入队两条 → 开「自动执行」→ 队列按序下发到 PTY、状态从
   `pending → waiting → executing → done`，任务历史 Tab2 有记录且统计 Tab4 数字对得上。
6. **定时任务真链路（票 16 遗留）**：建一条 1 分钟后触发的 job → 观察
   `pending →(到期) creating →(Created 事件) executed`，**创建腿必须真人看**
   （S1 无头 harness 没有全局 AppContext，票 16 §10 已记该缺口）；同时确认
   `Created` 事件载荷带 `name` / `working_dir`（缺字段会让 job 永久停在 creating 且不报错）。
7. **跨库搬运腿**：用装有 auto-task 的旧版本数据目录起一次本版本 →

8. **故障半径**：在插件管理页停用 `com.bedcode.session` → 四个贡献目录与设置分组消失、
   宿主兜底壳接管不白屏；重新激活后目录回来。

**跑测方式记三笔（重要，关系到「绿」是不是真的绿）：**

- **前端必须用 `--pool=forks`**。默认 threads 池在本机（13GB / 可用 8GB）跑全量会在
  ~66/81 个文件处 worker OOM（`Ineffective mark-compacts near heap limit`），
  `--maxWorkers=1` + 6GB 也一样炸。**且这不是本票引入的**：剔除全部本票新增文件、
  只跑 `src packages plugins/agent-hub plugins/scheduler` 同样 OOM。换 forks 池后
  全量一次过，比票 16 记的 `--maxWorkers=2 + 6144` 更稳。
- **S1 wasm 闭环用例会静默 skip**。`test_session_*` 系列读的是
  `src-tauri/resources/.../bedcode_plugin_session.wasm`，产物不存在时
  `eprintln!("[skip] …")` + `return` 直接算过。**跑宿主测试前必须先重出产物**，
  否则本票的闭环覆盖是假的（本次取证日志里 `[skip]` 计数为 0，已核）。
- **宿主插件私有库用例仍受进程级 `plugin_db_root()` 约束**（票 16 记过）：本票新增的
  迁移用例走独立 temp 目录，不碰该锁，但 `task_data_migration` 与 session 闭环同跑时
  不要为了加速去改并发。
