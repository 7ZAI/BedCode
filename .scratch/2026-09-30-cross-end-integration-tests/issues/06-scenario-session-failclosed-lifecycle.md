## spec §5「三种 deny_kind 至少各一」不可达 —— 记录在案

`deny_kind`（`no_center` / `unavailable` / `policy`）是宿主**日志结构化字段**，
**不是 wire 字段**：客户端一律只看到 401。这是**有意的**（把拒绝原因分类暴露给
客户端等于泄露部署状态）。因此跨端层能观测的契约是：

- 一律**显性拒绝**（401 / 404），不是「查不到就当没数据」的静默降级；
- 放行才返回数据，且必须同时满足「中心在册 + 凭证有效」（正例对照，证明前面的
  401 不是「总是拒绝」这一恒真断言）；
- WS 面同一闸门：无效凭证下链路反复重连但**永不 live**、零输出字节。

三态分类本身的覆盖在宿主 `utils/auth/auth_center` 单测，不在本工程职责内
（也不该在跨端层重复造 mock）。**已在文件头与 `mobile-desktop-auth.md` 写明。**

## 另一处实测发现：无中心时是 401 而非 404

初稿契约写「插件未激活 → 认证端点 404」。实测 **401 `{code:1007}`**：网关中间件
先于路由解析运行，而免凭证档位是插件在 activate 期登记的动态声明。**实测语义更强**
——不存在「无中心即可自助配对」的引导入口。已改写契约。

## 生命周期场景的关键断言

- L-002 停用 → 移动端链路掉线并退避重连（`reconnecting`）
- L-003 停用后受保护端点**显性失败**（fail-visible 形态 ①），不是返回空列表
- L-004 重新激活后**同一 token 仍然有效**（认证记录与密钥环都不在停用清理范围内）
  + 停用前的会话不复活（真源随实例停用失效）
