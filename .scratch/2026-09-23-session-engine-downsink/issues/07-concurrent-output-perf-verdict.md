# 07: 多端并发输出实测与环限额裁决（不许估算）

**What to build:** 回答 spec 里那条「性能红线要测过再判」的悬账：**桌面多个终端窗口 + 移动端通道
同时拉同一条会话输出**时，端到端吞吐与延迟到底是多少、同实例串行会不会成为瓶颈、
环容量与单次拉取上限在「长会话 + 多端」下够不够。产出是一份实测数据和一句结论
（达标 / 不达标 + 调什么参数），不是推测。

**Blocked by:** 06（形态 B 全链路接通之后，多端并发才真实存在）。

**Status:** ready-for-human

## 为什么要人跑

数据必须来自**真机真会话**（真 bash/真 agent 输出 + 真实多端），release 构建，
不能用 debug 数字或纸面推导冒充。探针代码可以 agent 写，判读与拍板要人看一眼曲线。

## 验收标准

- [ ] 对照基线写在 spec 里（历史实测 ≈40 µs/op、2.6 ms/MB 的插件侧拉取路径），
      本票测的是**并发**场景：1 桌面窗口 / 2 桌面窗口 / 1 桌面 + 1 移动 / 2 桌面 + 2 移动
- [ ] 每组给出：稳态吞吐、尾延迟（p50/p95）、丢帧或截断次数、CPU 占用、是否出现
      同实例串行排队导致的可见卡顿
- [ ] 环深度结论：长会话（持续输出 N 分钟）下现有环容量能回溯多久，
      多端各自的游标落后会不会互相挤掉历史；单次拉取上限对刷新率的影响
- [ ] 不达标时的**具体**调参建议（拉取批量 / 轮询频率 / 环容量档位），
      并写明「不需要回退形态」（形态 B 已被裁决锁定）
- [ ] 结论回写 spec 的性能验收项 + 一条 CHANGELOG；实测数据留档在票末或票同目录
- [ ] 探针用例若进仓（release-only、默认不跑），必须像既有性能用例那样注明
      「本机负载会漂移、不参与门禁」

## 边界与不做

- 不改形态（环本体留引擎是定案）。
- 不为了数字好看而放宽移动端协议。
- 不在本票做 P4 的任何删除。
