## 缺陷 2 细节（SafPickerPlugin launcher）

### 证据

`bedcode-mobile/.dev-logs/android-dev.2026-09-06.log` / `09-07.log`：

```
E BedCode-SafPicker: pickDirectory launch failed: Attempting to launch an unregistered
ActivityResultLauncher ... You must ensure the ActivityResultLauncher is registered
before calling launch().
```

### 根因链

1. Tauri `PluginManager.onActivityCreate`（反编译 `feature-tauri-android.jar`）：
   - 开头 `if (PluginManager.activity != null) return;` —— **只注册一次**；
   - 正常路径 `registerForActivityResult(...)` 注册三个静态 launcher（StartActivityForResult / StartIntentSenderForResult / RequestMultiplePermissions），绑定当前 Activity 的 lifecycle。
2. Activity 被系统销毁重建（内存回收、fontScale 变更等）：
   - 旧 Activity 销毁 → lifecycle-owner 自动 `unregister(key)`；
   - 新 Activity `onCreate` → `PluginManager.onActivityCreate` 因 guard **直接 return，不重新注册**；
   - `Plugin.startActivityForResult()` 仍持旧静态 launcher（key 已注销）→ `launch()` 抛 unregistered。
3. 上传第一步 `file-transfer.pick-files` 走 `pickFile`，必然失败 →「上传失败报错」。
4. 原文件头注释**已记录**这个失败模式，但判定「正常路径不重建」——真机实证频繁命中，需修复而非容忍。

### 修复（SafPickerPlugin.kt）

- `pickDirectory` / `pickFile` 从 `Plugin.startActivityForResult + @ActivityCallback` 改为 `launchPicker()`：
  - `activity.activityResultRegistry.register(key, contract, callback)`（无 lifecycle-owner 重载，无 "register before STARTED" 限制，可在 RESUMED 后调用）；
  - key = `saf-picker-${System.nanoTime()}` 每次唯一；
  - 回调内先 `unregister()` 再分发结果；`launch()` 异常时兜底 unregister 防 key 泄漏；
  - picker 模态单实例天然串行，无并发冲突。
- 构造参数类型 `Activity` → `AppCompatActivity`（`activityResultRegistry` 是 `ComponentActivity` 成员）。
- 已同步备份：`src-tauri/android-backup/app-java/SafPickerPlugin.kt`（该文件此前不在备份中，属既有恢复清单缺口，顺手补齐）。
- 验证：`./gradlew :app:compileUniversalDebugKotlin --offline` BUILD SUCCESSFUL。

> 同类隐患：`SafTransferPlugin.saveToDocument`（717 行）也用 `Plugin.startActivityForResult + @ActivityCallback`，Activity 重建后同样会失效。本次未改（用户未报「保存到…」问题），后续如再遇同错误按本方案同步重构。

## 缺陷 3 细节（历史卡 open-location 无反应）

### 根因

`plugins/file-transfer/src/components/TransfersTab.vue` 历史卡：

```html
<TaskCard
  v-for="entry in history"
  ...
  :actions="(entry.direction === 'download' && entry.state === 'completed')
    ? [{ kind: 'open-location', label: t('transfer.v2.history.openFolder'), variant: 'tint' }]
    : []"
  <!-- 缺 @action="onCardAction"：按钮渲染了但点击事件无绑定，静默无反应 -->
/>
```

发送卡 / 接收卡均有 `@action="onCardAction"`，历史卡漏绑。

### 修复

历史卡补 `@action="onCardAction"`。按钮点击 → `emit('open-location', id)` → `FileTransferView.handleOpenLocation`（优先 `entry.localPath → revealInDir`，否则按文件名 `revealReceivedFileLocation` → Kotlin `DownloadsDirPlugin.openFileLocationByName`）。真实设备 `localPath` 恒 null，走按名解析路径（MediaStore 公共下载命中 → 打开 Download 目录；未命中回退 app 私有下载目录 FileProvider）。

## 缺陷 1 现状（下载无进度，待运行时诊断）

### 已排除（静态走查全通）

- 引擎接收侧 `receive_files_after_accept` 每块 emit `TransferEvent::Progress`（`packages/peer-net/src/transfer.rs`，桌面端同源，桌面端进度正常佐证）；
- 移动端事件接线：`SharedDirHandler::new(shared, saf, config, transfer_tx)` → `drive_receive_events`（`peer_net.rs` start_locked）→ `update_progress` → `throttle_publish` → `emit_json("peer-receive-changed")` → bus `peer:receive` → 插件 `merge_and_emit` → `plugin:file-transfer:receiving-changed` → 前端 `useTasks`；
- pull 路径 `PeerRemoteState.session.events` = `handler.event_sender()` = `transfer_tx`，batch_id 用本地 `pull-{nanos}-{index}`，`register_remote_pull` 预登记任务行同 id，匹配一致；
- 插件 `merge_snapshot` 按 batchId upsert、transferredBytes 变化触发 flush；前端 `TaskCard` 进度条 `progressPercent(offset, size)` 渲染正确。

### 已加诊断（本次随修复落地，便于 dev 重测定位断点）

1. `peer_receive.rs drive_receive_events` Progress 分支：`tracing::debug!(batch_id, transferred, rate_bps, "receive progress event")` —— 断在宿主入口 = 引擎事件未到；
2. `throttle_publish` 跳帧：`tracing::debug!("receive progress throttled ...")` —— 确认节流行为；
3. `useTasks.ts` receiving-changed 回调：`console.debug('[File Transfer] receiving snapshot', len, first 'off=/st=')` —— 断在前端 = 插件事件未到/未发。

### 重测指引（用户）

dev 版（`pnpm run tauri:android:dev`，电脑端 `pnpm run tauri:android:dev:log` 落盘）或 release + `adb logcat -s BedCode:*`，下载一个文件，按诊断日志出现位置三段定位：

1. 无 `receive progress event` → 引擎/会话层（看 `peer-net`/`transfer` 日志，attach logcat 全量再查）；
2. 有 `receive progress event` 但无 `peer event pushed to plugin bus event="peer-receive-changed"` → 收宿主 publish 段；
3. 有 bus 推送但前端无 `receiving snapshot` → 插件 WASM `merge_and_emit`/事件透传段；
4. 前端有 snapshot 但进度条不动 → 前端渲染/节流段（带 `transferredBytes` 值一起看）。
