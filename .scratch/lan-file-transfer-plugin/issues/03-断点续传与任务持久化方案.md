# 断点续传与任务持久化方案

Type: grilling
Status: resolved
Blocked by: 01

## Question

传输任务的状态机与持久化如何设计？依赖「传输协议选型」（续传是 Range/Content-Range 还是自定义偏移端点，决定偏移语义）。

要敲定的：
- **任务状态机**：排队 / 传输中 / 暂停 / 待续传（断线自动转入）/ 完成 / 失败 / 同名被拒 —— 状态迁移与触发条件
- **偏移持久化**：存插件 storage（键值）的 schema——任务 id、方向、远端路径、本地路径、已完成偏移、分片图（若有分片并发）、时间戳；什么时机写（每个 chunk？节流？）
- **续传配对**：重连后如何识别"这是同一个未完成任务"（文件指纹：路径+大小+mtime？），远端文件在断线期间变化了怎么办（size/mtime 不匹配 → 拒绝续传、提示重来）
- **清理策略**：完成/取消任务的记录何时从 storage 删除，半成品文件（上传一半的目标文件）如何处置——已定"不覆盖"，半成品必须是不可见的临时文件，完成后原子改名？此点与"同名即拒"规则交互，需要一起定
- **双端对称**：上传方与下载方各自持久化什么，谁负责续传握手

产出：状态机图 + storage schema + 续传握手指规。

---
设计输入（来自已决票据「宿主通用文件服务能力接口设计」）：上传续传基于 upload session（创建校验 → 偏移 append → 完成改名）；两端任务状态/对端在线等控制面消息走现有 WebSocket，不走轮询。

## Answer

经逐项 grilling 敲定如下（用户确认）：

### 1. 任务状态机
状态：`queued` / `transferring` / `paused` / `resumable` / `completed` / `failed` / `rejected`（终态，原因码 duplicate-name）/ `cancelled`。
迁移：
- queued → transferring：并发槽空出
- transferring → paused：用户暂停
- transferring → resumable：断线/对端下线（自动）
- transferring → completed / failed
- 上传会话创建被拒 → rejected（终态）
- paused / resumable → transferring：恢复
- 除 completed 外 → cancelled：用户取消，清理临时文件与偏移数据

### 2. 恢复触发（两档）
- 连接断开后重连（App 未重启）：**自动续传**，UI 显示"已自动续传"，可取消。
- App 重启后：paused/resumable 任务恢复到列表但**不自动传输**，提供"全部继续"按钮。

### 3. 持久化
- 位置：插件 storage，单 key `transfer-tasks`（JSON 数组）。
- 字段：id、direction（upload/download）、peer{deviceId,name}、remotePath（相对挂载点）、localPath、size、offset、uploadSessionId（仅上传）、fingerprint{size,mtime}、state、reason、createdAt/updatedAt。
- 写入时机：传输中每 1 秒节流写一次；状态迁移立即写；宿主 shutdown 信号强制 flush。
- 跨重启保留：仅 paused/resumable；completed/cancelled/rejected/failed 当次会话可见，重启清除。

### 4. 偏移有效性与续传握手
- 下载：恢复前比对远端指纹（list/HEAD 取 size+mtime）；不匹配 → failed（原因"远端文件已变化"），可一键重新排队从头传；匹配 → `Range: bytes={offset}-` 续传。
- 上传：恢复时查询 session 已收字节数；一致 → append 续传；**session 丢失 → 自动重建从头传**（临时文件按 session id 命名、不可见，与"同名即拒"不冲突）；本地源文件指纹变化 → failed 提示重来。
- session TTL：24 小时无活动由宿主清理（宿主侧可配置）。

### 5. 半成品文件与清理
- 临时文件落**目标目录内**（同卷，完成后 rename 原子落位），命名 `.bedcode-upload-{sessionId}.part`（上传）/ `.part`（下载）。
- "不可见"语义：插件浏览列表过滤 `.part` + 落位前无任何路径指向最终文件名；物理存在属接受代价（不用独立暂存区，避免双倍 IO）。
- 上传清理三路兜底：取消端点、24h TTL、启动时宿主扫描孤儿 `.part`。
- 下载：取消删除 `.part`，暂停/待续传保留；完成原子改名；改名竞态（目标名恰被占用）→ 转 rejected/duplicate-name，保留 `.part` 供用户决定。
- 下载的"同名即拒"由发起方在本地检查目标路径。
