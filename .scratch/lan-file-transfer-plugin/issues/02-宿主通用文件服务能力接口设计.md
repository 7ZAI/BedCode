# 宿主通用文件服务能力接口设计

Type: grilling
Status: resolved
Blocked by: 01

## Question

两端宿主需新增的**通用受控文件服务能力**（数据不经 WASM，插件只配置不碰数据流），其接口如何设计？依赖「传输协议选型」的结论（续传机制、分片模型由协议决定）。

要敲定的接口面：
- **插件 → 宿主的配置 API**：挂载路径、允许目录根列表、操作白名单（list/download/upload）、生命周期（activate 挂载 / deactivate 卸载）
- **策略钩子**：上传前校验（"同名即拒"就是第一个钩子）——钩子在 WASM 中执行还是声明式规则？同步阻塞上传流程的开销可接受吗？
- **目录沙箱**：宿主侧路径规范化与越界防护（symlink 逃逸、`..` 遍历、大小写文件系统差异），这是安全底线，具体规则在此票定
- **认证集成**：桌面端挂现有 JWT 中间件的具体方式；移动端宿主从零起服务时的认证模型（复用配对令牌）
- **两端对称性**：桌面端（已有 actix server，挂新路由）与移动端（全新轻量服务）的接口能否同一套 SDK API？移动端能力的最小实现边界在哪
- **宿主代码归属**：这些能力加在宿主哪些模块（plugin/ 运行时 vs server/）、以什么形式保证"通用、无文件传输业务逻辑"

产出：能力接口草案（SDK 侧签名 + 宿主侧职责清单），作为两个 UI 票据与实现 spec 的骨架。

## Answer

经逐项 grilling 敲定如下（用户确认）：

### 1. SDK 接口形态：运行时挂载 API
- 不走 manifest 静态声明；插件在 `activate()` 中调用 `context.fileService.mount({...})`，返回 Disposable，`deactivate()` 时摘除。
- `plugin.json` 仅新增权限声明（`fileservice`），不含配置。
- 挂载配置：`mountPath`、`roots`（允许目录根，来自插件 storage 的用户配置）、`operations` 白名单（list/download/upload）、`onUploadRequest` 策略钩子。
- roots 变更走 `mount.updateRoots(...)` 即时生效，无需重新挂载。
- 宿主按插件 id 命名空间隔离 URL（桌面端 `/plugins/{pluginId}/...`）。
- 两端 SDK 签名同构（两端插件后端均为 WASM：桌面 wasmtime、移动端 wasm_runtime，架构对称）。

### 2. 策略钩子语义
- 仅上传会话**创建时**调用一次（目标相对路径 + 文件大小），拒绝发生在写任何字节前；chunk 流上不调用。
- 同步阻塞上传握手，**2 秒超时；超时/插件异常一律拒绝（fail-closed）**。
- MVP 只开 `onUploadRequest` 一个钩子；接口预留扩展。

### 3. 目录沙箱规则
1. 挂载时：root 必须存在、是目录、通过宿主 fs 授权，否则拒绝挂载；重复/嵌套 root 去重（取最外层）。
2. 请求时：路径规范化，`..` 拒绝；最终路径 `canonicalize` 后必须仍在某 root 前缀内（防 symlink 逃逸），否则 404。
3. 大小写按文件系统实际语义（canonicalize 后比较，天然正确）。
4. root 失效（删除/移动/权限回收）：该 root 下线，其余正常；列举时返回明确错误供 UI 提示（文案细节归「用户授权流与安全细节」票据）。
5. 隐藏/系统文件宿主不过滤，是否显示由插件 UI 决定。

### 4. 宿主代码归属：两端各自实现（不建共享 crate）
- 桌面端：现有 actix server 上挂载子路由，自动经过现有 JWT 中间件；模块归 `src-tauri/src/plugin/`（挂载随插件生命周期）。
- 移动端：宿主新增同款 server 栈（actix-web，与桌面对齐），独立端口，插件子系统持有生命周期——首个文件服务挂载时启动，最后一个摘除时关闭。
- 业务代码不进宿主；宿主只提供通用能力。

### 5. 移动端认证模型：宿主登记的 Bearer Token
- 文件服务核心只认宿主登记的 Bearer Token（通用机制，不掺认证业务）。
- Token 引导：移动端文件服务启动时生成服务 token，通过**已认证的现有 WS 连接**推送给桌面端；桌面端存储并在调用时携带；随配对解除失效。
- 对称方向（移动端调桌面端）继续用现有 JWT。

### 6. 附加设计输入（用户提出）
- **控制面消息走现有 WebSocket**：文件服务的数据面走 HTTP，但对端在线感知、挂载/端口公告、传输任务状态推送等控制面消息应复用已建立的 WS 通道，避免轮询与额外连接。后续票据（续传方案、UI 规格）需吸收此点。

### 对后续票据的约束
- 「断点续传与任务持久化方案」：upload session 端点形状（创建校验 → 偏移 append → 完成改名）由本票确定；任务状态推送走 WS。
- 「用户授权流与安全细节」：root 失效的呈现、token 失效的用户可见性在此票展开。
- 两端 UI 票据：入口/状态展示依赖本票的挂载与生命周期语义。
