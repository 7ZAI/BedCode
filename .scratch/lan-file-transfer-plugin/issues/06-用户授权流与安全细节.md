# 用户授权流与安全细节

Type: grilling
Status: resolved
Blocked by: 02

## Question

围绕"只能访问使用者设置的允许目录"的用户可见授权流与安全边界细节。依赖「宿主通用文件服务能力接口设计」（沙箱与钩子的机制在那边定，本票定用户视角的流程）。

要敲定的：
- **允许目录的设置流**：插件设置区添加目录 → 宿主 fs 授权弹窗 → 目录根存入插件 storage；目录不存在/被移动/权限被系统回收时的表现（服务端该目录自动下线并提示）
- **首次连接的信任确认**：已有配对即信任，还是文件服务首次被访问时本端额外确认一次（"允许对方访问你设置的目录"开关默认开/关）
- **操作审计**：是否需要最简访问日志（谁在何时下载/上传了什么，本端可查），还是完全不做
- **明文传输风险的呈现**：宿主当前 ws:// 未加密（E2E 加密计划中），文件传输同样明文——是否在设置页向用户明示"仅限可信内网"，措辞怎么定
- **同名被拒的用户文案**：双端提醒措辞（上传方看到"无法上传：目标已存在同名文件"，接收方是否要感知）

产出：授权流程说明 + 安全提示文案，并入 spec 的安全章节。

## Answer

经逐项 grilling 敲定如下（用户确认）：

### 1. 允许目录设置流
- 设置区「共享目录」列表 → 添加 → 宿主 fs 授权弹窗（桌面文件夹选择对话框 / 移动系统目录选择器）→ 存插件 storage → `mount.updateRoots()` 即时生效。
- **默认安全**：新装插件共享列表为空；未配置前对端只看到「对方尚未设置共享目录」。
- 条目操作仅「移除」（不动文件本身）；改路径 = 移除再添加。
- 失效目录：本端列表显示「目录已失效」警示（可移除/重选），宿主 root 自动下线；对端浏览返回「该目录当前不可用」。

### 2. 信任模型
- 配对 + 白名单即完整信任模型，**不加**额外的"允许访问"总开关。停用插件 = 挂载点摘除 = 服务消失，即插件级总开关。

### 3. 审计
- MVP 不做访问审计日志（任务记录已覆盖可见性；避免超出最小宿主扩展原则）。将来如需，作为宿主通用能力扩展项。

### 4. 明文传输：告知 + 加密拦截预留缝（用户决策）
- 保持明文传输。设置区常驻一行告知（非弹窗）：见下方 i18n `transfer.settings.plainWarning`。
- **传输层预留加密拦截接口，MVP 空实现直通**（如 TransportCipher seam：对传输字节流的加/解密拦截点）。未来接入 E2E 加密（X25519 + AES-GCM）时不动传输主流程。此缝由两端宿主通用文件服务能力提供——作为对票据 02 宿主能力的补充约束。

### 5. 同名被拒：接收方不感知 + i18n 文案定稿
- 接收方**不感知**（session 创建时即拒，接收目录无变化）。
- i18n keys（zh-CN / en 同步）：
  - `transfer.error.duplicateName` — 无法上传：目标目录已存在同名文件 / Upload failed: a file with the same name already exists in the target folder
  - `transfer.error.remoteChanged` — 远端文件已变化，无法续传，请重新传输 / The remote file has changed and can't be resumed. Please start over.
  - `transfer.error.dirUnavailable` — 该目录当前不可用 / This folder is currently unavailable
  - `transfer.settings.plainWarning` — 文件在本局域网内明文传输，请仅在受信任的 WiFi 网络中使用 / Files are transferred unencrypted on your local network. Only use this on trusted WiFi.
