## Bug 1（🟡）：`askTimeoutSecs` 拼写错误

### 位置

`src/composables/useSettings.ts:59-62`：

```ts
approvalTimeoutSec:
  typeof r.ask_timeout_sec === 'number'
    ? r.ask_timeout_sec
    : (typeof r.askTimeoutSecs === 'number' ? r.askTimeoutSecs : 60),
//             ^^^^^^^^^^^^^ 多一个 's'，应为 askTimeoutSec
```

### 根因

camelCase fallback 键名拼写错误。`Settings` 接口定义的是 `approvalTimeoutSec`（无 's'），fallback 应为 `r.askTimeoutSec`，但实际写成 `r.askTimeoutSecs`。

### 后果

当前后端 `get_settings` 返回 `ask_timeout_sec`（snake_case，Rust 侧硬编码），前端 `typeof r.ask_timeout_sec === 'number'` 分支命中，fallback 永不执行。**当前无症状**。

若后端未来改为返回 camelCase（如 `askTimeoutSec`），前端不匹配、退回默认 60，用户设置的超时值丢失。

### 修复建议

```ts
approvalTimeoutSec:
  typeof r.ask_timeout_sec === 'number'
    ? r.ask_timeout_sec
    : (typeof r.askTimeoutSec === 'number' ? r.askTimeoutSec : 60),
```

## Bug 2（🟡）：`direction` 反向兜底

### 位置

`src/composables/useTasks.ts:42`：

```ts
direction: raw.direction === 'receive' ? 'download' : 'upload',
```

### 根因

只显式匹配 'receive'，其余一律 'upload'。后端当前只返 'send'/'receive'，故 'send' 正确映射 'upload'。但若后端返 'download'（前端语义）或 null/undefined，会被误判为 'upload'。

### 后果

当前无症状。若后端语义演进（如统一为前端 camelCase 'upload'/'download'），前端会全部误判为 'upload'。

### 修复建议

```ts
direction: raw.direction === 'receive' || raw.direction === 'download'
  ? 'download'
  : 'upload',
```

或更防御性：

```ts
direction: ['receive', 'download'].includes(raw.direction) ? 'download' : 'upload',
```

## Bug 8（🟢）：`approveBatch/rejectBatch` 命令失败时无用户反馈（描述已修正）

### 现状核对（2026-09 核验）

实际代码（`useReceiving.ts:238-243` + `FileTransferView.vue:123-130`）：

```ts
// useReceiving.ts
async function approveBatch(batchId: string): Promise<void> {
  await context.commands.execute('file-transfer.approve-batch', { batchId })  // 无内部 try/catch
}

// FileTransferView.vue
function handleBatchApprove(batchId: string): void {
  approveBatch(batchId)
    .then(() => {
      queueVisible.value = true  // 命令成功才打开队列
    })
    .catch((e: unknown) => {
      console.error(`[File Transfer] approve-batch failed for "${batchId}":`, e)
    })
}
```

### 原审计描述 vs 实际行为

原审计声称：

> `approveBatch` 内部 catch 错误，不 rethrow → `.then()` 无条件执行，队列打开

**与实际不符**。`approveBatch` **没有**内部 try/catch——命令失败时 promise reject 直接传播到 `handleBatchApprove` 的 `.catch`，`.then()` 不执行，队列**不会**误开。

### 实际残留问题（低危）

1. 命令失败时仅 `console.error`，无 toast/错误态——与 Bug 4/5/9 同模式的 UX 问题；
2. `rejectBatch` 同理：失败静默，用户以为"拒绝成功"但批仍 pending。

### 可选改进（非缺陷修复，UX 增强）

命令失败时给用户反馈（toast 或行内错误）：

```ts
async function approveBatch(batchId: string): Promise<boolean> {
  try {
    await context.commands.execute('file-transfer.approve-batch', { batchId })
    return true
  } catch (e) {
    console.error(`[File Transfer] approve-batch failed for "${batchId}":`, e)
    return false
  }
}
```

调用方：

```ts
approveBatch(batchId).then((ok) => {
  if (ok) queueVisible.value = true
}).catch(...)
```

## Bug 9（🟢）：`refresh` 静默失败

### 位置

`useReceiving.ts:224-235`：

```ts
async function refresh(): Promise<void> {
  try {
    const [b, r, h] = await Promise.all([
      context.commands.execute('file-transfer.list-batches', {}),

receiving.value = r.status === 'fulfilled' ? ... : []
history.value = h.status === 'fulfilled' ? ... : []
```

设备在 `devices` 但缺 addr/port（如快照恢复失败），`rememberEndpoint` 不写 memo。后续数据面命令（浏览/拉取/发送）经 memo 重拨时命中空 memo → 后端 `dial_peer` 报 "dial: invalid endpoint"。用户看到错误但无理解路径。

### 修复建议

跳过时 console.warn，或设备卡片标注"端点缺失"。

## Bug 17（🟢）：`mapState` 兜底断言脆弱（描述已修正）

### 位置

`useTasks.ts:36-39`：

```ts
function mapState(status: string): TaskStateName {
  if (status === 'running' || status === 'transferring') return 'transferring'
  if (status === 'pending' || status === 'paused') return status
  return status as TaskStateName  // ← 兜底断言
}
```

### 原审计描述 vs 实际行为（2026-09 核验）

原审计称：

> 当前后端不发 'interrupted'

**与实际不符**。后端**确实发送** `'interrupted'`：

- `transfer_store.rs` `prune_absent`：快照缺席的进行中条目标 `interrupted`；
- `transfer_store.rs` `mark_interrupted_on_load`：重启恢复时 running/pending/paused 标 `interrupted`。

但 `'interrupted'` 已在 `TaskStateName` 联合中（`types.ts:20`），`mapState('interrupted')` 走兜底断言返回 `'interrupted'`——**运行时行为正确**。

### 实际残留风险（低危）

1. `return status as TaskStateName` 是类型断言，绕过编译期检查；若未来后端引入新状态（如 `'queued'`），会静默通过并渲染未知状态；
2. 建议显式列举终态、非法值回落 `'failed'`。

### 修复建议

```ts
function mapState(status: string): TaskStateName {
  if (status === 'running' || status === 'transferring') return 'transferring'
  if (['pending', 'paused', 'completed', 'failed', 'rejected', 'cancelled', 'interrupted'].includes(status)) {
    return status as TaskStateName
  }
  return 'failed'  // 兜底
}
```
