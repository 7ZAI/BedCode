# 传输协议选型

Type: research
Status: resolved
Blocked by: -

## Question

在已锁定约束下（复用宿主 actix server 与 JWT、单端口、数据不经 WASM、几十 GB 大文件、目标打满 WiFi 链路、断点续传），对比三个候选协议并给出推荐，供用户拍板：

1. **HTTP/1.1 + Range**（主候选）：下载用 Range，上传用分块 PUT + `Content-Range` 续传。调研 actix 流式 IO（`BodyStream` / `actix-web` chunked）在桌面端的实测吞吐上限；分片并发能否打满 WiFi；Range 续传在 Android 客户端（Rust reqwest / Tauri http）的成熟度。
2. **HTTP/2 多路复用**：actix 对 h2c（明文 h2，无 TLS 内网场景）的支持现状；移动端客户端兼容性；相对 ① 的实测增益是否值得复杂度。
3. **QUIC (quinn)**：作为对照组收集吞吐/弱网数据即可，已知与"复用宿主单端口 + JWT"决策冲突，除非 ①② 不达标否则不选。

需要回答的事实问题：
- actix + tokio 流式文件服务在大文件场景的吞吐与内存占用（零拷贝/sendfile 可行性）
- 分片上传的断点续传标准做法（Content-Range PUT vs 自定义偏移端点），哪种对"宿主通用文件服务能力"接口最友好
- 移动端（Android/Tauri）发起长连接大流量 HTTP 的已知限制（后台被杀、Doze 模式影响）

产出：对比表 + 明确推荐 + 对宿主能力接口设计的约束清单。

## Answer

（本会话无子代理能力，由 driving session 直接完成调研；外部事实来源：actix.rs 官方 HTTP/2 文档、GitHub actix/actix-web#3295；代码事实：两端 Cargo.toml）

### 关键事实

1. **actix-web 4 的 HTTP/2 支持形态**（官方文档原文）：
   - RFC 7540 §3.2 的 h2 **upgrade 机制不支持**；
   - **prior knowledge 方式的 h2c（明文）与 h2（TLS）均支持，但仅限低层 `actix-http` service builder**，不走常规 `HttpServer::bind` 路径。
   - 含义：② 技术上可行，但要放弃现有 `HttpServer` + 中间件的常规装配方式，改造成本高；且现有移动端终端 API 客户端走 h1，同端口切 h2c 会破坏存量通信。
2. **宿主依赖现状**：桌面端 `actix-web 4` + `reqwest 0.12(stream)`；移动端 `reqwest 0.12(stream, rustls)`。两端均无 quinn/hyper 依赖。
3. **下载续传**：actix-files `NamedFile` 原生支持 `Range` 请求（206 Partial Content），零额外开发。
4. **上传续传**：HTTP 标准中 `Content-Range` PUT 并非通行服务端能力；业界事实标准是 tus 式协议（HEAD 查询偏移 → 从偏移 append）。对本项目，最简形态是宿主自管理的 **upload session** 模型：创建会话（此时执行"同名即拒"校验）→ 按偏移写入临时文件 → 完成后原子改名。这属于票据「宿主通用文件服务能力接口设计」的设计细节。
5. **QUIC (quinn)**：纯 Rust、Android 可用（UDP 无特殊权限要求），吞吐上限最高；但必须独立 UDP 端口 + 自签证书 + 独立握手，与已锁定的"复用宿主单端口 + JWT"直接冲突，只作对照组。
6. **Android 后台**：切后台/锁屏后传输会被系统限制/中断——这恰是断点续传设计的输入（任务转"暂停-待续传"），不构成协议选型障碍。

### 吞吐评估（内网 WiFi，目标打满链路）

- 单条 HTTP/1.1 TCP 流 + tokio 流式文件 IO（256KB–1MB 缓冲）在千兆有线可打满（~110 MB/s）；WiFi 6 实际链路通常 50–110 MB/s，**单流即足以打满 WiFi**，无需文件内分片。
- 多文件并发 = 多条并行 HTTP 连接（并发数可配置），天然落在 HTTP/1.1 模型内。
- 文件内分片并发（chunk fan-out）会显著增加偏移管理与合并复杂度，**建议 MVP 不做**，留作基准测试不达标时的升级项。

### 对比表

| 维度 | ① HTTP/1.1+Range | ② HTTP/2 h2c | ③ QUIC |
|---|---|---|---|
| 打满 WiFi | ✅ 单流即可 | ✅ | ✅ |
| 断点续传 | ✅ Range 原生 + session 式上传 | ✅（流重置语义复杂） | ✅（内建流恢复） |
| 复用宿主 server/JWT | ✅ 直接挂现有 actix | ⚠️ 需低层 actix-http 改造，破坏存量 h1 客户端 | ❌ 独立端口/握手/证书 |
| 移动端做服务端 | ✅ 常规 Rust HTTP server（hyper/axum） | ⚠️ 同左但 h2c 生态验证成本高 | ⚠️ quinn 可用但第二套栈 |
| 实现复杂度 | 低 | 中偏高 | 高 |

### 结论与推荐

**推荐 ① HTTP/1.1 + Range**：唯一与全部已锁定约束自洽的方案，且性能论证成立（WiFi 场景单流可打满）。对后续票据的约束：

- 「宿主通用文件服务能力接口设计」：下载端点用标准 Range；上传端点采用 session 模型（创建校验同名 → 偏移 append → 完成改名），不依赖 Content-Range PUT；MVP 不做文件内分片。
- 「断点续传与任务持久化方案」：下载偏移 = Range 起始字节；上传偏移 = session 记录的服务端已收字节数。
- 并发默认值：**3**（可配置，上限初拟 8）——雾区该项已具备定值条件。
- 基准测试时若单流不达标，升级路径为"文件内分片并发"（仍在 HTTP/1.1 内），而非切换协议。
