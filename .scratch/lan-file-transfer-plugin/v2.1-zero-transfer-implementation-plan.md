# 服务器归零迁移实施方案（v2.1：全手机发起传输架构）

> **定位**：`docs/adr/0021-mobile-file-server-zero-transfer.md`（架构定案）与 `issues/13-服务器归零方案评审.md`（落地范围评审）的**施工图纸**，是 `v2-implementation-plan.md` 的**增量修订版**。评审 13 结论：「按一次明确定范围的迁移立项」——本文档即该立项的施工内容。
>
> **与 v2-implementation-plan 的关系**：v2 计划（批量批准协议 / 传输历史 / 队列分类 / Kotlin 通知 action / 四 tab UI）**全部保留、不变更**；本方案只替换「数据传输的服务端归属与发起权」这一层。凡本文档未提及的 v2 内容，按 v2-implementation-plan 执行。
>
> **术语纪律**（沿用）：发送/接收 = 发起方区分；上传/下载 = 协议方向；「执行方」= 实际搬运字节流的一端（本方案恒为手机）。
>
> **施工纪律**（沿用 v2）：wire 定义两端逐字一致；两端为同构双写，改一处须同步四处。

## 1. 迁移总览（四阶段）

## 2. 阶段 ①：手机端双向 HTTP client 传输栈

### 2.1 桌面端点发现（零新增消息）

手机是 WS 主动连桌面的客户端，`ConnectionManager` 已持有桌面 `address/port`（`TargetDevice`），认证已 HTTP 化（`get_credentials().session_token` = 桌面 JWT，WS 首消息 reauthenticate 同款）。

**结论：HTTP base = `http://{target.address}:{target.port}`，Authorization 复用 session_token**，不需要新的「桌面公告」消息，不新增端口。

- 【探索点】实现时确认 `file_service_controller.rs` 的鉴权中间件接受该 JWT（评审 13 已确认桌面端点「已挂 /api 下 + JWT 鉴权」；若中间件只认 WS 握手链路的 token 形态，则在 client 首次请求时统一走 `delete login` 同款 header，不新增认证机制）。
- 桌面 peer 记录在 mobile 侧即 `desktop_peer_id()`（`handler/sync.rs` 已有），插件激活时凭 `peer online` 判定端点可用。

### 2.2 连接信息端到端（手机自主发起，无需 intent）

| 手机动作 | HTTP 请求（均带桌面 base + JWT） | 落点 |
|---|---|---|
| 下载桌面文件 | `GET /api/file?path=<桌面挂载相对路径>` + `Range: bytes=start-` → 206 | SAF 中转文件 / MediaStore.Downloads |
| 上传给桌面 | `POST /api/upload`（`CreateUploadRequest` 含 `relativePath`, `size`, `batchId?`）→ `PUT /api/upload/{sid}?offset=` 从已收偏移 append → `POST .../complete` | 桌面 `file_service_controller` 会话引擎 |

路径语义：**发起方侧解析**（下载 = 桌面挂载内相对路径，由桌面控制器映射；上传 = 手机本地/SAF 路径，由手机 client 打开）。

### 2.3 模块划分（mobile `src-tauri/src/file_service/client/`）

新建目录 `client/`，三个模块（与 v2 `transfer.rs` 平级）：

```
file_service/client/
├── mod.rs            // 导出 DownloadClient / UploadClient / TransferHandle
├── download.rs       // GET + Range → SAF/MediaStore 落盘
├── upload.rs         // POST/PUT/GET session 编排（断点重查 + 重试）
└── cursor.rs         // 本地已写字节游标（纯函数，可单测）
```

### 2.4 DownloadClient（下载：手机从桌面拉）

- **指纹比对新增**：源文件变更放弃旧游标重传（`HEAD /api/file?path=...` 取 size+mtime，与现实现同构）。
- **游标**：`cursor.rs` 记录「已落盘字节数」，中断后以新 `Range: bytes={cursor}-` 重拉。
- **落盘**：复用 `saf_tree.rs` 现 SAF 中转 + `complete 落公共下载`（阶段 ① 不引 MediaStore 直写，SAF 中转不变，评审 8 的 M3 直传不作本方案范围）。
- **重试策略**（与 01 断点续传/任务持久化一致）：`failed → 保留游标 → 重试（新 Range）→ 连续 3 次失败转 failed 待手动`。

### 2.5 UploadClient（上传：手机推给桌面）

- **会话生命周期**：`POST /api/upload` 建会话（带 `batchId` 则批 gating）→ 从偏移 `PUT` append → `POST complete` 原子改名。
- **断点重查**：中断后用 `GET /api/upload/{sid}` 查服务端已收偏移 → 从该偏移续传（桌面 `UploadSessionManager` received-offset 为断点真源）。
- **409/404 语义**：`complete` 409 duplicate-name → 该文件 rejected（沿用 v1）；会话 404（对端清理）→ 重新 POST 建会话再续传。
- **重试编排**：send→append 循环；网络错误 → 重查偏移 → 续传，session 参数变化时（对端重启）重建。

### 2.6 并发与锁

- 并发默认 3（沿用 01，可配置 1–8）；每个 transfer 独立 SAF 读/写句柄，不共享文件锁（ADR 0021 并发节）。
- `cursor.rs` 游标按 transfer_id 分 key，抢断/并发无互踩。

### 2.7 与现有手机任务模型衔接（mobile 插件 `state.rs`）

- 手机自主发起的下载/上传任务 = 现有发送任务模型（TaskStore），仅传输执行层从「桌面 reqwest 直连手机 server」换成本 client。
- 【重要】阶段 ① 手机端既有 server 仍可被桌面端直连（旧路径），**任务在发送方（桌面/手机任一端）不变**；只有当桌面 UI 切到 intent 驱动（阶段 ③）后才移除旧直连路径。

### 2.8 阶段 ① 测试矩阵

| 层 | 必测点 |
|---|---|
| `cursor.rs` | 追加/回跳/越界拒绝（纯函数单测） |
| `download.rs` | Range 206 解析、游标恢复、指纹不符放弃旧游标（mock HTTP 响应） |
| `upload.rs` | 会话创建→append→complete 全链路、偏移重查、409、404 重建（mock/mockito） |
| 既有 | 两端 `cargo test` 全绿；v2 §15.1 批测试不受影响 |

**阶段 ① 验收**：真机手机自主下载桌面 10GB 文件吞吐 ≥ 80%×min(T,D)；30%/60%/90% 中断续传哈希一致（继承 12 联调清单 B 组）。

## 3. 阶段 ②：intent 线协议与手机 responder

### 3.1 wire 逐字定义（两端 `enums/file_service.rs` 同构双写）

在 `FileServicePayload`（Mobile→Desktop 方向，`server/ws/message.rs:232` 现有 envelope）新增两个变体；**注意方向**：intent 实际由 Desktop→Mobile 发出，但 v2 的 `TransferApproval` 也已在两端 SyncPayload/FileServicePayload 双向映射——**遵循 v2 既有双通道模式：Desktop 发 `SyncPayload::FileTransferIntent`（`enums/sync.rs`），Mobile 回 `FileServicePayload::IntentAck`（`enums/file_service.rs`）**，两端各新增一个 variant，方向语义清晰。

```rust
// ============ desktop `enums/sync.rs`（Desk→Mob 新增） ============
/// 桌面发起文件传输意图（v2.1：服务器归零后桌面经 WS 指挥手机执行）
FileTransferIntent {
    /// 意图 ID（uuid，ACK/进度/取消全程携带）
    intent_id: String,
    /// "pull"（桌面下载手机文件→手机把本地/SAF 文件 POST 给桌面）
    /// "push"（桌面推文件给手机→手机 GET 桌面挂载文件并落盘）
    direction: String,
    /// 业务语义（用于手机侧通知与任务记录）：
    /// "download"（桌面下载手机文件）| "upload"（桌面推文件给手机）
    semantics: String,
    /// 批 ID（与 v2 批审批联动，push 且 ask 时伴随）
    #[serde(default)]
    batch_id: Option<String>,
    /// 挂载相对路径（push：桌面挂载内路径，由桌面控制器映射；
    /// pull：手机本地/SAF 路径，由手机 responder 解析）
    relative_path: String,
    /// 字节大小（通知展示 + 断点预期）
    size: u64,
    /// 对端设备名（通知展示）
    #[serde(default)]
    device_name: String,
    /// 期望回执（ADR 0021 可靠性要求：intent 必须 expect_response ACK）
    #[serde(default = "default_true")]
    expect_response: bool,
}
```

```rust
// ============ mobile `enums/file_service.rs`（Mob→Desk 新增） ============
/// 意图回执（v2.1）：手机已接受/拒绝并回传会话（或拒绝原因）
IntentAck {
    intent_id: String,
    /// "accepted" | "rejected"
    decision: String,
    /// accepted：期望起始偏移（断点续传真源 = 手机本地已写字节）
    /// rejected："" 或 "user-rejected" | "no-storage"
    #[serde(default)]
    offset: u64,
    /// 手机本地会话标识（pull：upload sid；push：本地游标 id）
    #[serde(default)]
    session_id: String,
}
```

**JSON 示例（push 场景，桌面→手机）**：

```json
{
  "type": "sync",
  "action": "file_transfer_intent",
  "data": {
    "intentId": "9f1c...",
    "direction": "push",
    "semantics": "upload",
    "batchId": "b17",
    "relativePath": "movies/a.mp4",
    "size": 1234567890,
    "deviceName": "MyDesktop",
    "expectResponse": true
  }
}
```

**JSON 示例（手机 ACK）**：

```json
{
  "type": "file_service",
  "action": "intent_ack",
  "data": { "intentId": "9f1c...", "decision": "accepted", "offset": 0, "sessionId": "s8" }
}
```

### 3.2 手机 responder（mobile `file_service/responder.rs` 新建）

`intent responder` 按 `intent_id` 分发并发任务（复用 ADR 0021「按 transfer_id/batch 分发」）：

| 方向 | 手机执行动作 | 数据流终点 |
|---|---|---|
| `intent{pull}` | 用阶段 ① UploadClient 把本地/SAF 文件 POST 给桌面（复用 upload engine，**与手机自主上传同一引擎**） | 桌面接收端 |
| `intent{push}` | 用阶段 ① DownloadClient GET 桌面 + Range 落 SAF | 手机接收端 |

**执行/进度/取消闭环**（ADR 0021 生命周期节）：

1. 手机收到 intent → 通知（pull 信息性 / push 审批联动，见 §4.1）→ 回 `IntentAck{accepted, offset}`（offset = 已落盘字节，断点真源在接收端）。**pull 方向**：POST 桌面上传引擎时必须携带 intent 下发的 `batchId`（桌面已自批准，§4.1 防绕过 2）——不带会在桌面 ask 策略下 403；**push 方向**：ask 策略下须先经用户确认（Approved 门）才回 ACK 并执行 GET。
2. 执行中每推进一段回推 WS `transfer_progress` 事件（复用 v2 既有 progress 通道的 topic/载荷形状，字段补 `intentId`；见 §5.2）。
3. 桌面发 WS `cancel`（`SyncPayload::FileTransferCancel{ intent_id }`）→ 手机中止对应 HTTP 会话；手机中途失败回 `IntentFail{ intent_id, offset }`（接收端即断点真源，重试 = 桌面重发 intent，手机从 offset 续传）。

### 3.3 responder 状态机（mobile 侧，内存，不持久化）

```
Received → (question) → Approved → Executing → Completed
                   └→ Rejected → (通知)
Executing → Canced / Failed{offset} → 桌面重发 intent → Executing(from offset)
```

- Received→Executing 直接走（accept 策略/自主 pull）；`push+ask` 时先走审批问答（§4.1）。
- 断线：WS 重连后桌面查状态（offset 查询走阶段 ③ 状态同步，与既有断线重连一致）。

### 3.4 阶段 ② 测试矩阵

| 层 | 必测点 |
|---|---|
| wire | 两端 `enum` 新增 variant serde 往返 + `action` 字符串（对齐 §5.1 现测试模式） |
| responder | intent 分发（并发 3）、ACK 回执、cancel 中止、fail 偏移上报 |
| 宿主 | desktop `sync_handler` / mobile `handler/file_service.rs` 各新增路由分支 |
| 命令验证 | 两端 `cargo test` + gradlew Kotlin 编译 |

## 4. 阶段 ③：审批触发点重构 + 桌面协调者化

### 4.1 评审差距 2 落定：审批规则 = 只有上传需要落盘方审批（用户已拍板）

**定案规则（一句话）**：审批只发生在「上传」方向（文件被写入对方存储）的**落盘方**；「下载」方向一律免审批。自洽性：下载场景的发起人 = 落盘方本人（手机自主下载落盘手机=本人；桌面 pull 落盘桌面=本人），自己批准自己无意义；上传场景落盘方是**对方**用户（手机上传落盘桌面、桌面推送落盘手机），才需要对方授权——正是 v2「接收端宿主仲裁」的语义在新的全手机发起拓扑下的落位。

| 业务场景 | 协议方向 | 落盘方 | 是否需要审批 | 落定设计 |
|---|---|---|---|---|
| 手机自主下载桌面文件 | 下载 | 手机（发起人本人） | ❌ 免审批 | 直接执行 |
| 手机自主上传给桌面 | 上传 | 桌面（对方用户） | ✅ **桌面审批**（v2 机制完整保留：ask→桌面临时批卡→approve/reject→`TransferApproval` 推送） | 手机 POST `/transfer-request` → 桌面批卡 → 批准后手机继续（wire 原样复用 v2 §2.1） |
| 桌面推文件给手机（intent{push}） | 上传 | 手机（对方用户） | ✅ **手机审批**：ask → 手机弹确认（前台对话框）/ 通知 action（后台）→ **用户接受后手机才发 `IntentAck{accepted}` 并执行 GET**；accept → 直接 ACK+执行；reject → `IntentAck{rejected}` | 手机侧接收策略复用手机插件 `receiving_policy`（v2 §8.1 已有），触发载体从「HTTP 端点」换成「intent 消息」；ask 确认 = 响应器层 Approved 门，不走 v2 宿主批状态机 |
| 桌面下载手机文件（intent{pull}） | 下载 | 桌面（发起人本人） | ❌ 免审批 | 手机仅发**信息性通知**「桌面正在拉取 N 个文件」（无 action 按钮、不阻塞执行）；桌面直接执行 |

**防绕过改写**（原「ask 模式强制批上下文」）：

1. **push+ask 门**：手机是唯一需要防「无用户确认的数据流入本机」的一方——ask 策略下手机在收到 `IntentAck{accepted}` 前**不得**执行 GET（responder 状态机 Received→Executing 之间插 Approved 门）。
2. **pull 的批上下文自批准**：pull 数据流 = 手机 POST 桌面上传引擎，会撞上桌面 ask 策略的「无已批准批 ID 的 session 创建 403」。**桌面在发 `intent{pull}` 前在桌面宿主 registry 内部自建 approved 批（零用户交互——审批人就是桌面用户本人），`batchId` 随 intent 下发，手机 POST upload 时携带 → 桌面 gating 通过**。这保持 v2 防绕过语义（session 创建必须带已批准批），又不引入冗余交互。
3. **push 数据流（手机 GET）无批**：Range 无状态、无 session 创建，不需要批上下文。

**旧语义清理**：手机端 `registry.check_batch` 的 ask 403 逻辑随 server 删除（阶段 ④）自然移除；桌面端 check_batch 保留，gating 语义从「防手机用户绕过」变为「桌面（唯一接收端宿主）自批准 + 对端监督」。

### 4.2 评审差距 3 落定：桌面从「数据驱动者」退为「协调者」

桌面 UI 的进度/队列/速度全部依赖手机经 WS 回传（`transfer_progress`）。兜底设计：

| 风险 | 兜底 |
|---|---|
| 手机退后台/被杀，进度停更 | 桌面任务卡显示「对端离线」状态（`peer offline` 事件已有）+ 进度冻结文案；重连后经状态查询（offset）恢复 |
| 回传滞迟 → 进度抖动 | 桌面 UI 进度采用**乐观更新**：intent 发送即置 0%→以 ACK offset 校正→progress 事件覆盖；非实时刷新不闪跳 |
| WS 抖动的控制面影响 | 数据流不依赖 WS（阶段 ② 已按 ADR 0021 保证）；仅进度/取消受影响，重连后续传 |

**心跳**：手机执行中每 10s 若无 progress 则发 `transfer_heartbeat{ intent_id }`（或复用 progress 同通道，字段 `kind: "progress"|"heartbeat"`）；桌面 30s 无任何回传 → 判定对端失联 → 任务转「暂停-待续传」（沿用 01 策略），重连后状态同步触发 offset 查询续传。

### 4.3 桌面任务模型切换（desktop 插件 `state.rs`）

- 桌面「下载手机文件」「推文件给手机」任务的执行路径从「reqwest 直连手机 HTTP 端点」改为「发 intent → 收 ACK → 收 progress」三步。
- 任务五态（v2）不变；新增「intent 已发送（等待回执）」瞬时态，ACK 到达即转 queued/transferring。
- `peer offline` 时 intent 不可发（沿用 v2 §8.4 断线边界）；重连后重发 = 重试。

### 4.4 桌面宿主（file_service_controller）零新增端点

评审 13 已确认：桌面端点原样服务手机。仅需：
- `CreateUploadRequest` 已含 `batchId`（v2 已实现）；
- 新增 intent 消息的路由处理（`server/ws/terminal_ws.rs` handle 分支 → 转发 `SyncPayload::FileTransferIntent`）。

## 10. 风险与注意

- **审批规则已定案**（用户拍板）：只有上传需要落盘方审批（手机上传→桌面批卡；桌面推送→手机确认）；下载均免审批（pull 手机仅信息性通知、无拒绝门）。pull 的 ask 批量上下文用「桌面自批准批」解决（§4.1）。
- 两端 endpoint 已分化（手机 SAF/client，桌面 controller），**不要假设同构粘贴**；批逻辑共用但落点/执行分开。
- 手机端既是执行者又是接收端（push 时）：**游标真源 = 接收端已写字节**——push 的断点真源在手机（`IntentAck.offset`），pull/自主上传的断点真源在桌面（session received-offset）；两端语义不可混。
- progress 载荷扩展须 `#[serde(default)]` 兼容 v2 载荷（桌面旧版任务面板不受影响）。
- Kotlin `Intent` 通知 action 与 v2 批应答 action 并存：PendingIntent extra 需区分 `kind=batch` / `kind=intent`，路由到不同命令。
- `.scratch/`、`docs/` 受 git hooks 保护：本方案（开发分支）正常跟踪；提交按 AGENTS.md 流程。
- 阶段 ④ 删除 actix-web 后 `cargo test` 的集成测试（`tests/file_server_http.rs`）需同步删除/改写为 client 栈测试——提前规划，避免删除时测试缺口。
