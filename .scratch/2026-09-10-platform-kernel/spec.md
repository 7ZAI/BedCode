# 无业务底座内核（Businessless Kernel）+ 全业务插件化 架构演进规格

Status: ready-for-agent（**终态愿景，暂缓实施** —— 渐进次序见 `.scratch/plugin-kernel-roadmap/spec.md`；核心业务暂留宿主侧，本规格不立即执行）
Date: 2026-09-10
决策来源: 架构探索会话（同日）。地基为 `docs/adr/0022-plugin-host-interface-primitive-boundary.md`（裁剪线）、`docs/adr/0017-plugin-inter-plugin-call-gate.md`（插件互调）、`docs/adr/0019-wasmtime-version-locked-across-ends.md`（锁版）。术语以 `CONTEXT.md` 为准。子规格 `.scratch/mdns-service-plugin/spec.md` 为本愿景的首个试点。

## Problem Statement

BedCode 当前的底座内核**混杂了两类东西**：一类是「应用无关的引擎原语」（进程、网络、存储、安全、通信），一类是「产品业务」（会话、设备连接、终端交互）。业务概念锁在内核里，导致底座无法作为**通用应用平台**扩展——任何新应用（不只是远程终端）都必须改内核，而不是作为一个插件挂载上来。

具体表现：

1. 「会话」这个产品概念与「PTY 进程 + 输出流」这个引擎原语耦合在 `session/` 与 `pty/` 中，第三方无法在不改内核的前提下定义新的「会话语义」。
2. 「设备连接」的编排（配对流程、设备列表、设备名、能力通告）与「JWT/密钥/TLS/信任存储」耦合，第三方无法替换连接编排。
3. 内核每多一个产品概念，底座就离「可扩展任意应用」远一步——而这是 BedCode 未来作为平台的核心价值。

本规格确立目标架构：**底座内核保持零业务（只含应用无关的通用引擎原语 + 安全边界 + 运行时），所有产品业务（含会话、设备连接、终端交互）全部插件化。** 未来任何应用作为插件挂载到底座上，内核无需改动。

---

## Solution

底座内核收敛为「五类通用引擎 + 运行时 + 安全边界」，彻底移除产品概念；当前内核里的「会话 / 设备连接 / 终端交互」拆解为「引擎原语（留内核）+ 业务插件（下沉）」。

**无业务内核的精确清单**——内核只留这些，不含任何产品语义：

1. **运行时**：wasmtime Engine/Store/Instance 生命周期、Component Model 接线、trap/backtrace、燃料预算。
2. **进程原语**：spawn 进程（PTY 是其中一种伪终端模式）、写 stdin、读 stdout/stderr 流、信号/生命周期（kill、退出码）。这是「进程」，不是「终端」。
3. **网络原语**：HTTP 服务器（监听 + 路由分发到插件 handler）、WebSocket 连接（建立、帧收发、连接注册表）、TLS、链路加密、mDNS（广播/浏览原语）。
4. **存储原语**：SQLite 引擎、文件系统、KV 存储。
5. **通信原语**：插件消息总线（pub/sub）、插件互调 gate（JSON-RPC 2.0，ADR 0017）。
6. **安全边界**：密钥（X25519/RSA/AES）、JWT 签发/校验、信任存储、权限管理器、审批闸门。

「会话 / 设备连接 / 终端交互」全部下沉为**内置插件**（默认启用），等价替换当前内核里的业务语义；用户可停用即主动关闭对应能力。

## User Stories

1. 作为一个第三方开发者，我想在 BedCode 底座上构建一个非终端类应用，从而复用进程/网络/存储/安全能力而无需改内核。
2. 作为一个产品负责人，我想底座内核保持零业务、长期稳定，从而让内核 ABI 不再随任何业务迭代漂移。
3. 作为一个插件开发者，我想通过通用进程原语启动任意命令，从而构建「调度器」「自动化」「终端」之外的任意进程类应用。
4. 作为一个插件开发者，我想通过通用网络原语建立连接，从而构建「投送」「同步」「隧道」等任意网络类应用。
5. 作为一个用户，我想停用「会话」插件从而关闭远程终端能力，而不影响底座上的其他应用。
6. 作为一个架构维护者，我想「会话」作为一个可替换的内置插件存在，从而未来可以引入完全不同的会话语义而不动内核。
7. 作为一个插件开发者，我想通过通用存储原语持久化自己的数据，从而不依赖任何产品级表结构。
8. 作为一个插件开发者，我想通过安全边界能力证明自己的身份、建立信任，从而在底座上安全地与其他插件/节点协作。
9. 作为一个移动端用户，我想底座应用仍能开箱即用地提供远程终端，从而内置插件默认启用保证核心体验不回退。
10. 作为一个架构维护者，我想「设备连接」编排（配对流程/设备列表）作为插件存在，从而可以替换连接 UI 与流程而不动 JWT/密钥内核。
11. 作为一个插件开发者，我想通过输出流原语订阅任意进程的输出，从而构建「日志监控」「输出解析」等应用。
12. 作为一个架构维护者，我想内核的进程原语对 PTY 与普通子进程一视同仁，从而底座通用到可支撑任意进程形态。
13. 作为一个架构维护者，我想「无业务内核」的边界由一份权威清单定义，从而后续任何「该不该进内核」的判断都有唯一真源。
14. 作为一个插件开发者，我想通过插件互调复用其他业务插件提供的服务，从而组合出新的应用形态。

## Implementation Decisions

### 裁剪线的完整表述（本文档的架构地基）

**内核只承载「离开底座就无法实现、且与任何具体应用无关」的通用引擎能力；一切产品概念（含会话、设备连接、终端交互）都是业务，一律插件化。** 唯一的例外是「安全边界」——它携带语义（谁可信、谁有权），但那是**安全语义**而非**业务语义**，必须留内核，不得下沉。这是对 ADR 0022 裁剪线的完整化：ADR 0022 已确立「原语无业务语义」，本文档把这一原则推广到产品核心概念本身。

### 无业务内核清单（权威真源）

- **进程原语**：spawn（PTY 与普通子进程同构，PTY 只是 spawn 的一种模式）、stdin 写入、stdout/stderr 流订阅、信号/kill/退出码。内核不携带「会话」「配置」「预设任务」概念。
- **网络原语**：HTTP 服务器（监听 + 通配路由分发到插件 handler）、WS 连接管理（注册表、帧、心跳、重连）、TLS、链路加密、mDNS（browse/advertise 原语）。内核不携带「设备」「配对」「发现列表」概念。
- **存储原语**：SQLite 引擎、文件系统、KV。内核不携带「会话配置表」「传输历史表」等任何产品级 schema。
- **通信原语**：消息总线（topic pub/sub）、插件互调 gate（JSON-RPC，ADR 0017）。
- **安全边界**：密钥、JWT、信任存储、权限、审批闸门。
- **运行时**：wasmtime 全套生命周期。

### 当前内核模块的拆解映射

| 当前内核模块 | 拆出「引擎原语」（留内核） | 拆出「业务」（下沉为内置插件） |
|------------|--------------------------|------------------------------|
| `session/` + `pty/` | 进程 spawn、stdin/stdout 流、信号、输出分发管道 | 会话配置 CRUD、生命周期编排、会话列表/详情、终端 UI/渲染/工具栏/输出解析 |
| `utils/auth/` + 认证控制器/服务 | JWT 签发/校验、密钥、TLS、信任存储、连接注册表 | 配对流程、QR 展示、设备列表派生视图、设备名/能力通告解读 |
| `server/session_*` 服务 | WS 帧收发、连接管理 | 会话控制编排、会话订阅语义 |

### 业务插件（内置 + 默认启用）

- `com.bedcode.session` —— 会话业务：配置语义、生命周期编排、列表/详情，消费进程原语与输出流原语。
- `com.bedcode.terminal` —— 终端业务：PTY 会话的 UI 渲染、工具栏、命令面板、输出解析，消费进程原语与通信原语。
- `com.bedcode.devices` —— 设备连接编排：配对流程、设备列表、能力通告解读，消费 mDNS 原语与安全边界。
- `com.bedcode.mdns` —— 设备发现服务（`mdns-service-plugin` spec 的首个试点），向其他业务插件提供统一发现服务。

### 兜底语义的等价替换

「核心体验开箱即用」不再依赖内核启动流程，而依赖**内置插件默认启用**：会话/终端/设备连接插件随应用分发、默认启用；用户停用即主动关闭对应能力。内核「无业务」的代价由「内置插件默认启用」承担，与 mDNS 试点同一模式。

### 性能热路径的边界（关键红线）

进程输出流（stdout 高频逐帧）的**分发**（广播通道、缓存、多端订阅回放）是引擎原语，必须留内核——WASM 每帧进出开销不可接受。插件化的是输出的**消费与渲染**（解析、格式化、UI），而非分发。因此「会话业务插件」消费内核的输出流原语，但内核保有分发管道。任何「把输出分发下沉到插件」的尝试都违背性能红线，明确禁止。

### 不可重入约束的推广（关键工程约束）

会话生命周期事件与插件回调存在不可重入（wasmtime Store 不可重入、tokio RwLock 不可重入），当前以「wasm 调用内预生成句柄、实际创建 spawn 异步执行、事件在调用返回后分发」化解。业务下沉后，该模式推广为**内核事件分发的统一约束**：所有会回灌插件实例的内核事件，一律在 wasm 调用返回后异步分发，禁止在调用栈内同步回灌。

### 分阶段演进路径

- **Phase 1（本愿景固化 + 试点）**：确立无业务内核清单为权威真源；完成 `mdns-service-plugin` 试点（已验证「内核原语 + 服务插件 + 消费者互调」模式）。
- **Phase 2（服务插件模式推广）**：`com.bedcode.devices` 下沉（设备连接编排插件化，安全边界留内核）。
- **Phase 3（会话/终端下沉）**：`com.bedcode.session` / `com.bedcode.terminal` 下沉，进程原语与输出分发留在内核。此阶段风险最高，需先完成输出分发管道的「内核保有 + 消费插件化」验证。
- **Phase 4（内核冻结）**：五类通用引擎 + 安全边界 ABI 冻结，内核不再随业务演进；后续任何应用作为插件挂载。

### 双端与锁版

- 所有原语 WIT 变更双端同步 bump ABI（ADR 0019）；wasmtime 版本两端锁死，本演进不升级 wasmtime 与 wit-bindgen 组合。
- 移动端能力域可与桌面端分化（已有先例：移动端刻意无 session 能力），但同名词义保持对齐，传输机制（组件模型）两端一致。

## Testing Decisions

- **只测外部行为，不测实现细节**：断言「进程原语 spawn/输出流」「业务插件的会话生命周期/设备列表」「互调调用的请求/响应形状」，不断言内核内部结构。
- **主 seam = 引擎原语 + 插件互调 gate**：以「业务插件消费内核原语 + 互调其他服务插件」为测试主接缝；内核原语自身以单测覆盖（进程原语、输出流、权限门禁）。
- **模块覆盖**：
  - 进程原语（spawn 普通子进程与 PTY、stdin 写入、输出流订阅、kill/退出码）。
  - 输出分发管道（高频逐帧分发、多端订阅、缓存回放——内核保有行为不变）。
  - 业务插件（session/terminal/devices）的编排行为，经互调 gate 观察。
  - 安全边界（JWT、密钥、信任、权限、审批闸门）不因业务下沉而有任何回退。
- **先例**：host-mdns / host-session 既有单测、peer-net 集成测试、ADR 0017 插件互调 scheduler 测试。
- **回归门槛**：每个 Phase 完成后，既有功能（远程终端、文件传输、自动任务）行为等价——内核拆解不得产生功能回退。
- **编译级验证**（`AGENTS.md` Done When）：`cargo test`、`pnpm run test:run`、i18n 双端同步、`frontend-styles` 自查。

## Out of Scope

- **内核引擎本身的插件化**（wasmtime 运行时、进程 spawn、SQLite、TLS、JWT/密钥/信任）——引擎原语与安全边界永远留内核，任何尝试均违背裁剪线，明确不做。
- **输出分发管道的下沉**——性能红线，禁止下沉，只开放消费/渲染插件化。
- **移动端完整业务插件实现**——移动端同步 WIT 契约，完整业务插件逻辑按需再上。
- **具体未来应用的实现**（投送、同步、隧道、OCR、调度等）——本规格只确立「它们作为插件挂载」的架构，不实现任何具体应用。
- **本规格是架构演进愿景**——具体下沉的每个业务插件（session/terminal/devices）应各自独立立项 spec，本规格只定边界与路径。

## Further Notes

- **本规格统领 `mdns-service-plugin` 试点**：mDNS 是「内核原语 + 服务插件 + 消费者互调」模式的第一个验证，成功后同模式推广到 devices/session/terminal。
- **「无业务」的精确含义**：内核保留的是「应用无关的通用引擎」，不是字面的「什么都不做」。「进程、网络、存储、安全、通信」五类是任何应用的地基，它们不是业务。
- **安全边界的例外性**：JWT/密钥/信任是唯一「携带语义但必须留内核」的部分，因其是安全语义而非业务语义；任何把安全边界下沉的提议都直接否决。
- **内置插件与第三方插件同构**：会话/终端/设备连接插件与 ai-chatbox/file-transfer 无形态差异，只是「内置 + 默认启用」，这保证「替换核心业务」与「新增任意应用」走同一条路。
- **风险提示**：Phase 3（会话/终端下沉）是本愿景最高风险段——输出热路径与不可重入约束在此交汇。若该阶段验证「输出分发必须留内核」与「业务插件消费」之间存在无法调和的开销，应回退为「会话/终端保留为内核稳定面、只开放扩展点」，但这不否定 Phase 1/2 已确立的「服务插件」架构价值。
