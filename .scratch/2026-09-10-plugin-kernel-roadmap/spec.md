## 目标与基线

**最终目标**（见 `platform-kernel/spec.md`）：底座内核零业务——只含「五类通用引擎（进程/网络/存储/安全/通信）+ 运行时」，所有产品业务（会话、设备连接、终端交互、文件传输、AI……）全部插件化，未来任意应用作为插件挂载。

**当前基线**（本路线图起点，冻结不动）：

- 核心业务**留在宿主侧**：会话管理、终端（PTY）、设备连接/认证（JWT/密钥/配对）、对等网络连接引擎——本轮演进**不触碰**。
- 已插件化的能力**保持现状**：HTTP 入站/出站、数据库（主库前缀隔离 + 插件独立库）、会话生命周期/输入行扩展点。
- 已落地的内核基础能力服务：mDNS（`MdnsService`：browse/advertise 原语 + 属主定向事件投递，2026-09-15 双端验收）。

## 渐进原则

1. **小步增量**：每阶段只做「一件事」，不做跨领域的大改。

> **原则 1 / 2 的一处已记账例外（2026-09-20）**：阶段 2 与阶段 3 的会话部分被**主动合并
> 执行**，打破了「每阶段只做一件事」。理由与代价见「合并执行」节——这不是遗忘原则，
> 而是在两处 ABI 开窗、两次 UI 迁移、两次 i18n 冲突处理可以一次性付清时选择了合并，
> 风险改由纵向 tracer-bullet 切片与既有测试接缝（S1 宿主真实 wasm 闭环 / S2 跨端协议
> 集成）吸收，而不是由「流程假设它是安全的」吸收。原则本身对后续阶段仍然有效。
2. **每步可验证、可回退**：任一阶段完成后独立编译 + 测试通过；回退只影响该阶段，不牵连基线。
3. **先基础设施、后产品核心**：先啃「通用引擎能力」的插件化（mDNS 是最薄、最中性的一块），验证模式后，再逐步逼近「产品核心」（设备连接、会话、终端）。
4. **核心业务冻结**：会话/终端/设备连接在下文明确阶段之前，禁止下沉——保持基线稳定。
5. **单一试点先行**：用一个能力跑通「内核基础能力服务 + 插件消费」完整模式，后续能力复用同一模式，不各自发明新套路。该模式已由 mDNS（MdnsService）验证；「WASM 服务插件」形态经 mDNS 试点评估后否决——引擎性、多消费者、无产品语义的能力留内核作基础服务更合适。

## 路线阶段

### 阶段 0 —— 基线冻结（已完成）

核心业务留宿主侧，只做文档与边界固化。产出：本路线图 + 终态愿景 + mDNS 基础能力服务规格。

### 阶段 1 —— mDNS 基础能力服务（✅ 已落地，2026-09-15 双端验收）

**决策变更（2026-09-15）**：mDNS **不再完全插件化**（v1「服务插件试点」方案作废，见 `2026-09-10-mdns-service-plugin/spec.md` 的 superseded 标记），改判为**内核基础能力服务 `MdnsService`**——与 host-http / host-database 同构，引擎性、多消费者、无产品语义的能力留内核作基础服务，经 WIT 原语供插件调用。实施规格：`2026-09-10-mdns-service-plugin/spec-basic-capability-service.md`（v2，Status: implemented）。

落地内容：

- **内核**：`host-mdns` 契约升级为 browse + advertise / stop-advertise / is-advertising 纯原语；`MdnsService` 全局单例共享 ServiceDaemon（消灭双 daemon 同绑 5353 互抢病灶）、BROWSERS/ADVERTISERS 属主句柄表、事件定向投递 `mdns:found.<owner>` / `mdns:lost.<owner>`（owner = 发起 browse 的插件 id）、周期 re-announce 续期、`purge_for_plugin` 回收；peer-net 引擎经同守护登记 host 身份（零业务代码红线 D3）。
- **消费侧**：file-transfer 迁移为定向 topic 订阅 + 自建设备缓存（设备列表派生视图下沉插件侧）；宿主 DiscoveryCache、全局 `mdns:found`/`mdns:lost` 桥接与缓存重发通道整体退役（D1）。
- **平台与安全**：Android MulticastLock 随单守护首次使用获取、常驻持有（幂等）；ADR 0022 v4 补记（D5）。

**验收门槛（已达成）**：对等网络集成测试全绿；发现、在线判定、能力通告行为等价无回退；双端 cargo test / eslint / i18n 全绿。

### 阶段 2 —— 设备连接编排下沉（原 `com.bedcode.devices`，✅ 已落地：形态改判为合并进 `com.bedcode.session`）

在阶段 1 确立的模式上，把「设备连接**编排**」下沉为内置插件：配对流程、设备列表派生视图（模式已由 file-transfer 插件侧设备缓存示范）、设备名/能力通告解读、QR 展示。**安全边界（JWT/密钥/TLS/信任存储）与连接注册表留在内核**。

> **落地形态改判（2026-09-20）**：设备编排没有独立成 `com.bedcode.devices`，而是与阶段 3
> 的会话/任务域合并为单一 `com.bedcode.session`（理由见「合并执行」节）。语义本体不变：
> 配对码 / QR 的 TTL 与生命周期编排、派生视图（在线判定 + 真实会话数 + 任务状态合并）、
> consent 决策编排全部在插件侧；`pairings` / `connection_history` 两张表、JWT 签发验签、
> 密钥托管、连接注册表按上表留在内核，插件经 `host-auth` 记录面（v18）读内核原始记录。

| 动 | 不动 |
|----|------|
| 配对流程编排、设备列表、能力通告解读 | JWT 签发/校验、密钥、TLS、信任存储、连接注册表 |

**前置条件**：✅ 已达成（阶段 1 于 2026-09-15 落地并验收）。

**实施范围（2026-09-18 决策）**：**仅桌面端先行，移动端暂停推进**——`com.bedcode.devices` 只在桌面端实现并验收；移动端作为消费端暂不迁移（其设备列表 UI / 配对流程 / 扫码链路保持宿主现状，随移动端需要另行立项，不与桌面端绑定推进）。桌面端下沉不要求移动端同步 WIT 契约变更（宿主侧编排不触双端协议；若下沉过程确实需要动 WIT/ABI，仍按 ADR 0019 双端同步评估，但预期不涉及）。

**前置内核工程（2026-09-18 决策）**：**wasi2 → wasi3 全量升级**（宿主运行时 async 化 + SDK 切 wasm32-wasip3 + wasmtime 47 → 48 LTS 双端升级）作为阶段 2 的独立前置工程 A0，详见 `.scratch/2026-09-18-devices-plugin-scope/auth-center-spec.md` §4 A0；认证中心插件直接基于 wasi3 构建。

### 阶段 3 —— 会话 / 终端下沉（✅ 会话 2026-09-20 落地、终端 2026-09-22 落地；延续规格 `.scratch/2026-09-21-terminal-into-session-plugin/`）

**本愿景最高风险段**，最后执行。会话业务（配置语义、生命周期编排、列表/详情）与终端业务（UI 渲染、工具栏、输出解析）下沉为内置插件。**进程原语（PTY spawn、stdin/stdout 流、信号）与输出分发管道留在内核**（性能红线经 2026-09-21 修订，见 ADR 0022 v23：输出字节禁止经 JSON 命令通道搬运，**经 WIT 二进制原语可进 WASM**）。

| 动 | 不动 |
|----|------|
| 会话配置语义、生命周期编排、会话列表/详情、终端 UI/渲染/输出解析 | 进程 spawn、输出分发管道、信号、会话状态机引擎 |

**前置条件**：阶段 2 完成；输出分发管道的「内核保有 + 消费插件化」先行验证通过。
**✅ 2026-09-21 验证通过**（`.scratch/2026-09-21-terminal-output-consumer-perf/report.md`：

ADR 0022 v23（详见其「终端输出消费插件化 · 性能红线修订」节）。

**落地状态（2026-09-20，票 01–18 验收）**：**「会话」一半已落地**——会话配置语义（真源

### 阶段 4 —— 内核冻结

五类通用引擎 + 安全边界 ABI 冻结，内核不再随业务演进。后续任何应用作为插件挂载，内核零改动。

## 合并执行（阶段 2 + 阶段 3 会话部分，2026-09-20）

**做了什么**：三个产品域（设备与配对 / 会话编排 / Agent 任务）合并进**一个**内置插件
`com.bedcode.session`；原计划的两个插件 `com.bedcode.devices`、`com.bedcode.auto-task`
先后退役（后者连同其 6 张任务表与 4 个 agent hook 脚本一起搬入，私有库跨库一次性搬运）。

**为什么合并（收益）**：

- 省掉两次 ABI 开窗（阶段 2 一次、阶段 3 一次）、两次 UI 迁移、两次 i18n 命名空间冲突处理。
- 「设备—会话—任务」是同一件事的三元事实（哪台设备、哪个会话、什么状态），拆在两个插件里
  要靠互调 api 与宿主桥接维持一致性；合并后是同一份私有库、同一次 tick、同一套广播。
- 内核去业务化在这一步真正完成：会话记录里不再有任何任务语义字段。

**代价与吸收方式**：

| 代价 | 吸收 |
| --- | --- |
| **故障半径扩大**（D7 是本批次最大风险项）：配对侧 trap 会连带会话编排与任务 tick 一起停 | 四条硬性补偿：认证路径保留宿主降级 + `warn` 留痕；三域各自 `Result` 边界、禁止跨域持锁、tick 分域计数失败只降级本域；activate 分段（建表→订阅→恢复）任一步失败落 `Degraded`；UI 贡献面 error 态整组摘除 + 宿主兜底壳。均有行为测试（票 18 §2） |
| 回归面变宽（一次改三域） | 纵向 tracer-bullet 分 18 张票（P0 prefactor → P5 回归），每张票自带门禁；S1 宿主真实 wasm 闭环 + S2 跨端协议集成测试断言零改动 |
| 阶段划分的「可回退」变弱（不能只回退阶段 2） | expand–contract 排程：插件 id 改名（04/05→06）、任务字段→注解槽（11→12）、旧 HTTP 前缀双投（16→17）各自分两步落，任一步可单独回退 |
| 双端同步原则被破 | 经用户 2026-09-19 授权**豁免本规格范围内**的 §9「协议改动两端同步部署」；自守边界是线协议形状不变。受损项与恢复动作见下一节，**不许只留在 spec 里** |

## 回退与风险控制

- **阶段 1 形态决策**：mDNS 经试点评估否决「WASM 服务插件」形态（引擎性/多消费者/无产品语义能力留内核更合适），以基础能力服务落地；该形态无独立回退路径（能力本就在内核），对等网络发现不受阶段 2/3 影响。
- **阶段 2 风险**：设备列表从「内核常热」变「插件激活才有」，靠内置插件默认启用 + 持久化 last-seen 缓存缓解（同 mDNS spec 处理）。
- **阶段 2 + 阶段 3（合并执行）的实际风险落在 D7 故障半径**：三域同实例后，配对侧 trap 会连带会话编排与任务 tick 一起停。补偿是四条硬性验收（认证降级 + `warn`、分域 `Result` 边界与 tick 分域计数、activate 分段落 `Degraded`、贡献面 error 态整组摘除 + 兜底壳），并**实测留档**（票 18 端到端回归 + 摘除/恢复行为用例），不靠流程假设。若实现期发现认证兜底与桥接超时互相放大，回退备选是「设备域留独立 headless 认证中心、只并会话与任务」——该备选在本批次未被触发（认证桥接探活锚点与降级门是同一处判据，不存在双判据打架）。
- **跨私有库数据的回退窗口**：票 16 的库内改名带账本可逆向改回旧名（零复制）；票 17 的跨库搬运是**追加式**（`INSERT OR IGNORE`，旧库文件本身不动），回退只需停用新插件并用旧版本重启——旧 auto-task 私有库里的行仍在。旧插件工程目录已随票 17 退役，回退需从 git 恢复该目录（`96d9aef1b` 及其前）。
- **阶段 3 最高风险**：若「输出分发必须留内核」与「业务插件消费」之间出现无法调和的开销或不可重入冲突，**回退为「会话/终端保留内核稳定面、只开放扩展点」**，但此回退不否定阶段 1/2 已确立的「内核基础能力服务 + 内置业务插件」架构价值（见 `platform-kernel/spec.md` Further Notes）。
