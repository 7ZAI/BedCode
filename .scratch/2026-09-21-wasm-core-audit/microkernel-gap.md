# 作为微内核，还缺哪些功能要素

Status: needs-info（判断与差距清单已成型；标注「待立项」的要素需用户裁决优先级后才转票）
Date: 2026-09-21
判定基准: `.scratch/2026-09-10-platform-kernel/spec.md`（无业务内核权威清单 + 阶段 4 冻结）+ `.scratch/2026-09-10-plugin-kernel-roadmap/spec.md`（阶段 0-4 现状）+ 通用微内核判据（IPC/IDL/能力/服务端可换/故障隔离/资源账目/生命周期/版本治理）。

## 1. 先给衡量标准，再谈差距

不拿 Mach/microOS 的教科书清单当目标，用三条**本平台自己需要的**判据衡量「是不是微内核」：

| 判据 | 含义 | 当前 |
| --- | --- | --- |
| **A 挂载性** | 新应用作为插件挂载，内核零改动 | 🟡 能挂载，但要改 8-10 处手抄清单才拿得到新引擎面；系统组件路线零真实用户 |
| **B 边界不逃逸** | 任一插件被攻陷（或作者恶意）都不越界、不冒充、不耗尽他人 | 🔴 越界（P0-1/3/4）、冒充（P0-5）、耗尽（任务池）各有实证缺口 |
| **C 可问责** | 内核的行为、授权决策、资源消耗可观测可复盘 | 🔴 有产无消（monitor）、无审计流水、策略硬编码不可外部化 |

**结论**：运行时面（wasmtime 沙箱、资源上限、trap 自愈、实例串行）已达微内核水准；**通信面、授权面、账目面尚未成型**——即「有隔离、无边界治理」。缺的不是功能数量（21 组原语、28 个权限位很丰富），而是让这些声明**被强制、被派生、被记账**的三件事。

## 2. 已具备的要素（勿重复建设）

1. **运行时与故障隔离**：Component Model 加载、ABI 协商（上界拒载）、`catch_unwind` + trap 限频重载、Store 级 `ResourceLimiter` + 燃料续费、AOT 产物落宿主目录。
2. **引擎原语面**：进程 3 / 网络 4 / 存储 4 / 宿主面 8 / 互调 2 共 21 组，且经 ADR 0022 裁剪线审过「无业务语义」。
3. **IDL 单源雏形**：`packages/plugin-sdk-*/rust/wit/bedcode.wit` 是契约真源，bindgen 生成 guest/host 绑定。
4. **声明式扩展点**：`contributes`（commands/views/httpEndpoints/toolProviders/fileHandlers/configuration/lifecycle/provides）+ 前端贡献注册。
5. **传输解环**：`MessageDispatcher` / `PluginServices` 两处 trait 注入真实打破循环依赖，无 PluginHost 反引用。
6. **配额意识**：`PLUGIN_*_MAX_*` 普遍 fail-visible，不是静默截断。
7. **双端偏离治理**：ADR 0022「双端偏离」节 + roadmap 移动端受损清单，偏离是显式的而非暗账。

## 3. 缺失/半成品要素清单

### E1 强制 IPC 与命名空间（**最关键**）

微内核里 IPC 是唯一跨边界通道，因此**它本身必须是安全边界**。当前总线是唯一被 AGENTS §5 指定的插件间通道，却对 topic 无任何命名空间与 ACL（spec §4-P0-4）：owner 作用域 topic 靠命名约定，谁都能订阅与伪发布。
- **缺**：topic 命名空间（按属主/私有前缀物理隔离）、宿主定向投递的接收者校验、互调回复通道的 sender 校验。
- **落地**：票 05。

### E2 能力式授权（capability）而非自报权限位

现状是「manifest 自报权限 → 激活时全量授予 → 每次调用查位」。这只解决「有没有」，不解决三件事：**谁批准的**（桌面审批链未接线，P0-2）、**能不能转授/撤销**（`revoke_all` 存在但运行时不重判）、**权限从哪来**（`granted_permissions` 是只写不读的影子状态，真源只有内存 `PermissionManager`，无持久化授权记录）。
- **缺**：授权记录持久化 + 批准来源绑定内容哈希 + 高危位的运行时重判；进一步可演化为「宿主签发句柄即能力」（pty/ws/task 的 owner 句柄已经是这个形状，缺的是把它推广为统一模型）。
- **落地**：票 02（取消 `storage` 自动授予）、票 03（批准 ∩ 请求 + 钉扎）、票 04（句柄即属主）；「统一能力句柄模型」= **待立项 E2'**，建议等票 03 落地后评估，不要提前抽象。

### E3 服务端可替换性——微内核的立身之本，当前为零

`capability.rs` 实现了「能力名 → 宿主原语 / WASM 系统组件」二选一装配，但 `ROUTABLE` 只有 `host-storage`，且全仓无一个 `"type":"system"` manifest（spec §2）。也就是说：**内核原语目前只有「内核自己做」这一条路**，platform-kernel 终态愿景里「http 服务器 / 数据库 / mDNS 也是 WASM 组件、经 Linker 向内核提供能力」没有真实案例。mDNS 已改判留内核（2026-09-15），更说明这条线缺的是**验证**而不是机制。
- **缺**：至少一个真实系统组件（候选：把 `host-config` 或「设置项真源」做成可替换系统组件；或让 `auth-policy` 从「仅探测」升级为可路由能力），以及「宿主服务也能被声明依赖」的装配语义。
- **待立项 E3'**。不做这条，阶段 4「任意应用挂载」只剩「插件消费内核原语」一个方向，谈不上可替换内核。

### E4 契约派生与版本治理

WIT 是单源，但**围绕它的清单全是手抄**：`HOST_PRIMITIVE_CAPABILITIES` 字符串表、权限词汇三副本（28/22/24 实测漂移）、SDK `host/*.rs` 薄层、前端合法集。ABI 侧只有「上界拒载」，缺三样：最低支持版本策略、弃用窗口（v21 首次删接口函数但无 deprecation 期与告警面）、双端兼容矩阵产物。
- **缺**：从 WIT + SDK 派生 capability/权限清单（票 01 起步）、ABI 弃用告警（加载时对 `abi.version() < 当前支持窗口` 记 warn 并可查询）、双端契约矩阵生成物。
- **落地**：票 01 + **待立项 E4'**。

### E5 资源公平性与跨插件账本

单插件被攻陷不能拖垮他人——目前做不到：`host-task` 池是进程级 static（8 线程、无按插件配额生效的单元超时），一个挂死单元即可长期占槽；总线消费任务与 `dispatch_to_wasm` 共用 tokio worker（慢订阅者可放大）；燃料只计 guest 指令，**宿主调用阻塞不计**（文档已如实写明），所以「恶意/失控插件占住宿主线程」没有上界。
- **缺**：按插件的 CPU/时间片与并发配额（含宿主侧等待上界）、原语级超时默认值、跨插件公平调度。
- **落地**：票 09（单元超时 + 按插件并发上限）；宿主调用侧的统一超时闸门 = **待立项 E5'**。

### E6 可观测与审计闭环

三个断口：`MetricsRegistry::snapshot` 无消费者（票 10）；授权决策只 `warn`，**无可查询审计流水**（谁在何时被拒/被弹窗放行/读了哪个路径，事后无法复盘——AGENTS §8 只约束了不泄露凭据，没提供留痕面）；配置运行时覆盖层无入口（票 10）。
- **缺**：指标出口 + 诊断页 + 授权/拒绝审计流水（结构化字段，遵 §8，只记长度）。
- **落地**：票 10 + **待立项 E6'**（审计流水）。

### E7 依赖装配语义（版本、顺序、重启策略）

`dependencies` 只有能力名，无版本；启动顺序靠「`type:system` 先激活 + id 排序」的硬编码规则，插件无法表达「我在 X 之后启动」「X 挂了我怎么办」；崩溃后策略是全局节流重载，插件无法声明「失败即降级」「失败即停」。
- **缺**：依赖版本约束、显式启动序/失败策略（manifest 声明面）。
- **待立项 E7'**，量级小但对「替换核心业务」很关键（否则替换者无法表达自己必须先于消费者就绪）。

### E8 信任与分发链

桌面侧：无签名、无发布者身份、`downloader` 无 `wasm_hash`、无 zip 解压限额、批准与内容不绑定（P0-2）。「内置 vs 用户安装」的信任分档只写在文档与注释里，代码上仅体现为 `source` 字段与 dev 裁剪的 watcher。
- **缺**：票 03 的审批 + 钉扎；再往上是 ADR 0020「后续」段的签名链与发布者隔离、受信更新通道。
- **落地**：票 03 + **待立项 E8'**（签名链，独立 ADR）。

### E9 前端贡献面的隔离与身份

微内核把 UI 也是当插件面看。当前 `sandbox:'isolated'` 未实现、所有插件前端在 webview 内 inline 执行并可自报 `plugin_id` 调宿主命令（P0-5）——**内核最强的隔离（WASM）与最弱的隔离（同 webview JS）服务于同一批插件**，攻击者会选后者。
- **缺**：身份绑定（票 06）+ 对 `isolated` 形态的实现或明确放弃。
- **落地**：票 06 + **待立项 E9'**（真隔离：iframe + postMessage 桥，或明确「不做」并删字段）。

### E10 策略即数据（当前策略硬编码在代码里）

`.claude/` 子串免弹窗、两个插件 id 全盘免弹窗、`auth-policy` 传输失败回退放行、WS 端点默认证据、`/api/plugin/*` 无 JWT 放行——都是**代码里的策略**而非可配置可审计的数据。这既是票 07/08 的具体问题，也是微内核的一个通用要求：边界策略要能被运维与审计，不能只被编译。
- **落地**：票 07、票 08；「统一策略面」（一处声明所有边界默认值 + 可导出）= **待立项 E10'**。

## 4. 阶段 4（内核冻结）的前置顺序

冻结不是「不再写代码」，而是**契约、授权、账目三件事都能自证**。建议次序：

1. **先做（无裁决依赖）**：票 01 词汇单源 → 票 02 主库隔离 → 票 11 结构去重 → 票 04 属主闭环 → 票 05 总线 ACL → 票 09 任务超时与生命周期。这批把「判据 B 边界不逃逸」从红抬到黄。
2. **需先裁决再做**：票 03（审批时机/信任分档/高危位逐位确认）、票 06（身份绑定方式 + isolated 去留）、票 08（HTTP 认证档位 + 是否动线协议）、票 12（peer-net 归属）。
3. **然后才立项微内核要素**：E3' 系统组件真实场景（冻结前必须有，否则「无业务内核」只是删除了业务而没有替代机制）、E5' 宿主侧超时闸门、E6' 审计流水、E4' ABI 弃用治理、E7' 依赖装配语义。
4. **明确不做**：内核引擎自身插件化、输出分发管道下沉（性能红线）、把 mDNS 再改回插件（已裁决改判）。

## 5. 一句话总结

这套内核**已经是一个合格的 WASM 宿主运行时**，但还不是微内核：它给了插件「能做什么」的清单（21 组原语、28 个权限位），却没给「谁能对谁做什么」的强制（IPC 无 ACL、权限自报无批准、跨插件命名空间靠约定），也没给「谁做了什么、花了多少」的账目（monitor 无出口、无审计流水）。补 **E1/E2/E6** 三条，判据 B、C 才立得住；补 **E3**，platform-kernel 的「服务端可换」才从愿景变成有证据的架构。
