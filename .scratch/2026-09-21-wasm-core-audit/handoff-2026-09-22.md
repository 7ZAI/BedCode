## 3. 已完成三票：落地了什么（只写需要知道的结论）

### 票 01 — 权限词汇单源（prefactor，票 02-08 的前置）

- **唯一真源**：`bedcode-desktop/packages/plugin-sdk-desktop/rust/src/permission.rs`
  的 `PERMISSION_VOCABULARY` 反射表（`(stringify!(CONST), CONST)`），`VALID_PERMISSIONS` 由 `const fn` 派生。加权限位 = 改一行。
- **两份生成物**（都在仓库里、都不是手抄）：
  `packages/plugin-sdk-desktop/bin/permission-vocabulary.json`（打包 CLI 读）、
  `bedcode-desktop/src/plugin/permission.vocabulary.ts`（宿主前端读）。
  重跑：`cd bedcode-desktop/packages/plugin-sdk-desktop && pnpm run gen:permissions`
  （= `cargo run --manifest-path rust/Cargo.toml --example gen_permission_vocabulary`）。
- **锁**：宿主 `src-tauri/src/plugin/permission.rs` 五条（三副本集合相等 / 生成物标注且确被 import /
  **每条词汇都有门禁落点** / 生产 + fixture manifest 无死词汇 / validate 确在构建链）；
  前端 `src/__tests__/plugin/permissionVocabulary.test.ts` 五组。
- **加锁后任何「拆权限位 / 加权限位」都会被自动拦住**——这是本票存在的目的，后续票改词汇时必须重跑生成器，否则锁转红。
- 死词汇清零：file-transfer 去掉 `bus` / `fileservice` / `transfer`；`bus` 在 code-map 明确「不是桌面权限位」
  （移动端 SDK 有 `PERMISSION_BUS` → 双端分叉，ADR 0018，**不动移动端**）。
- `bedcode-plugin validate` 挂进 `bedcode-desktop/scripts/plugin-build.js`（规则在 `bin/manifest-validate.js`，CLI 与构建链共用）。

### 票 02 — 主库 SQL 隔离（P0-1）

- 边界从正则挪到引擎：`host_impl/database.rs::with_main_db_guards`
  在插件语句 prepare 期间装 `rusqlite::hooks::AuthContext` 仲裁（`hooks` feature 仓库早已开），
  只放行 `plugin_<id>_` 前缀表；主库五面（`db_execute` / `db_query` / `*_params` / `db_execute_batch`）走它，
  **私有库五面刻意不装**（一库一插件）。`validate_sql_table_prefix` 保留但**文档写明它不是边界**。
- 策略是**探针实测**定的，不是猜的（探针脚本已删，结论在票面实施记录）：
  DDL 必然隐式记账 `sqlite_master` / `sqlite_sequence`；`CREATE INDEX` 附带一条 `Reindex`；
  `ALTER TABLE` 内部调 `printf`/`substr`。所以目录表放行与否 = 「**语句自己有没有点名**」
  （`names_schema_catalog`：剥 `--` / `/* */` / 单引号字符串后按词元匹配；双引号/反引号/方括号**保留**在扫描内，
  因为 `"sqlite_master"` 正是规避形态）。
- `storage` **不再自动授予**；新增高危位 **`database:main`**（词汇 30 → 31）：
  主库面挂它，私有库/KV 仍挂 `storage`，两者互不代持（有 SDK + 宿主三态用例）。
- 消费者实测：四个桌面生产插件**只用 `plugin_db_*`**，主库面零生产消费者
  → AGENTS §7 已定档「仅第一方按需申请」。
- 契约收缩：`grant_permissions` 无默认位；被词汇表过滤的声明在 `host/activation.rs` `warn` 留痕。
- 移动端分叉（**不得静默**）：移动端 SDK 仍自动授予 storage、无 `database:main`。

### 票 04 — 会话/终端属主（P0-3）

- 内核加不透明表 `SessionManager::session_owners: session-id → 创建方 plugin_id`
  （`create_session_from_spec` 第 6 参 `owner`；随移除注销；**不进 DTO → 线协议零变化**）。
- 判定链固定 **权限门 → 参数门 → 属主门**：`session_close` / `remove` / `rename` / `resize` / `annotate` +
  `terminal_send`；文案 `not owner of session`（不回带真实属主 id）。
- `session_lifecycle_register` 此前**零权限**，现补 `session:read`。
- peer 句柄表补 `owner` 列；`peer_close` 的属主判定排在 `require_app` 之前，拒绝时 `restore_session` 放回。
- **两处需要接手者注意**：
  1. **注解槽没按票面字面做命名空间**（票 04 实施记录第 5 条有理由：槽的读路径喂内核对外 DTO，
     分命名空间会逼内核回答「`taskStatus` 取哪个插件」= 产品语义回内核）。达成的是「属主独占写入」。
     若将来要「多插件共享注解」，再引键形状并交插件层解释。
  2. **契约收缩**：未知会话 id 的 close/remove 从「静默幂等成功」变成「按非属主显性拒绝」。
     宿主错误串是英文，插件侧是否映成 i18n 文案**待实机确认**（票 04 登记为未做项③）。
- 关键前提（核实过，别推翻）：**所有会话创建（桌面 UI / 移动端 HTTP / 定时器）都经
  `com.bedcode.session` 的 `session-create` 编排**（`utils/session_create_bridge.rs`，插件必需、无宿主降级）
  ⇒ 该插件按构造就是全部会话的属主，所以属主门禁不打断产品路径。file-transfer 里的
  `session-remove/rename/resize` 只是 `#[plugin_api]` 防漂移镜像声明，无调用点。

- **一张票做完先提交再开下一张**；票据/spec 单独 `docs(scratch)` commit，实现各自一个 commit。
- commit message 用中文 conventional commits，**必须写实际跑过的门禁数字**（用户拒绝照抄票里的历史证据）。
