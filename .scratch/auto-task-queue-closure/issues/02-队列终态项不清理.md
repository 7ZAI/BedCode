# 队列终态项不清理（task_queue 数据累积）

Type: task
Status: needs-triage

## 背景

对 auto-task 插件任务队列状态机（`bedcode-desktop/plugins/auto-task/rust/src/queue.rs`）的闭环审查中发现：`task_queue` 表的**终态行（done / cancelled / interrupted）永久留存，从不清理**。

## 现状

队列项状态机终态有四个出口，全部只 UPDATE 状态、不删除行：

| 场景 | 终态 | 落库位置 |
|------|------|---------|
| 任务完成 | `done` | `try_dispatch_next`（`UPDATE task_queue SET status = 'done' WHERE status = 'executing'`） |
| clear 超时 ×3 | `cancelled` | `check_waiting_timeouts` |
| 会话异常结束 | `interrupted` | `interrupt_running_tasks_on_session_end`（state.rs） |
| terminal_send 失败 | `done` | `dispatch_task` |

`list_queue` 只查询 `status = 'pending'`，所以功能不受影响；但：

- 没有清理入口：`clear_queue`（`task-queue/clear`）只删 pending；无任何删除终态行的操作
- 无数据上限：无 TTL、无封顶（对比 file-transfer 插件 HistoryStore 有封顶 200 的归档设计）
- 历史数据已存在大量这类悬挂项（`interrupt_running_tasks_on_session_end` 的注释即提到"历史数据里存在大量这类悬挂项"——虽然它指 waiting/executing 残留，终态累积同理）

## 影响

- 表无限增长：长时间使用后 `task_queue` 行数持续膨胀（每次完成一个任务 +1 行），查询 `list_active_task` / `pending_count` 等带索引的查询影响尚小，但全表 UPDATE（如 `try_dispatch_next` 的 `WHERE status = 'executing'` 无 session 限定时会扫描）与磁盘占用会随使用时长恶化
- 状态机语义混淆：终态行与活动行混存，后续若做取消/重跑等扩展（见 issue 01），需要额外区分

## 建议方案（供实现者评估）

1. **入队时清理**：`add_task` 时顺带删除该会话的终态行（最简单，零定时器依赖）
2. **终态归档**：仿照 file-transfer 的 HistoryStore 模式，终态只保留最近 N 条（如 200），超限删除最旧
3. **定时清理**：宿主 scheduler-tick（已有 `auto-task.scheduler-tick` 定时器）周期清理超过保留期的终态行
4. 注意：删除终态行前需确认没有依赖方（移动端对账 `reconcile` 依赖队列中**存在** executing 项来匹配，终态行删除不影响对账；`interrupt_running_tasks_on_session_end` 查询的是 waiting/executing，也不受影响）

## 相关代码

- `bedcode-desktop/plugins/auto-task/rust/src/queue.rs`：`try_dispatch_next`（done 归档）、`check_waiting_timeouts`（cancelled）、`clear_queue`、`add_task`、`broadcast_queue_changed`
- `bedcode-desktop/plugins/auto-task/rust/src/state.rs`：`interrupt_running_tasks_on_session_end`（interrupted 兜底）
- 参考对照：`bedcode-mobile/plugins/file-transfer/rust/src/state.rs` 的 `HistoryStore::trim_to_cap`（封顶 200 归档模式）
