# Spec: 对等网络前端 UI 迁移至文件传输插件

Status: ready-for-agent

词汇表沿用 CONTEXT.md「对等网络」「文件传输」节；信任模型约束见 ADR 0028，传输栈见 ADR 0027。本 spec 是 `.scratch/peer-network/spec.md`（下称「父 spec」）的修正性后续：父 spec 落地时，对等网络的**服务层**正确落在宿主共享 crate，但其**前端页面与编排逻辑**被错误地内置进了两端宿主应用。本 spec 将这部分 UI 职责整体迁移到两端的 file-transfer 插件。

## Problem Statement

对等网络切换收口后，桌面端与移动端的宿主应用里各长出了一批对等网络专属页面：附近设备、传输任务、对端文件浏览、可信对端管理、接收设置，以及全局挂载的首连确认弹窗与批量请求弹窗宿主。这些页面与宿主的终端远程控制主业无关，却占据侧边栏菜单、设置分组与路由表；而 file-transfer 插件自身已有相当完整的浏览/传输/接收页面实现，形成同一功能两套 UI 并存的局面。用户在宿主里看到「附近设备」「传输任务」等入口，感知上却是宿主内置功能，插件架构下这些能力本应随插件的启停出现与消失。

## Solution

删除两端宿主中的全部对等网络前端页面、弹窗宿主、编排 composable 及其接线（路由/菜单/设置分组/i18n 命名空间），把这些职责并入各自的 file-transfer 插件——以插件现有的浏览主页面为基座，重构并补齐应有的功能：附近设备发现与连接管理、首连确认弹窗、可信对端管理。宿主保留且仅保留对等网络服务层（节点引擎、Tauri 命令面、事件桥、WASM host-peer 能力原语），符合父 spec 决策 1「对等网络是宿主内置核心服务，file-transfer 是上层消费者」——迁移的只是消费端 UI。

## User Stories

1. 作为任一端用户，我要在文件传输插件的设备面板中看到同一网络内所有具备文件传输能力的 BedCode 节点（设备名 + 连接状态），以便选择与谁互传。
2. 作为任一端用户，我想点击发现列表中的未连接设备发起连接，以便与其建立传输关系。
3. 作为任一端用户，我想断开已连接的对端，以便收回直连会话。
4. 作为发起方，连接被拒绝或对端不可达时，我想在设备列表中看到明确的失败态文案，以便知道稍后重试而不是反复点击。
5. 作为任一端用户，正在握手的设备应显示连接中状态，避免我重复发起。
6. 作为被连接方，陌生节点首次连接我时我要收到应用内确认弹窗（设备名 + 指纹 + 倒计时），以便决定是否信任它。
7. 作为移动端用户，确认弹窗即使我不在文件传输页面也要能弹出，以免错过首连请求。
8. 作为桌面端用户，首连请求到达而我不在文件传输面板时，我要能在状态栏看到待确认提示并可一键跳转过去处理。
9. 作为已有终端配对关系的移动端用户，我的手机与桌面在对等网络中应自动互信免确认，并以 toast 告知，以便不为传文件重复做一遍配对。
10. 作为任一端用户，我可以在文件传输插件的设置页查看全部可信对端并撤销其中任意一个，以便随时收回权限。
11. 作为任一端用户，撤销前应看到后果说明的确认框（撤销后对方重连需重新确认），以防误操作。
12. 作为发送方，我可以从文件传输页面向当前对端推送文件并看到实时进度、速率与状态，以便了解传输情况。
13. 作为接收方，收到的传输批按我的接收策略放行，询问弹窗展示文件清单与总大小并有倒计时自动拒绝。
14. 作为任一端用户，我可以在插件设置中管理本机共享目录与接收落点，策略修改即时生效。
15. 作为任一端用户，禁用/卸载文件传输插件后，宿主不应再显示任何对等网络相关入口或页面，以便界面与实际能力一致。
16. 作为任一端用户，终端远程控制链路与宿主对等服务本身不受本次迁移影响，既有工作流不变。
17. 作为任一端用户，升级后既有的传输历史、可信对端与本机配置应保留，以便无缝过渡。

## Implementation Decisions

### 实施顺序（三阶段，前端先行）

- **阶段一：插件页面重构（纯前端）** —— 两端插件以现有浏览主页面为基座按功能需求重构：附近设备面板、首连确认弹窗、可信对端管理分区、设备连接状态机编排。本阶段只面向 PluginContext 契约编程：调用下文定义的新增命令名与事件名，不依赖任何后端改动；被调命令在前端注册临时 mock handler 或由阶段二 devMock 提供。
- **阶段二：dev-shell 截图评审迭代** —— 在两端插件工程目录分别用对应 dev-shell 启动浏览器开发环境（桌面端 CLI 与移动端 `npm run dev` 各按其 SDK 文档），插件入口导出/扩充 devMock 演示数据驱动各页面的关键状态；Chrome headless 对每个页面逐状态截图，交视觉评审（frontend-styles 规范 + design-taste 品味基线），按结论迭代样式与交互直至达标，本阶段结束冻结前端 UI。
- **阶段三：后端实现与宿主删除** —— 实现 WASM 薄代理新增转发命令与 topic 桥接（决策 2/3）、manifest 权限显式化（决策 4），重建插件产物同步打包资源；随后执行宿主删除清单（决策 10）、移植测试（决策 11），真实链路真机冒烟收尾。

阶段一/二期间不触碰任何 Rust 与宿主文件；阶段三一次收口后端与宿主。定稿前已先行落地的桌面代理桥接片段保留，归入阶段三一并验证。

### 服务与契约

1. **层次边界不变**：peer-net crate、Tauri 命令面、`peer-*` 前端事件与消息总线 `peer:*` topic 桥接全部留在宿主；删除的只是宿主内的消费端 Vue 页面/composable 与其接线。host-peer WIT 能力原语不新增不修改（本约束限于本次 UI 迁移范围；随后 docs/adr/0022 v2 对 host-peer 做原语化收缩并新增 host-mdns / host-platform，以后者为准）。
2. **插件命令面扩展**：两端 file-transfer 插件的 WASM 薄代理补齐五条转发命令——拨号连接、断开会话、首连确认应答、可信对端列表、撤销信任——逐一映射到既有 host-peer 原语，DTO JSON 过界形状与其余命令一致。
3. **事件桥扩展**：插件 WASM 代理增订 `peer:consent` 与 `peer:connection` 两个总线 topic，分别翻译为插件命名空间下的首连确认事件与连接态事件推给前端；载荷保持宿主 camelCase 契约形状原样透传。
4. **权限声明显式化**：两端插件 manifest 的 permissions 补声明 `peer`（此前靠既有授权路径隐式可用，迁移后命令面扩大，改为显式声明）。
5. **桌面端设备管理**：现有「在线设备切换下拉」重构为完整的附近设备面板——列出全部发现节点，区分已连接/连接中/未连接三态，支持连接、断开、切换活跃对端；拨号结果（拒绝/不可达）以行内错误文案呈现；活跃对端自动兜底切换逻辑保留。
6. **桌面端首连确认**：队列 + 30 秒倒计时 + 应答编排放进插件激活期常驻的事件订阅（不依赖视图挂载）；富弹窗（设备名、完整指纹、倒计时）渲染在插件视图内（Teleport 到 body），另注册一个状态栏项显示待确认数量、点击经宿主共享 router 跳转插件面板。这是相对原宿主全局弹窗的一处已知体验折衷（不在面板时需经状态栏一次跳转），接受——不为单一插件扩展宿主级对话框能力。
7. **移动端首连确认**：经插件对话框 API 的确认框全局弹出（宿主对话框宿主挂在 App 根，可达性与原实现等同）；消息文本含设备名/短指纹与超时提示；终端配对迁移规则（请求方设备名命中 `paired_devices` 名单即静默自动互信）随迁，匹配纯函数与「宁可多弹勿误信」原则不变。
8. **可信对端管理归位**：桌面端并入插件设置覆盖层的独立分区；移动端并入插件设置二级页。列表项含设备名、指纹、加入时间，撤销走确认框。
9. **i18n 归位**：宿主 `peers.*` 与 `settings.peer*` 命名空间中仍被使用的文案迁入两端插件的插件前缀 i18n（zh-CN 与 en 同步），宿主命名空间整段删除；纯宿主视角的描述性文案（如设置分组的副标题）随分组一起消亡不再迁移。
10. **宿主删除清单（按模块域描述）**：两端各删除——附近设备页、传输任务页、对端文件浏览页、（移动端另有）可信对端页与接收设置页、首连确认弹窗宿主组件、批量请求弹窗宿主组件、六个对等编排 composable（设备/确认/接收/远端文件/发送/可信对端）、对应路由注册、侧边栏内置菜单项（桌面）/设置分组入口（两端）、布局中的弹窗宿主挂载、上述 i18n 键及四个宿主侧编排测试文件。移动端工具箱本无对等入口，无需处理。
11. **测试移植**：被删宿主测试的断言覆盖迁移到插件侧等价物——mock 插件上下文（commands.execute / events.on / dialogs）驱动编排 composable，纯函数（迁移规则匹配、倒计时边界、扇出独立性等）直接单测；测试文件放两端各自的前端测试套件目录下的插件子目录，复用现有 mock 模式（捕获事件 handler 手动派发）。
12. **构建产物同步**：插件源码变更后按既有插件统一构建脚本重建并同步到打包资源，保持 dev 与打包行为一致。
13. **单活跃对端 UX 维持**：本迁移不重引入宿主版的多目标扇出发送编排；发送模型维持「当前活跃对端」粒度（父 spec 故事 13 的扇出能力由服务层天然支持，UI 编排留作后续票）。
14. **devMock 演示数据扩展**：两端插件入口的 devMock 导出（SDK `PluginDevMock` 协议）扩充对等领域子数据——附近设备列表（覆盖在线/未连接两态）、待确认首连请求、可信对端列表、传输批/接收批/历史种子；dev-shell 浏览器端 `commands.execute` 对新命令名返回对应 mock 值，使阶段一/二的页面重构与截图评审完全不依赖后端。真实宿主忽略 devMock，无运行时影响。

## Testing Decisions

好测试只断言外部行为，不测实现细节。自动化不新增接缝，前三条沿用父 spec 已与开发者确认的既定接缝，第四条为阶段二专用的人工评审缝：

1. **复用缝：双节点对打 harness（Rust）** —— 首连闸门、身份拒止、传输批生命周期等行为真源仍在宿主 crate，既有集成测试不动即回归保障；插件薄代理只是转发，不为它立新缝。
2. **复用缝：前端 vitest 编排测试** —— 被删的四个宿主编排测试文件的场景矩阵（start 幂等、事件全量替换、应答/取消/清历史命令路由、失败如实上报、迁移规则匹配）逐项映射为插件侧版本：mock 一个最小 PluginContext（记录 commands.execute 调用、可手动派发 events.on 回调、dialogs 返回受控值），只测编排逻辑不测渲染。
3. **复用缝：无头纯函数单测** —— 迁移规则匹配、倒计时归零结算、设备状态派生等纯逻辑独立直测，模块不依赖 tauri/插件运行时。
4. **视觉评审缝（非自动化，阶段二专用）** —— dev-shell + devMock 驱动的页面状态截图是 UI 质量的验证入口：每个页面的空态/列表态/错误态/弹窗态逐张截图，按 frontend-styles 自查清单与 design-taste 量化基线（VARIANCE/MOTION/DENSITY）评审后迭代；不进 CI、不作断言，产出为评审结论驱动的样式修正。

Prior art：被迁移的宿主编排测试自身的 mock 模式（vi.mock tauri api + handler 表手动 emit）与既有插件 composable 的依赖注入风格（context 参数传入）。

## Out of Scope

- 多目标扇出发送的插件 UI 编排（决策 13，后续票）
- 可信对端自动接收白名单（父 spec 既定 out of scope）
- 桌面端宿主级插件对话框/通知能力扩展（决策 6 的折衷以此为代价）
- 终端控制链路、peer-net 服务层、TLS/信任语义的任何改动
- 插件的启用/停用生命周期与审批流程改造
- 移动端 registerSettingsSection 扩展点的渲染落点问题（现状走插件自有设置页，维持）

## Further Notes

- 父 spec 开发窗口内「旧链路冻结」约束已被切换收口提交解除，本 spec 是收口后的第一张结构性修正票。
- 桌面端插件 WASM 代理的 topic 订阅扩展在 spec 定稿前已先行落地一小部分（consent/connection 桥接与五条命令的桌面侧转发），属本 spec 决策 2/3 的实现起点，无方向性偏离。
- 行为零回归的验收锚点：迁移后宿主源码树内 grep 不到任何对等网络页面组件与编排 composable；两端 `test:run` 全绿；两端插件构建产物同步后 dev 冒烟可见设备列表、首连弹窗、可信对端管理三项核心流。
