## 2. 逐模块对照审核

### 2.1 core-config（`plugin/config.rs`）

已合规：

- `defaults` 常量与历史生产常量逐一相等，且有 `defaults_match_legacy_constants` 对照测试锁定（票据 02 主验收）。
- 分层：编译期默认 < 配置文件 `wasm-core.json`（缺失回落、未知字段容忍）< 运行时覆盖 `WasmRuntime::set_config`（只影响新建 Store，非法值拒绝且旧配置不受影响）——均有测试。
- ResourceLimiter 与燃料注入点读取配置快照，`test_runtime_config_override_applies_to_new_stores` 断言限额来自覆盖值。

**发现 C-1（P1）per-plugin 资源覆盖未接线**

- spec `Implementation Decisions → 配置模块` 与 US6 要求「单插件经 manifest 请求资源覆盖、由安全模块仲裁上限」；
- 现状：`PluginManifest`（`packages/plugin-sdk-desktop/rust/src/types.rs`）**无资源请求字段**；`StoreLimits::clamped_within` 除自身单测外**无生产调用方**（`config.rs` 内定义，`instantiate_component` 直接 `cfg.store.clone()`）；
- 票据 02 记录「延后到票据 04（安全模块），钳制机制已备」，但票据 04 未承接该项（其 checklist 与完成记录均未涉及资源仲裁）；
- 影响：重型插件（大 JSON 解析）无合法扩容通道；`clamped_within` 为待接线的死代码。
- 建议：补 manifest `resourceOverrides` 字段 + 实例化时经安全模块钳制（`clamped_within`）；或下沉为独立票据并在 spec 标注。

### 2.2 core-monitor（`plugin/monitor.rs`）

已合规：

- 计数器（calls_total）/ 仪表（memory_current）/ 直方图（duration buckets）三类形态齐备；内存经 ResourceLimiter 增长回调记账；燃料/耗时经 `exports()` 续费点与 RAII `CallTimer` 聚合；六类生命周期事件带最近时间戳；快照一次性导出；埋点全原子、热路径零日志。
- `test_monitor_metrics_end_to_end` 端到端锁定（instantiate/activate_ok/calls=3/燃料>0/直方图计数=3/内存当前=峰值）。

**发现 M-1（P3，已修）决策与总线计数无单测**

- `record_authz_decision`（三分类）、`record_bus_dropped`、`record_bus_format_rejected` 是票据 04/05 的监控落点，此前只被「快照字段存在性」间接覆盖，未断言数值与分桶正确性。本次补 2 个单测（见 §3）。

### 2.3 core-security（`plugin/security/framework.rs` 等）

已合规：

- 三段决策管线（`check_declared → check_approved → enforce`）、`RequireApproval` 不中止、`ResourceAuthorizer` trait 注册扩展（FakeAuthorizer 证明）、未注册资源默认拒绝、决策计数进监控、api-call 互调门（ADR-0017）回归——均有测试。
- 生产装配：`WasmHostContext::new` 注册 `FsAuthorizer` + `ApiCallAuthorizer`。
- **fs 迁移零丢失**：`security/fs_auth.rs` 7 个用例与迁移前（`fd031193e^:plugin/fs_auth.rs`）测试名逐一一致。

**发现 S-1（P1）fs 链路未走统一授权框架**

- spec `Implementation Decisions → 安全模块`：fs 三层校验应重构为框架的 fs 资源实现；
- 现状：`framework.authorize()` 的**唯一生产调用点是 `host_impl/bus.rs`（bus_publish 互调门）**；`host_impl/fs.rs` 仍是手工内联链（`check_permission` → `fs_auth.check/check_batch`），`FsAuthorizer` 仅为并行适配器；
- 票据 04 记录已声明「调用链暂保留手工内联形态，统一路由后续渐进」，属已知取舍，但副作用是**fs 授权决策不进 `authz` 埋点**——安全审计最活跃的资源路径缺失于监控快照；
- 建议：将 `host_impl/fs.rs` 的 fs 调用改为经 `SecurityFramework::authorize` 路由（至少接入埋点），并保留等价错误文案。

**发现 S-2（P2）凭据明文断言未落地**

- 票据 04 checklist「审计/日志无凭据明文（grep 断言长度字段模式）」无对应测试；实际是结构性满足——框架管线不接触凭据（`AuthRequest` 仅含 plugin_id/resource/operation/target），无明文可落。
- 建议：把该 checklist 改为「凭据面不在框架内，结构性豁免」，或补一条「决策消息不含凭据字段」的断言以防未来扩字段时回归。

### 2.4 core-plugin-manager（`plugin/manager/`）

已合规（票据 06 五集成用例覆盖）：

- 能力注册表二选一装配、宿主原语预登记 18 组、可路由门禁、`revert_to_host` 条件回落。
- 加载顺序（`PluginHost::new` 全路径，系统组件先于应用插件）、依赖缺失报错含能力名并落 Error 态、trap 隔离 + 能力回落 + 回落后续调用正常、停用回落 + 启停不持久化 + 重激活再装配、fixture 私有 KV 对照（证明转发到达组件实例而非宿主 SQLite）。
- ItemName 探测修复由 `setup_system_component` 的 `exported_capabilities == ["host-storage"]` 断言锁定。

**发现 PM-1（P3，未覆盖风险）** `CapabilityRegistry` 的 `register_system_component` 成功/拒绝路径、`revert_all_from`、`system_component_instance` 自调用回落分支无独立单测——构造 `Arc<Mutex<LoadedWasmPlugin>>` 需真实 WASM 实例；运行态已由 host.rs 集成用例覆盖（注册/回落/撤销），**自调用（provider == caller 回落宿主原语，防实例互斥锁重入死锁）分支无覆盖**。建议后续扩展 `plugin-system-test` fixture（同时 import/export host-storage）后补测；当前依赖部署约定（系统组件不消费自己提供的能力，见 `capability.rs` 模块头）。

### 3.3 为可测性做的最小生产改动

`StoreLimits::fuel_budget` 拆出纯函数 `fuel_budget_for(debug_mode: bool)`（原函数转发并传入 `plugin_debug_mode()`）。
理由：倍率分支原依赖 `BEDCODE_PLUGIN_DEBUG` 环境变量 + `cfg!(debug_assertions)`；用环境变量在并行测试中触发该分支会全局放大燃料预算，污染其他 wasm 用例（非确定性）。纯函数形式使分支可被精确断言，且 `fuel_budget` 行为不变。

## 5. 补做：票据 07 / 08（同日立项并完成）

### 5.1 票据 07：per-plugin 资源覆盖（原发现 C-1）

- **SDK**：`ResourceOverrides`（6 个可选字段，camelCase，`Copy`）+ `PluginManifest.resourceOverrides`
  （`Option`，default + skip_serializing_if，旧 manifest 零迁移）；TS 侧 `types.ts` 双侧类型同步。
- **core-config**：`StoreLimits::apply_overrides` —— 只做「请求合并」（None 继承配置）；
  `fuel_debug_multiplier`（全局调试开关）与 `max_wasm_stack_bytes`（Engine 构建期参数）不在请求面。
- **core-security**：`SecurityFramework::resolve_store_limits(plugin_id, config, request)` ——
  双重天花板 `min(请求值, 内核配置值, 编译期硬上限)`；越界请求 warn（structured `plugin_id`）。
- **接线**：`instantiate_component` / `load_plugin_from_file` 增加 `resource_overrides` 参数；
  生产路径（`PluginHost` 加载 + 实例重建）传 `manifest.resource_overrides.as_ref()`。
- **测试 7 个**：SDK manifest 解析（部分字段/缺省/序列化不落盘）、`apply_overrides` 合并语义、
  仲裁（无请求原样继承 / 收紧保留 / 放宽钳回 / 低于运行时配置时钳到配置值）、
  实例化端到端（4MiB 限额下增长 3MiB 放行、5MiB 拒绝）。

### 5.2 票据 08：fs 链路接入统一授权框架（原发现 S-1）

- `host_impl/fs.rs` 新增 `authorize_fs()`（构造 `AuthRequest { resource: Fs, operation: "read"|"write", target: path }`
  走 `SecurityFramework::authorize`）；`fs_read` / `fs_write` / `fs_copy` / `fs_delete` / `fs_exists` 全部改经它；
  `fs_copy` 保持源读 + 目标写双授权。
- **行为等价**：对外错误文案仍为 `"permission denied"`；既有 18 个用例零回归。
  等价性核对：declared 段权限映射与 enforce 段 `fs_auth.check(.., FsOp)` 与手工链逐项一致；
  新增的 `check_approved`（持久授权快速放行）不改变结果集。
- **收益**：fs 授权决策首次进 `authz` 埋点（`SecurityFramework::set_monitor` 已在 `PluginHost` 生产注入）。
- **有意变更**：授权拒绝日志统一为 `warn!` + 结构化字段（原「权限不足 error! / 校验拒绝 warn!」分裂），
  符合 AGENTS.md §8（授权拒绝属可恢复异常）。
- **范围外**：`fs_request_auth` 批量预授权（`check_batch` 一次弹窗覆盖多路径）保持手工链，代码注释已说明原因。
- **测试 5 个**：拒绝 → `authz.deny+1`、放行 → `authz.allow+1`、write 需 write 权限（防越权升格）、
  `fs_copy` 双权限、未授权路径由强制段拒绝并计数。

## 6. 未覆盖风险

1. **自调用回落分支**（PM-1）：`system_component_instance` 的 `plugin_id != caller_plugin_id` 分支无测试；需 fixture 同时 import/export 同接口，成本较高，当前依赖部署约定。
2. **`register_system_component` 成功/拒绝路径无独立单测**：门禁由 `is_routable` 单测覆盖，注册态由 host.rs 集成覆盖；构造实例的成本使纯单测不可行。
3. **弹窗 warn 日志断言缺失**：票据 05 要求「丢弃 + warn（结构化字段）」，现有用例以「不投递 + 计数」替代，未捕获 tracing 输出验证结构化字段（需 tracing 订阅器，成本较高）。
4. **US11 吞吐维度缺失**（B-1）：当前快照无法回答总线消息数/字节数/topic 分布。
