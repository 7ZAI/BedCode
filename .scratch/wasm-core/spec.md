# WASM 核心（wasm-core）模块化改造规格

Status: done（2026-09-13，01–06 六票据全部落地并验证：桌面 cargo test 643 单测 + 集成全绿，eslint 0 error，前端 614 全绿）
Date: 2026-09-13
关联文档: 终态愿景 `.scratch/platform-kernel/spec.md`（无业务内核）；渐进次序 `.scratch/plugin-kernel-roadmap/spec.md`；ADR 0017（互调门）/ 0019（wasmtime 双端锁死）/ 0022（host 接口裁剪线）；术语 `CONTEXT.md`

## Problem Statement

当前 WASM 插件能力集中在 `src-tauri/src/plugin/` 子系统（约 10.7k 行：wasm_runtime、21 组宿主能力实现、message_bus、fs_auth、approval、api_registry 等），功能可用但**不是按「内核」组织的**：

- wasmtime Engine/Store 的运行参数（燃料预算、内存上限、栈深、表/实例上限、编译缓存、debug 放大倍率）是散落在运行时代码顶部的常量，无统一配置面，调参要改代码重新编译；
- 运行过程**不可观测**：每个 Store 的内存消耗、燃料消耗、插件调用耗时/次数、trap 频率、总线吞吐均无埋点，出问题只能靠日志倒查；
- 安全能力分散在多个彼此独立的模块（权限声明、fs 三层校验、授权弹窗、互调门），没有统一的「资源授权框架」，新增受管资源时各自发明仲裁逻辑；
- 插件只有**一种形态**：所有 WASM 插件都是「应用」。终态愿景（platform-kernel）要求 http 服务器、数据库、mDNS 这类**系统组件**也是 WASM 组件、经 Linker 向内核提供基础能力，应用插件基于系统能力构建——当前架构没有这个类型划分与装配机制；
- 消息总线只支持 JSON 字符串载荷，二进制数据（文件块、终端输出、对等网络帧）必须 Base64/转义后走 JSON，低效且无法承载大载荷。

## Solution

把 `src-tauri/src/plugin/` 演进为明确的 **WASM 内核（wasm-core）**：以 wasmtime 47 为运行时核心，划分为五个内聚模块——**配置、监控、安全、插件管理（核心）、消息总线**——模块间只经内核根（facade）组合，各自带可扩展点。内核逻辑闭环：

```
CoreConfig 加载 → Engine 构建 → Monitor 注册表初始化
→ Security 仲裁管线注册 → Linker 装配宿主原语
→ 系统组件加载并注册能力 → 应用插件加载（import 路由到系统组件/宿主原语）
→ Bus 连通（JSON + 二进制双格式）→ 运行时全程监控埋点 → 优雅停机
```

插件分两种类型：**系统组件**（内置 WASM 组件，如 http 服务器组件、db 组件、mDNS 组件，经能力注册表向内核/应用插件提供基础能力）与**应用插件**（如 file-transfer，只消费能力与总线）。本规格落地**类型划分与装配框架**；把宿主现有 Rust 引擎逐个替换为 WASM 系统组件是后续各自立项的事，不在本规格内。

## User Stories

### 配置模块（core-config）

1. 作为内核维护者，我想要 wasmtime Engine 的所有构建参数（fuel 开关、编译缓存、并发编译策略）集中在一个配置结构里，以便调参不用翻运行时代码。
2. 作为内核维护者，我想要 Store 级资源上限（线性内存、表元素、栈深、实例数、内存数、单次调用燃料预算）全部来自配置，默认值为当前生产验证过的常量，以便我可以按部署环境调整而不改代码。
3. 作为内核维护者，我想要配置分层（编译期默认 < 配置文件 < 运行时覆盖），以便打包默认值安全、运维可覆盖。
4. 作为内核维护者，我想要新增配置项时只需加带默认值的字段、旧配置文件不报错，以便配置面可演进。
5. 作为内核维护者，我想要插件调试模式的燃料放大倍率可配置，以便 debug 产物插件不被燃料看门狗误杀。
6. 作为内核维护者，我想要单插件可通过 manifest 请求资源覆盖、但由安全模块仲裁上限，以便重型插件（大 JSON 解析）有合法扩容通道。

### 监控模块（core-monitor）

7. 作为内核维护者，我想要一个指标注册表（计数器/仪表/直方图三类），以便所有运行数据有统一埋点入口。
8. 作为诊断者，我想要每个插件 Store 的线性内存当前值与峰值可查询，以便定位内存失控插件。
9. 作为诊断者，我想要每次插件导出调用的燃料消耗与耗时被记录（聚合统计，非逐条日志），以便发现失控/低效插件。
10. 作为诊断者，我想要插件生命周期事件（加载/激活/停用/降级/trap）带计数与最近一次时间戳，以便回答「哪个插件什么时候崩过几次」。
11. 作为诊断者，我想要消息总线吞吐指标（消息数、字节数、按 topic 分布、丢弃数），以便评估总线瓶颈。
12. 作为诊断者，我想要授权决策计数（允许/拒绝/弹窗/持久化授权），以便审计安全行为。
13. 作为内核维护者，我想要监控数据经快照 API 一次性导出（供前端诊断页/CLI），以便观测不依赖翻日志。
14. 作为内核维护者，我想要监控 sink 可扩展（当前内存快照 + tracing 结构化字段，未来可接文件/远程），以便监控后端可演进。
15. 作为内核维护者，我想要热路径埋点零日志、纯原子计数（遵守日志红线：PTY 输出、WS 每帧级别的高频路径禁止逐帧日志），以便监控本身不成为性能问题。

### 安全模块（core-security）

16. 作为内核维护者，我想要统一的授权框架：资源类型（fs/网络/进程/存储/总线/互调）× 操作 × 仲裁点的决策管线，以便新增受管资源时走同一框架而非各写一套。
17. 作为内核维护者，我想要决策管线固定为「manifest 声明（前端快速失败）→ 授权审批（弹窗/持久化授权记录）→ 运行时强制（Rust 端最终仲裁）」三段，以便安全语义全系统一致。
18. 作为内核维护者，我想要现有 fs 三层校验（路径白名单 → 插件白名单 → 弹窗授权）成为授权框架的第一个资源实现而非独立特例，以便框架是从真实需求抽出来的。
19. 作为内核维护者，我想要互调门（ADR 0017：未在 manifest `api` 声明的 API 不可调）并入授权框架作为「互调资源」的仲裁，以便插件间调用与资源访问同一套审计。
20. 作为内核维护者，我想要新资源类型以 trait 注册仲裁器，以便安全框架可扩展。
21. 作为安全审计者，我想要凭据（token/密钥）在任何监控指标与日志中只出现长度不落明文，以便符合安全红线。
22. 作为终端用户，我想要授权弹窗的决策被持久化、可撤销，以便我不被重复打扰且能收回授权。

### 插件管理模块（core-plugin-manager，核心）

23. 作为内核维护者，我想要插件 manifest 声明 `type: system | application`（默认 application），以便内核按类型走不同装配路径。
24. 作为系统组件作者，我想要把 http 服务器、数据库、mDNS 这类基础能力做成内置 WASM 系统组件，经能力注册表向内核注册「我提供什么能力」，以便基础能力与应用同构、可被监控/授权/热管理。
25. 作为应用插件作者，我想要我的 import（host-* 能力）由内核路由到对应的系统组件实例，以便我只面向能力编程、不关心能力由宿主 Rust 还是系统组件提供。
26. 作为内核维护者，我想要能力注册表支持「同一能力宿主 Rust 原语与 WASM 系统组件二选一装配」，以便现有 Rust 引擎可逐个平滑替换为 WASM 系统组件（对齐 platform-kernel 服务插件模式）。
27. 作为内核维护者，我想要加载顺序保证：系统组件先于应用插件完成加载与激活，以便应用插件激活时其依赖的能力已就绪。
28. 作为内核维护者，我想要系统组件与应用插件走同一条 Store/安全/监控管线（单插件单 Store、trap 不扩散），以便系统组件不享有绕过内核边界的特权。
29. 作为内核维护者，我想要系统组件内置、默认启用、不可被用户卸载（只可停用，对齐内置插件语义），以便基础能力不被误删。
30. 作为应用插件作者，我想要消费某系统组件能力时在 manifest 声明依赖，缺失时激活失败并给出明确错误，以便依赖问题前置暴露而非运行时才炸。
31. 作为内核维护者，我想要插件管理模块吸收现有 loader/registry/watcher/host/component 的职责并对外只暴露一个 facade，以便内核根是唯一组合点、模块禁止横向耦合。

### 消息总线（core-bus）

32. 作为应用插件作者，我想要总线消息载荷支持 JSON 文本与二进制（字节列）两种格式，以便文件块/终端输出/网络帧不用 Base64 过 JSON。
33. 作为应用插件作者，我想要 JSON 路径行为与现状完全一致（topic 订阅、发布、on-message 回调），以便存量插件零迁移。
34. 作为内核维护者，我想要二进制路径零 JSON 编解码，以便大载荷传输高效。
35. 作为内核维护者，我想要二进制载荷在 WIT 契约中以 `list<u8>` 承载，ABI 变更走 bump 流程双端同步，以便契约演进有纪律。
36. 作为内核维护者，我想要订阅者只收到自己能处理的格式（或统一收到带格式标签的载荷），以便 JSON 订阅者不会被二进制消息打崩。
37. 作为内核维护者，我想要总线有背压/丢弃策略（队列满丢弃打 warn，结构化字段带 plugin_id/topic），以便慢消费者不拖垮内核。

## Implementation Decisions

### 总体结构

- 现有 `src-tauri/src/plugin/` 重组为内核五个模块：**core-config / core-monitor / core-security / core-plugin-manager / core-bus**（扁平模块结构 ADR：每模块一个目录、入口文件与目录同名、测试 `*_test.rs`）。
- 内核根 facade 是唯一组合点：五模块之间禁止横向 import 对方内部，只经 facade 或显式 trait 注入协作（沿用 message_bus 现有 `MessageDispatcher` trait 解耦模式——该模式已验证有效，推广为模块间协作的标准形态）。
- 现状代码**大规模复用不重写**：wasm_runtime（Engine/Linker/Store 生命周期、燃料看门狗、ResourceLimiter）、host_impl 21 组宿主能力、fs_auth、approval、api_registry、message_bus 都是各模块的实现底子，本规格做的是「归位 + 抽象 + 补缺口」。

### 配置模块

- 单一配置结构（serde，字段全带默认值 = 现 wasm_runtime.rs 顶部常量：`FUEL_PER_CALL` / `MAX_PLUGIN_MEMORY_BYTES` / `MAX_WASM_STACK_BYTES` / 表/实例/内存数上限 / `FUEL_DEBUG_MULTIPLIER` / 编译缓存开关与目录），分 `engine` 与 `store` 两组。
- 分层加载：编译期默认 → 配置文件（应用配置目录）→ 运行时 API 覆盖；反序列化对未知字段容忍（老端忽略未知字段的增量原则）。
- ResourceLimiter 改为配置驱动；per-plugin 覆盖经 manifest 请求 + 安全模块钳制在安全上限内。

### 监控模块

- 指标注册表支持 counter / gauge / histogram；插件维度标签用 `plugin_id`（结构化字段红线）。
- 内存记账挂在 ResourceLimiter 的增长回调上（当前值 + 峰值）；燃料/耗时在每次导出调用前后采样聚合；生命周期事件计数。
- 快照导出 API（一次调用拿全量 JSON 快照）；埋点热路径纯原子操作，不打日志；状态迁移级事件走 tracing（遵守 §8 级别语义）。

### 安全模块

- 授权框架抽象：`ResourceKind`（fs / network / process / storage / bus / api-call，可注册扩展）× 操作描述 × 三段决策管线（manifest 声明快速失败 → approval 审批 → 运行时强制）。
- fs_auth 三层校验重构为该框架的 fs 资源实现；api_registry 互调门重构为 api-call 资源实现；approval 持久化授权记录继续负责「已授权」判定。
- 仲裁点统一在 Rust 端（安全红线：前端校验仅是 UX）；凭据只记长度。

### 插件管理模块

- manifest 新增 `type` 字段（`system` / `application`，缺省 `application`，旧插件零迁移）与 `dependencies` 字段（应用插件声明依赖的系统组件能力）。
- **能力注册表（capability registry）**：键 = 能力名（如 `host-http` / `host-database` / `host-mdns`），值 = 提供者（宿主 Rust 原语 **或** WASM 系统组件实例）。Linker 装配应用插件 import 时查表路由：宿主原语则现状直连；系统组件则生成转发闭包，把 guest 调用桥接到目标组件实例的导出（host-side 转发，组件间不共享内存，序列化边界在 WIT 类型层）。
- 加载编排：先系统组件（按注册能力拓扑序）后应用插件；应用插件依赖缺失 → 激活失败报明确错误；系统组件内置、默认启用、只停不删。
- 一期边界：系统组件的「能力接口」复用现有 host-* WIT 接口形状（组件导出与宿主 import 同形），**不引入新的组件组合 world**；wasmtime 原生组件组合（composition）是二期方向。
- 单插件单 Store 的崩溃隔离不变；Activated/Degraded 语义沿用（ADR：lifecycle 导出如实上抛成败）。

### 消息总线

- 载荷建模为带格式标签的变体：`Json(string)`（现状兼容）/ `Binary(list<u8>)`；WIT 侧新增 `publish-binary` 与 `on-message` 的二进制承载形式 → **ABI bump，双端同步**（ADR 0019，两端 wasmtime 47 锁死）。
- 订阅声明格式偏好（默认 JSON）：JSON 订阅者收不到二进制消息（发布方有义务按订阅者能力投递，或总线侧拒绝并 warn）；二进制路径全程无 JSON 编解码。
- 背压：每订阅者有界队列，满则丢弃 + warn（`plugin_id` / `topic` 结构化字段），丢弃计数进监控模块。

### 硬约束（全程生效）

- wasmtime 47 两端锁死，本规格不升级（ADR 0019）。
- 系统组件提供的能力**不得携带业务语义**（ADR 0022 裁剪线）；业务编排一律在应用插件层。
- 核心业务冻结不动：会话/终端/设备连接/对等网络引擎留宿主侧（roadmap 阶段 0 基线），本规格不做任何业务下沉。
- 协议/契约演进「老端忽略未知字段」，禁止破坏性替换；manifest `type`/`dependencies` 缺省兼容旧插件。
- 日志红线：结构化字段 `plugin_id`/`session_id` 等 `key = %value`；panic hook 只 `eprintln!`；热路径不逐帧打日志。
- Rust 规范：`AppError` 统一错误、关键链路错误带操作上下文、禁止裸 `?` 透传、`spawn_with_error_boundary()`。

## Testing Decisions

**接缝（唯一新接缝在最高处）**：内核公共面——即重组后内核根 facade 的 Rust API + WIT 契约边界。测试全部走 `cargo test`（`src-tauri` 内联 `#[cfg(test)]` + `src-tauri/tests/` 集成测试），不触碰 Tauri 命令层、不加前端测试负担。

**好测试的标准**：只测外部行为（配置值 → 运行时限制实际生效；消息发出 → 订阅者收到字节一致；未授权 → 拒绝且审计计数 +1；依赖缺失 → 激活失败报明确错误），不测内部实现（模块私有结构、中间状态）。

**各模块测试点与既有先例**：

| 模块 | 测试点 | 先例 |
| --- | --- | --- |
| core-config | 默认值与现常量一致；配置文件加载/未知字段容忍；运行时覆盖生效 | plugin/types.rs 内联单测 |
| core-monitor | 内存记账（增长→当前值/峰值正确）；燃料/调用计数聚合；快照导出形状 | wasm_runtime.rs `mod tests` |
| core-security | 决策矩阵（声明/审批/强制三层 允许×拒绝×弹窗）；fs 资源回归（现有 fs_auth 测试迁入不丢用例） | fs_auth.rs / approval.rs 现有测试 |
| core-plugin-manager | 最小 WASM fixture：一个 fake 系统组件注册能力 + 一个应用插件消费它，验证 Linker 路由闭环、加载顺序、依赖缺失报错、trap 隔离 | component.rs 现有组件测试、`src-tauri/tests/server_integration.rs` 集成测试形态 |
| core-bus | JSON 路径回归（现有 message_bus 测试全保）；二进制 roundtrip（含非 UTF-8 字节、大载荷）；格式不匹配投递拒绝；背压丢弃 + 计数 | message_bus.rs `mod tests` |

**验证门禁**：`cd bedcode-desktop/src-tauri && cargo test` 全绿；根目录 `pnpm exec eslint .` 0 error（本规格基本不动前端）；改 WIT 则双端 SDK 契约同步检查 + ABI bump 记录。

## Out of Scope

- **业务下沉**：会话/终端/设备连接/对等网络引擎全部留宿主侧（roadmap 阶段 1–3 各自另行立项，本规格只做内核运行时层）。
- **现有 Rust 引擎逐个替换为 WASM 系统组件**：http 服务器/db 的真实 WASM 化各自立项（mDNS 已改判为宿主基础能力服务，不再 WASM 化，见 `.scratch/2026-09-10-mdns-service-plugin/spec-basic-capability-service.md`）；本规格只交付「系统组件类型 + 能力注册表 + 装配框架」，并用一个 fake 系统组件 fixture 证明闭环。
- **wasmtime 原生组件组合（composition）**：二期方向，本规格一期用 host-side 转发。
- **前端诊断页**：监控快照 API 的消费 UI 另行立项。
- **移动端内核移植**：WIT 契约变更双端同步演进（ADR 0019；移动端契约独立演进见 ADR 0018），但移动端运行时模块化移植另行立项。
- **wasmtime 版本升级**：锁 47。
- **前端 UI 改动**：本规格无。

## Further Notes

- **与愿景/路线图的关系**：platform-kernel/spec.md 是终点（无业务内核 + 全业务插件化），plugin-kernel-roadmap/spec.md 是渐进次序（业务下沉的阶段划分）。本规格不重叠两者——它落地的是愿景中「**运行时层 + 内核扩展点**」的模块化：配置/监控/安全/插件管理/总线五块是内核的「自我修养」，无论业务下沉到哪个阶段都需要。系统组件类型为「内置 WASM 能力组件」提供正式挂载形态——mDNS 已改判为基础服务留内核（见 v2 spec，不再插件化），该类型仍为后续引擎能力 WASM 化（如 http/db）保留装配位。
- **术语对齐**：「系统组件」即愿景中的「服务插件」（内置 WASM 组件，提供能力）；「应用插件」即现有插件形态。文档与代码注释沿用 CONTEXT.md 词汇（插件契约、启用/激活、内置插件只停不删）。
- **用户原始诉求中的「wasmtimer」即 wasmtime**（项目技术栈中的运行时，两端锁 47）。
- **风险提示**：系统组件「host-side 转发」路径会让能力调用多一跳 guest→host→guest 序列化开销。一期可接受（能力调用非热路径；热路径红线如 PTY 输出分发本就不进 WASM）。若未来某能力成为热路径，再评估 wasmtime 原生组件组合。
