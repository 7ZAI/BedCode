## 1. 目标与范围

用户指令三点：① 每个 wasm-app 有独立的授权记录；② 针对权限资源设计授权策略（先是文件与网络请求，其他资源后续按同一机制扩展）；③ 宿主提供界面查看 wasm-app 的授权情况，并对具体授权目录/请求地址做取消授权等管理。

- **范围**：桌面端宿主（`bedcode-desktop/src-tauri/src/` + `bedcode-desktop/src/`）。
- **不在范围**：移动端（ADR 0018 独立契约，本次**不跟演**）；wasm 应用侧（`wasm-apps/*`）**零改动**；`network:http` 的**入站**方向（`http_register_endpoint`）；`ws:client` / `ws:server` / `peer` / `pty` / `process` 等其余 `ResourceKind`。
- **契约影响**：**不 bump ABI**（理由见 §10）。

## 2. 现状核查（设计前的事实，非推测）

| # | 事实 | 对设计的影响 |

## 3. 术语

### 3.1 新增词条（写进 `CONTEXT.md`）

**授权策略 (Authorization Policy)**：
每个 wasm-app × 每类受管资源（本期：文件 / 网络）一条的记录，回答「遇到**授权记录未覆盖**的目标时，要不要问用户」。三档：总是询问 / 默认 / 始终允许。策略**只决定是否询问**，不决定权限位是否生效，也不放松任何安全硬闸门。宿主侧安全闸门（§5.1.3），非业务默认值。
_Avoid_: 权限开关、权限档位、忽略权限、白名单、放行策略

**授权记录 (Authorization Record)**：
单条「某 wasm-app 对某资源上的某目标被允许或被拒绝」的落账，是运行期事实。文件侧记路径前缀 + 生效操作集，网络侧记归一化 origin（可带 path 前缀）。每条带来源（用户确认 / 免询问自动放行 / 旧版遗留 / 用户拒绝）与时间。
_Avoid_: 授权（单指弹窗动作时）、白名单、目录授权（见下）

### 3.2 与既有词条的关系

- **目录授权**（既有，定义**一字不动**）：插件 activate 时批量申请数据目录前缀的弹窗机制。它是**授权记录的一处批量生产入口**，不是与授权策略并行的第二套机制。新词条里注明这层关系即可。
- **接收策略**（file-transfer，ADR 0016）：与其正交，不动。

## 4. 核心契约

### 4.1 策略三档

| 档位 | 中文 | 值 | 读授权记录 | 询问 | 落账 |
|---|---|---|---|---|---|
| 0 | 总是询问 | `always_ask` | **跳过**（不读任何 allow 记录） | 每次判定都问 | 仅用户显式选「以后都拒绝」时落 deny |
| 1 | 默认 | `default` | 读 | 未命中才问 | 命中即已有；新命中经用户确认后落 allow |
| 2 | 始终允许 | `always_allow` | 不读 | **不问** | 放行且以 `source='always_allow'` 落账，UI 标「未经确认」 |

**命名决策**：弃用 `bypass`（与安全语境 "bypass the gate" 撞车），三档值 `always_ask` / `default` / `always_allow`。**否决「忽略权限」这一措辞**——它承诺的事做不到：策略之上仍压着 manifest 声明门、SSRF/重定向、路径规范化、配额，任何档位都放行不了这些（§6.4）。安全界面宁可低估，不可高估。

### 4.2 授权硬闸门（任何档位、任何记录都不可放行）

1. **manifest 声明门**（`check_declared`）：没在 manifest 声明对应权限位，调用在最外层就被拒。策略与授权记录**永远**不能替代批准位（ADR 0020 的批准位决定「哪些位生效」，策略只决定「生效的位上遇未记录目标时问不问」）
2. **SSRF 防护**：`is_private_target`（私网 / 回环）与 `redirect_decision`（公网 → 私网重定向）
3. **路径规范化失败即拒**：canonicalize 失败不降级放行
4. **配额上限**：`ptyQuota` / WS 连接数 / 任务条数等加载期与运行期仲裁
5. **属主隔离**：他人句柄 / 他人 topic 一律显性拒绝

### 4.3 不提供的能力（明确不做）

- **无「一次性整机放行」**：`always_allow` **不在切档瞬间授予全盘权限**——它改变的是「后续遇到未覆盖目标时的动作」（自动放行并落账），新目标要等插件实际碰到才产生记录。所以刚切档时该应用的授权清单**仍然是空的**，不会一下子变成整机放行。但要如实认识其长期效果：只要该应用持续访问，它会逐步把碰过的目录/地址累积进记录——这是该档位的固有语义，不是漏洞
  - 修正记录：R3 阶段曾加过「即便 bypass 也只能对已存在的授权目标免询问」这条收窄，与 §4.1 的「不问 + 落账」及 R2 的「默认放行」原话冲突。**以 (A) 为准，收窄条款作废**
- **无 `always_allow` 的「不落账」形态**：免询问也必须落账，否则 §11 需求③在最高风险档上出现不可见空洞
- **无「立即阻断」独立语义**：管理界面的撤销 = 删 allow 记录 + 落 deny 记录（deny 可在界面自行移除）——见 §8.4

## 5. 数据模型

### 5.1 新增两表（进 `db/schema.sql`，单一事实源）

```sql
CREATE TABLE IF NOT EXISTS plugin_auth_policies (     -- 每个 (应用, 资源) 至多一行
  plugin_id  TEXT NOT NULL,
  resource   TEXT NOT NULL,      -- 'fs' | 'network'
  strategy   TEXT NOT NULL,      -- 'always_ask' | 'default' | 'always_allow'
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (plugin_id, resource)
);

CREATE TABLE IF NOT EXISTS plugin_auth_records (      -- 每个 (应用, 资源, 目标) 至多一行
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  plugin_id    TEXT NOT NULL,
  resource     TEXT NOT NULL,     -- 'fs' | 'network'
  target       TEXT NOT NULL,     -- fs: 规范路径 | network: 'https://host:port[/prefix]'
  effect       TEXT NOT NULL,     -- 'allow' | 'deny'
  ops          TEXT NOT NULL DEFAULT '[]',  -- fs: ["read","write"]；network 恒 '[]'
  prefix_match INTEGER NOT NULL DEFAULT 0,  -- network: 1 表示 target 带 path 前缀
  source       TEXT NOT NULL,     -- 'user' | 'always_allow' | 'legacy' | 'user_deny'
  created_at   INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_auth_records_lookup
  ON plugin_auth_records(plugin_id, resource, target);
```

**迁移要求（AGENTS §9 硬约束）**：`run_migrations()` 幂等（可对旧库重跑）+ 补迁移幂等测试。表是 `IF NOT EXISTS`，但**建表 + 索引两条语句都要被幂等测试覆盖**。

### 5.2 fs 旧记录的处置（修正 R2 阶段的「新 key」方案）

`fs_granted_paths`（`plugin_storage` 里的 key）**退化为只读 legacy 回退，不再被写入**。新记录一律进 `plugin_auth_records`。判定规则（`resolve(op, canonical)`）：

```
1. 取出 records 中 resource='fs' 且 effect='allow'
   且 target 是 canonical 的祖先或自身的全部行（strip_prefix 成功）
2. 若该集合非空：
     任一行 ops 含 op  → ALLOW
     否则            → DENY（该子树被显式管理过，但不含此操作）
3. 集合为空 → 回退 legacy flat：命中任一前缀 → ALLOW（视作 read+write，与今天逐字一致）
4. 都未命中 → 未命中（进第一方层 / 询问）
```

**规则的一句话表述**：用户显式管理过的子树，完全由新表说了算；**没被管理过的子树继续沿用旧记录**，存量用户零感知。legacy 同项作废由第 2 步的「集合非空即短路」天然保证。

**落账方**：`check` / `check_batch`（目录授权）/ `authorize_picked`（选择器结果门，粒度仍为所在目录）三个入口写新表，`ops` 取本次请求的操作集。`remember=false` 的一次性放行**不落账**（与现状一致）。

## 6. 决策管线

### 6.1 统一顺序（fs 与 network 共用同一骨架，差别只在目标形态）

```
0. manifest 声明门（权限位）              —— 硬闸门
1. 硬拒绝记录（effect='deny' 命中）      —— 硬闸门，优先于一切放行路径
2. 第一方免弹窗目录（fs 专属，F5）        —— 见 §7
3. 策略层：always_allow → 放行并落账
           always_ask   → 跳到 5（不读记录）
           default      → 继续 4
4. 授权记录命中（fs: §5.2 规则 / network: origin 匹配，deny 优先）→ 放行
5. 询问用户（fs 弹窗 / network 弹窗）
```

**「总是询问」仍受第 1 步约束**——它跳过的是 allow 记录，不是用户已经说过的「以后都拒绝」。否则同一条硬拒绝会在每次访问时重新弹窗，等于把 deny 记录作废。

### 6.2 策略抽象（本期落点）

策略求值抽成**一个按 `ResourceKind` 分派的函数**，fs 与 network 各自提供「目标归一化 + 记录匹配」两个小实现。**不**在本次把 fs 从 `host_api/fs.rs` 的手工内联链改接 `framework.rs` 的 `ResourceAuthorizer`（那是独立的重构票，不夹带）。理由：本期要的是策略层，`framework.rs` 的三段管线在 `check_approved` 位置加一层即可，改接的收益不抵其 blast radius。

### 6.3 fs 侧询问

- 弹窗按钮：**允许本次 / 拒绝 / 以后都拒绝**（「总是询问」档下**不出现**「记住」——它会与「跳过记录」语义矛盾；且在弹窗里临时切档会造成两处口径）
- 答「允许本次」= 一次性放行不落账；答「以后都拒绝」= 落 `effect='deny'`
- 「默认」档保留现有「记住」按钮（写入新表）

### 6.4 network 侧（出站 `http_fetch`）

- **目标归一化**：`scheme://host:port`，**默认端口显式化**（https→443、http→80），host 小写，去尾斜杠。**query 与 fragment 绝不进入 target**（AGENTS §8 凭据红线：token 不得落库）
- **path 前缀**为可选收紧项（`prefix_match=1`）；匹配时前缀按 path 段边界比较，不做子串
- **同 origin 并发合并**：同一 origin 的并发/连续请求合并为**一次**弹窗，答一次放行该批在途请求（合并窗口为显式常量，不做隐式去抖）。理由：agent-hub 一次列表刷新就是几十个 `api.github.com` 请求，逐次弹窗会让「总是询问」在实践中等于不可用
- **超时 30s，超时按拒绝**（与 fs 一致，§8 fail-safe 默认「无应答即拒」）
- **SSRF / 重定向检查位置不变**（F6）：它们在请求执行期，与策略求值正交。**即使 `always_allow` 且记录命中，私网目标仍被拒**
- **入站方向不变**：`http_register_endpoint` 维持「权限位 + 动态注册表」现状

## 7. 第一方免弹窗层（F5）

**裁定：优先级高于策略档位，策略只管其余路径。**

- 用户给 agent-hub 设「总是询问」，`~/.agents` 等第一方目录**仍免弹窗**——这是票 07 写这张表的唯一理由（注释原文：「弹窗会把一次同步技能拆成 N 次点击」）
- **可选方案「取消第一方层、全部走记录」不可行**：`ProjectSegment` 是**段名规则**而非具体路径（项目根由用户每次选），落不成可复用的授权记录
- **可选方案「策略为总是询问时第一方层也失效」违背该表存在理由**，否决
- **必须配套（否则不可见特权）**：管理界面**显式展示**这批「内置免询问项」，只读展示但**可撤销**——撤销 = 落一条 `effect='deny'` 记录，由 §6.1 第 1 步拦截（deny 优先于第一方层）

## 8. 生命周期与生效

### 8.1 生效时机

- 策略**判定时实时读取**，不缓存、不做激活期快照（否则「已改成总是询问」却仍有缓存判定在放行 = 策略语义骗人）
- **已在等待应答的弹窗按弹出时的旧策略走完**，不半途改口径
- 持久化于 `plugin_auth_policies`，重启后仍生效

### 8.2 记录容量

- 按**目标去重**（网络 = origin；文件 = 目录前缀），**不记次数**
- 每 (应用, 资源) 封顶 **500** 条，超出丢弃并在 core-monitor 计数
- 网络侧 origin 数量天然有限；文件侧若无封顶，遍历型插件会无界增长

### 8.3 插件生命周期

| 事件 | 授权记录 | 策略 |
|---|---|---|
| 停用 deactivate | **保留** | 保留 |
| 激活 activate | 保留 | 保留 |
| 卸载 uninstall | **清空** | **清空** |
| 重装 | 不恢复（= 全新授权，与 ADR 0020 内容哈希钉扎同调：重装即新审批） | 回到默认 |

**「停用保留 / 卸载清空」要写成防回接锁**：它与「不兼容存量用户」是两件事，容易被后人「顺手统一」掉。

### 8.4 撤销语义

管理界面的「取消授权」= **删除该目标的 allow 记录 + 落一条 deny 记录**。理由：管理语境下用户点的是「停止」，不是「下次再问我」。deny 记录在界面「硬拒绝」分区可见且**可自行移除**（移除 = 只删 deny，回到「默认」档的未覆盖状态），两种意图都有出口。

## 9. 界面

### 9.1 归属：设置页内的二级入口（不进一级菜单）

用户裁定：**一般用户不关心权限，权限不是业务，不该占一级菜单显眼位置**。这与 §5.1 的分层同向——引擎事实归设置项，不归业务门面。

- 设置页新增子项「应用授权」→ 单页**列出所有已安装 wasm-app**
- **按风险排序**（`always_allow` 置顶），而非字母序
- 每行可展开：本 app 的三档策略控件 + 文件目录清单 + 网络 origin 清单 + 逐条撤销 + 内置免询问项

### 9.2 应用中心详情页

- 新增「授权记录」区块：**四个分区**——用户已授权 / 免询问自动放行（标「未经确认」）/ 内置免询问（第一方）/ 硬拒绝，**全部可撤销**
- 现有区块**改名**：「权限」→「**申请的权限**」（manifest 声明位）。两者是**正交事实**（一个静态声明、一个运行期落账），不合并成一块——合并会暗示它们之间有映射，而实际一个权限位可对应零条或几十条记录
- 职责切分：**详情页 = 看 + 撤销**（用户「刚看到这应用动了哪」的动机会出现在此刻）；**设置页 = 设三档策略 + 全量管理**。三档策略控件**只在设置页**，避免两处口径漂移

### 9.3 读模型

**单一命令** `plugin_auth_overview(plugin_id?)` 返回策略 + 记录 + 内置免询问项；`plugin_id` 为空 = 总览。两个页面共用同一读模型，不各写一套查询（防漂移）。

### 9.4 展示纪律

- `always_allow` 自动放行的记录**必须**带「未经确认」标记并与用户确认的记录视觉区分
- 第一方免询问项**必须**在两页都可见（§7）
- i18n 键落 `settings` 分组，zh-CN / en 同步（AGENTS §6）

## 10. 契约与影响面

- **不 bump ABI**：网络询问是 `host-http` **内部**新增的失败模式，`http_fetch` 的 import 签名与返回类型一字未改；应答通道复用 F4 那套宿主面凭证绑定机制（新事件 + 新命令，宿主内部）。沿用 v22 总线 topic 的「不 bump 的语义变更」先例，在 WIT 该段登记
- **移动端不跟演**（ADR 0018 双端偏离：移动端是自持业务 App，SAF 选择器本就按 tree URI 授予）。因不 bump ABI，AGENTS §5.1.4 的移动端影响评估**不触发**
- **wasm 应用侧零改动**：`host-*` 签名不变，四个 wasm 应用的 manifest / 代码均不需改
- **双端 WIT 副本**：无 WIT 变更，两份副本不动

## 11. 红线自检（AGENTS §5.1）

| 判据 | 结论 |
|---|---|
| B1 产品类型/字段 | 无产品名词。授权策略/记录是任意第三方插件可同形复用的引擎事实 |
| B2 业务编排/状态机 | 无。判定管线是纯函数式的顺序裁决，无多步流程与状态迁移 |
| B3 业务真源 | **是宿主的权威存储**（两张新表）——但 §5.1.3 明列「安全闸门」与「通用注册表」为宿主合法职责，授权记录是安全闸门的配给账，不是产品事实 |
| B4 业务投影/DTO | 读模型是宿主**自有**记录的投影，不是把原语结果翻译成产品 wire 形状 |
| B5 业务默认值/策略 | **正面命中风险**。缓解已落地：① 策略**默认值 = 默认档**（fail-safe，非替插件决定「业务上该怎样」）；② **manifest 不得声明策略档位**（否则是「宿主替插件决定业务策略」的镜像问题） |
| B6 业务生命周期挂钩 | 无。撤销/改策略是宿主对自身记录的操作，不是对产品事件的解释与回调 |

**提交前自检三问**：
1. 第二个消费者？——无，唯一消费者是宿主安全闸门本身 ⇒ 但它属 §5.1.3 合法薄壳，非业务代码
2. 第三方能否同形自建？——能（策略/记录是通用机制，非某个产品概念）
3. 新增对产品事件的解释或回调？——无

**结论：不越线，但需在 ADR 0022 补一段**——「授权策略 = 安全闸门，不是业务默认值」这条判据值得写进单一事实源，否则下一个人会以为「宿主替插件决定策略」是允许的。

## 12. 测试矩阵（`unit-test-discipline` 强制）

### 12.1 行为契约 → 用例

| # | 契约 | 正例 | 反例 / 边界 |
|---|---|---|---|
| C1 | 管线顺序 | deny 记录命中 → 拒绝且**不询问** | deny 存在时第一方目录也被拒（deny 优先） |
| C2 | always_ask 语义 | 已授权目录在 always_ask 下**仍询问** | 已有 deny 记录时**不再询问**（不询问 ≠ 忽略拒绝） |
| C3 | always_allow 语义 | 未覆盖的新目标免询问放行 + 以 `source='always_allow'` 落账 | 落账超 500 条上限时丢弃 + 计数 |
| C4 | legacy 回退（§5.2） | 目录仅在 legacy flat 中 → read **与** write 均放行 | 目录在 records 中 `ops=["read"]` → write 被拒（**legacy 同项作废**） |
| C5 | fs ops 拆分 | 授权读某目录后写该目录会**再问一次** | 写授权记录后读写均放行 |
| C6 | origin 归一化 | `HTTPS://API.X.com:443/` 与 `https://api.x.com` 归一到同一条记录 | 带 query 的 URL 落库后 target **不含 query**（凭据红线） |
| C7 | origin 前缀匹配 | `prefix_match=1` 命中同段前缀 | `/v1abc` **不**被 `/v1` 前缀命中（段边界） |
| C8 | 硬闸门不可放行 | always_allow + 记录命中 + 目标为 `169.254.169.254` → **仍拒** | 私网重定向 → 拒（策略不介入） |
| C9 | 弹窗合并 | 同 origin 5 个并发请求 → **1 次** emit，全部放行 | 不同 origin → 各自独立弹窗 |
| C10 | 询问超时 | 30s 无应答 → 按拒绝 | 超时不落任何记录 |
| C11 | 生命周期 | 停用后记录仍在；卸载后记录与策略均清空 | 卸载重装 → 无任何历史记录 |
| C12 | 实时生效 | 改为 always_ask 后**下一次**判定即询问 | 在途弹窗按旧策略走完 |
| C13 | 迁移幂等 | 迁移脚本对同一库跑两次结果一致 | 对旧库（有 `fs_granted_paths` 无新表）跑一次即建表成功 |
| C14 | 第一方可见性 | 第一方免询问项出现在读模型中且可撤销 | 撤销后该目录被 deny 拦截 |

### 12.2 硬性门禁

- 每条用例必须**驱动真实判定链**（不能只测纯函数）——教训来源：上一批 fs_auth 变异自检中，「只断言纯函数」导致「落账粒度改回文件粒度」这个变异 17 项全绿（杀死失败）
- **变异自检**至少覆盖：always_ask 改回读记录 / always_allow 改成询问 / deny 移到第一方层之后 / legacy 短路条件反转 / SSRF 闸门放到策略之后 —— 每个变异必须杀死 ≥1 项
